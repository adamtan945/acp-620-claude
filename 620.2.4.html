620.2.4 · Translate requirements into board filters, sub-filters, and quick filters

把需求翻成 board filter、sub-filter 與 quick filter

一張 board 上看得到哪些卡片，是三層過濾的結果：board filter（saved filter 的 JQL）決定母體，Kanban sub-filter 再拿掉已發布的版本，quick filter 讓讀者當場再篩。考題最愛問「為什麼這張 issue 不在 board 上」，答案幾乎都藏在這三層裡。

術語：考試用 project／issue；現行產品為 space／work item。本教材沿用考試用語，引用現行文件時保留其用語。

Bullet 1

從 filter 建 board

建 board 時有三種來源，前兩種其實也是 filter——Jira 會自動幫你建一個。

來源Jira 幫你做什麼適用
新 project建立 project 的同時，一併把 board 與它背後的 filter 都建好，你不用自己寫 JQL從零開始
既有 project（一或多個）自動產生 filter：project = "X" ORDER BY Rank ASC；需要該 project 的 Browse ProjectsCMP 想要第二、第三個 board
Saved filter你先在 Filters 存好 JQL，建 board 時選「Board from an existing Saved Filter」；可以是自己的或別人分享給你的跨 project board；TMP 要額外 board 的唯一方法
路徑 A：全域
  1. 搜尋列（或按 /）→ Go to all: Boards
  2. 右上 Create board
  3. 選 Scrum 或 Kanban
  4. 選 Board from an existing Saved Filter
  5. 命名、選 filter → Create board
路徑 B：project 側欄
  1. 滑到 CMP 名稱旁出現 ＋ → Create board
  2. 選類型、命名
  3. 下拉選內容 → Advanced
  4. 選 saved filter → Create
誰看得到這張 board
官方原句：新 board「becomes available to all users with access to your chosen filter」。也就是 board 可見度 ＝ filter 的分享設定 ∩ 各 project 的 Browse Projects。filter 是 private，就只有你（和 Jira admin）看得到 board。

Kanban 建好後的 sub-filter

從 saved filter 建 Kanban board，Jira 會自動加上預設 sub-filter（見 下一段）；Scrum board 沒有 sub-filter，因為 Scrum 用「完成 sprint」清掉 Done。

Bullet 2

改 board filter 的後果，與 ORDER BY Rank

在哪裡改
  • Board settings → General → Filter 區塊 → Edit filter query（跳到 filter 編輯）
  • 需要 filter 的編輯權（owner 或被分享為 editor），或是 Jira admin
  • Board admin 不等於 filter editor——常見的「我是 board admin 卻改不了 filter」就是這個
  • 換一張 filter（Board settings → General 指定另一個 saved filter）與改這張 filter 的內容（Edit filter query）是兩件事
  • 沒有該 filter 的編輯權時，用 Save as 另存一份自己的 filter，再把 board 指到新的那張——不要覆寫別人共用的查詢
改了會發生什麼
  • 立即生效：board、backlog、所有這張 board 的報表都用新母體重算
  • 一張 filter 可能被多張 board 共用，改一次全部受影響
  • 被排除的 issue 若在進行中的 sprint 裡，sprint 報表會把它視為「移出」
  • 加了 project 進去，就要確認新 project 的 status 有對到 columns

Rank：能不能拖曳的開關

圖 2　「Enable ranking」＝讓 filter 的 ORDER BY 是 Rank。CMP 建的 board 預設已開；從 saved filter 建的要自己檢查。
  • 按 Add Rank 後 Jira 會自動把 filter 改成以 ORDER BY Rank ASC 結尾。
  • 站台上只該有一個 global context 的 Rank 欄位；多個會讓排序錯亂。
  • Rank 是「相對順序」欄位，不是數字；JQL 可用 ORDER BY Rank 但不能 Rank > 5。
Kanban 專屬

Kanban sub-filter：Done 卡片為什麼會消失

項目內容
預設 JQLfixVersion in unreleasedVersions() OR fixVersion is EMPTY
來源：官方 KB「Kanban board does not show all issues」與 board filter JQL 範例頁；Cloud 的 configure-filters 現行頁已不列此句，實機 Kanban board 預設值相同。
意思這句 JQL 的意思是「只顯示尚未發佈、或根本沒填 fixVersion 的 issue」。Kanban 沒有 sprint 可以完成，它清掉 Done 卡片的方式就是靠 Release 版本：一旦你把完成的 issue 指定某個版本並發佈，它的 fixVersion 就變成 released，於是自動被這個 sub-filter 藏起來——注意是「藏起來」，資料完全沒有被刪除
在哪裡改Board settings → General → Kanban board sub-filter；board admin 或 project admin 可改
常見改法常見的調整有兩種：一是追加條件例如 AND status != Cancelled，把取消的工作也一併藏起來；二是直接把 sub-filter 清空，代價是 board 從此不會再自動清 Done，卡片會一直累積
只有 Kanban 有sub-filter 只存在於 Kanban board，Scrum board 的設定頁面根本沒有這個欄位，因為它是用「完成 sprint」來清 Done 的
證據界線：sub-filter 對「報表」的影響不能一概而論
官方 sub-filter 頁只說它會讓 Reports 呈現不同資料，沒有逐一列出每個報表怎麼套用；而 CFD 與 Velocity 兩頁都明講「board-specific — 只包含符合 board saved filter 的工作」。所以「sub-filter 對所有報表都沒影響」與「所有報表都套用 sub-filter」兩種通則都不能背；作答時要指名是哪一張報表、哪一層 filter。CFD 另有 Refine report 可在報表內再篩選，board 上亮著的 quick filter 不會自動繼承到每種報表。
官方 KB 的陷阱：Fix Version 欄位被藏起來
如果某個 issue type 的 field configuration 把 Fix Version hidden，那個 type 的 issue 對 JQL 來說「fixVersion 不存在」，既不是 unreleased 也不是 EMPTY → 整個 type 從 Kanban board 消失。修法：把欄位設回可見並 re-index，或清空 sub-filter。
Bullet 3、4

Quick filters：讀者的即時篩選器

預設兩個
名稱JQL
Only My Issuesassignee = currentUser()
Recently UpdatedupdatedDate >= -1d

兩個都能刪、能改。

怎麼管理
  • ••• → Configure board → Quick Filters
  • 新增：Name、JQL、Description（可選）→ Add
  • 編輯：直接點 Name 或 JQL 欄位改 → Update
  • 刪除：Delete；排序：拖格線圖示
  • 需要 board admin 或 project admin
  • 「Show quick filters」可把它們顯示成按鈕列而不是下拉

與 board filter 的整合規則

規則說明
作用範圍它只在 board filter（以及 Kanban 的 sub-filter）篩完的結果上再篩一次，方向永遠是往下收窄；沒有任何辦法讓已經被排除的 issue 重新出現
多選AND：同時勾三個 ＝ 三個條件都要符合
JQL 可用什麼任何 JQL 子句，含函數：assignee in membersOf("bugfix")、type = Bug、savedfilter = "My Filter"、duedate <= endOfWeek()
ORDER BY在 quick filter 的 JQL 裡寫 ORDER BY 不會有任何效果，board 上卡片的排序自始至終都由 board filter 的 ORDER BY 決定
與 swimlane／card color 的差別quick filter 是「藏／顯示」；swimlane 是「分組」；card color 是「上色」——三者都用 JQL，但功能不同
狀態記憶誰勾了哪些 quick filter，是記在各自的瀏覽器裡的個人狀態，不會影響其他人看到的畫面，所以放心勾
互斥的兩個 quick filter ＝ 空集合
同時勾 type = Bug 與 type = Task，因為多選是 AND，一張 issue 不可能同時是兩種 type → board 全空。要「Bug 或 Task」必須寫成單一 quick filter issuetype in (Bug, Task)。同理「我的或未指派」要寫 assignee = currentUser() OR assignee is EMPTY，不是開兩個 filter。
練習：Mine＝{A,B}、Bugs＝{B,C}、Tasks＝{A,D}。Mine+Bugs → 只剩 B；Bugs+Tasks → 空集合。
參考

官方範例：常用 board filter JQL

需求JQL
只看進行中的兩個狀態project in (LIFE) AND status in ("In Progress", "To do") ORDER BY Rank ASC
我建立或指派給我、且未發布project in (LIFE) AND (assignee = currentUser() OR reporter = currentUser()) AND (fixVersion in unreleasedVersions() OR fixVersion is EMPTY)
三個 team 的工作（自訂 label 欄位）project in (LIFE) AND (team = ateam OR team = dreamteam OR team = engineroom) ORDER BY Rank ASC
「已完成」的展示 boardproject in (LIFE) AND status in (Done, Duplicate) AND statusCategory = Done ORDER BY assignee（沒有 Rank → 不能拖曳，展示用剛好）
依 label 分工作流project in (LIFE) AND labels in (ui-only, android-app) ORDER BY Rank ASC
下一個要發布的版本project in (LIFE) AND fixVersion = earliestUnreleasedVersion(LIFE)

官方提醒：filter 裡明確寫 project in (...) 會比全站搜尋快很多。

情境練習

先自己判斷，再點開解答

TMP 團隊想要第二張只看 Bug 的 board，怎麼做？
解答
因為 TMP 只有一個內建 board，沒有「再建一個」的入口，所以要繞路走 saved filter。先到 Filters 存一份 JQL：project = X AND type = Bug ORDER BY Rank ASC（結尾的 ORDER BY Rank 別漏，否則新 board 上的卡片拖不動），再到 Boards → Create board → Board from an existing Saved Filter 選它建立。建好之後記得檢查 filter 的分享對象，因為能存取這份 filter 的人才看得到這張 board。
同事說看得到 project，卻在 Boards 清單找不到你建的跨 project board。
解答
因為底層的 saved filter 沒有分享給他。board 本身沒有獨立的分享設定，它的可見度是一個交集：filter 的分享範圍 ∩ 各 project 的 Browse Projects 權限。他有 project 權限只滿足了後半段，前半段沒過，board 就不會出現在他的清單裡。解法是到 Filters 找到那份 filter，把它分享給對應的 project、group 或 role。
Board 上拖不動卡片，也不能建 sprint。
解答
因為這張 board 的 filter 沒有以 ORDER BY Rank 結尾（可能被改成 ORDER BY created，或根本沒寫 ORDER BY）。Jira 是靠 Rank 這個特殊欄位記住人工排序的，沒有它就無法拖曳，連帶建 sprint、sub-task 歸組也會失效——所以這不只是「排序不同」而已。解法是到 Board settings → General 按 Add Rank，Jira 會自動把 filter 補上 ORDER BY Rank ASC。
Kanban board 上 Done 欄的卡片放了一個月都不消失。
解答
因為沒有人發佈版本，或是這張 board 的 sub-filter 被清空了。Kanban 沒有 sprint 可以「完成」，它清 Done 的機制是：預設 sub-filter fixVersion in unreleasedVersions() OR fixVersion is EMPTY 只顯示尚未發佈的工作；當你把 issue 指定一個版本並 Release 掉，它的 fixVersion 變成 released，就自然被 sub-filter 藏起來了。所以卡片堆著不動，通常代表這個 project 根本沒在用 version，或有人把 sub-filter 清掉了。
Kanban board 上所有「Task」都不見了，但搜尋得到；Bug 正常。
解答
這是官方 KB 記載的一個陷阱：Task 的 field configuration 把 Fix Version 設成 hidden 了。欄位一旦被隱藏，對 JQL 來說這個欄位「不存在」——它既不符合 fixVersion in unreleasedVersions()，也不符合 fixVersion is EMPTY，於是預設的 sub-filter 就把整個 issue type 全部濾掉了。Bug 沒事，正是因為它的 field configuration 不同。修法有兩條：把 Fix Version 設回可見並重建索引（re-index），或是把 sub-filter 清空。
使用者勾了「Only My Issues」再勾「Bugs」，抱怨卡片變更少。
解答
這是正常行為：同時勾選多個 quick filter 時，它們之間是 AND 而不是 OR，也就是「既是我的、又是 Bug」的卡片才留得下來，勾愈多當然愈少。如果使用者真正想看的是「我的或 Bug」，那就得另外做一個 quick filter，把 OR 寫在同一句 JQL 裡：assignee = currentUser() OR type = Bug。
PM 想用 quick filter 在 board 上順便看另一個 project 的 issue。
解答
做不到。三層過濾是一個只能往下收窄的漏斗：quick filter 作用的對象是 board filter（與 sub-filter）已經篩完的結果，它沒有能力把被排除掉的 issue 找回來。想看另一個 project，只能往上游動——修改 board filter 的 JQL 把那個 project 納進來（記得接著檢查它的 status 有沒有對應到 columns），或是另存一份 filter 建一張新的 board。
你是 board admin，但 Board settings 的 filter 改不了。
解答
因為 board admin 和 filter editor 是兩種不同的權限。board admin 管的是這張 board 的設定（columns、swimlanes、quick filters…），但 filter 是一個獨立的物件，要改它的 JQL 必須是 filter 的 owner，或是被 owner 加為 editor。解法有三：請 filter owner 把你加進 editors、請 Jira admin 幫忙改（Jira admin 也能變更 filter 的 owner），或是用 Save as 另存一份自己的 filter 再把 board 指過去——最後這招最安全，因為不會動到別人共用的查詢。
Jira admin 把 board filter 的 project = A 改成 project in (A, B)，B 的 issue 卻沒出現在 board。
解答
因為 B project 的 workflow status 還沒有對應到這張 board 的 columns，它們全躺在 Unmapped statuses 面板裡。三層漏斗只解決了「母體有沒有包含它」，而能不能顯示在 board 上還要過 column mapping 這一關——兩個 project 的 workflow 往往不同，這一步幾乎每次擴大 filter 都要做。到 Board settings → Columns 把 B 的 status 逐一拖進對應的欄位即可，特別記得把它的「結束」status 拖到最右欄。
一個 saved filter 被三張 board 共用，其中一張的 admin 想只改自己那張的範圍。
解答
不能直接改——那份 filter 是三張 board 共用的，動一次三張一起變，另外兩個團隊會莫名其妙少一堆卡片。正確做法是先複製再修改：用 Save as 另存一份新的 filter、在新的那份上改 JQL，然後到自己這張 board 的 Board settings → General 把 filter 換成新的。如果只是想臨時看個切面、不需要永久改變範圍，用 quick filter 就好，完全不會影響到別人。
Scrum board 的 Board settings 找不到 sub-filter 欄位。
解答
這是正常的，sub-filter 是 Kanban board 專屬的欄位。原因在於兩種 board 清 Done 的機制不同：Kanban 沒有 sprint，所以需要 sub-filter 搭配 Release 來把已完成的工作藏起來；Scrum 則是靠「完成 sprint」這個動作，一次把最右欄的 issue 清出 board，不需要額外的過濾層。
常見陷阱

考題喜歡設的誤解

誤解事實
「quick filter 多選是 OR」是 AND。同時勾選多個 quick filter，代表這些條件必須全部符合，所以勾愈多卡片愈少；想要 OR 的效果，得把 OR 寫在同一個 quick filter 的 JQL 裡
「quick filter 可以擴大 board 範圍」不行。quick filter 只能在既有結果上繼續縮小，沒有能力把 board filter 排除掉的 issue 找回來；要擴大範圍只能改 board filter
「board admin 就能改 board filter」不一定。改 filter 需要的是該 filter 的編輯權（owner 或 editor），而 board admin 管的只是 board 本身的設定，兩者是不同層級的權限
「Scrum 也有 sub-filter」沒有。sub-filter 是 Kanban 專屬的；Scrum board 靠「完成 sprint」把最右欄的 issue 清出去，不需要這一層
「filter 私有沒關係，board 分享就好」有關係。board 沒有自己的分享設定，它的可見度完全跟著 filter 走；filter 是 private，就只有你和 Jira admin 看得到這張 board
「拿掉 ORDER BY Rank 只影響排序」不只。Rank 是 Jira 記住人工排序的欄位，少了它，board 上的拖曳、建立 sprint、sub-task 歸到 parent 底下全都會失效，不是單純換個排序而已
「Release 會刪掉 Done 的 issue」不會刪。Release 只是讓那些 issue 的 fixVersion 變成已發佈，於是被預設的 sub-filter 藏起來；issue 本身完好無缺，JQL 搜尋、直接開連結都還在
實作（30 分鐘）

在試用站台驗證三層

  1. 存一個 filter project = X ORDER BY Rank ASC，先不分享，從它建 Kanban board；用第二個帳號看 Boards 清單——找不到。分享給 project 後再看。
  2. 把 filter 的 ORDER BY 改成 created，回 board 拖卡片——失效；按 Add Rank 修好。
  3. 建版本 1.0，把兩張 Done 的 issue 填 fixVersion 1.0，Release → 卡片消失；搜尋仍找得到；把 sub-filter 清空 → 卡片回來。
  4. 對 Task 的 field configuration 把 Fix Version 設 hidden，觀察 Task 從 board 消失；還原。
  5. 加 quick filter「Bugs」type = Bug；同時勾 Only My Issues 與 Bugs，數卡片確認是 AND。
  6. 試著寫一個 quick filter project = Y（不在 board filter 內）→ board 變空，證明只能縮小。
  7. 四筆工作交集實驗：在測試 project 建「我的 Bug、我的 Task、未指派 Bug、未指派 Task」四筆。只開 Mine → 預期 2 筆；再開 Bugs → 預期 1 筆；全部清除 → 4 筆回來（證明沒有刪資料）。改用單一 issuetype in (Bug, Task) → 預期 3 筆。
  8. 三層算術對答案：base 有 A、B、C；sub-filter 只保留 B、C；quick filter 只保留 A、C → 最後剩 C。驗收標準：你能分別說出每一層各排除了哪一筆，而且不是靠刪 issue 解決卡片太多。
