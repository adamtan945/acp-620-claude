620.5.3 · Analyze information from agile reports and issue analysis reports

讀懂 Agile 報表

這一節不考「怎麼開報表」，考「這張圖在說什麼」：紅線往上是什麼意思、藍帶變寬代表什麼、預測還要幾個 sprint 是怎麼算的。九份官方報表頁全部讀完，每張報表整理成「看什麼 → 怎麼讀 → 常見誤讀」。

術語：考試用 issue／project；官方報表頁現已改稱 work item／space。本頁沿用考試用語。

記法
Kanban 只有 Control Chart 與 CFD（沒有 sprint 就沒有 sprint 類報表）。TMP 的報表另成一套（burnup、velocity、cumulative flow 等），Sprint report、Epic report、Epic burndown 是 CMP 專屬。

Scrum

Sprint 三兄弟：Burndown、Sprint Report、Velocity

Burndown Chart
  • X＝時間、Y＝board 設定的 estimation statistic（story points／issue count／時間）
  • 灰線 guideline：從 sprint 開始的總量直線降到 0；sprint 開始時沒有 issue 就不會有 guideline
  • 紅線＝實際剩餘；往上跳＝scope 增加或估點調高
  • sub-task 的 story points 不計，只算 parent
  • active sprint 中途加 sub-task，一律算 scope change；差別在 burndown 看不看得到：
    ・Remaining estimate and time spent 開：sub-task 的時間 roll-up 到 parent，scope change 會畫在 burndown 上
    ・關：一樣算 scope change，但 burndown 不會顯示這筆
  • 只含 board filter 內的 issue；最右欄＝Done
  • 報表上方的下拉可以切換 estimation statistic，Jira 會記住你的選擇
Sprint Report
  • 四個清單：Completed、Not completed、Removed、Completed outside of this sprint
  • 星號 *＝sprint 開始後才加入的 issue
  • 3 → 3.5＝sprint 中估點被改過
  • 圖：灰 guideline、紅實際、綠＝有記錄工時時的 time spent
  • 只有 CMP 有；retro 用，也適合 sprint 中途檢查進度
  • 灰線在非工作日保持水平；紅線＝目前還沒解決的工作的總估算，加入或移出 sprint 都會反映在上面
  • sprint 綁的是 board，不是 project：issue 搬到別的 space，sprint 資料不會跟著過去，報表可能對不上
  • 接了 Confluence 可以從 Linked pages 直接建 retrospective 頁
Velocity Chart
  • 每個 sprint 兩根柱：Commitment（開始時的量）vs Completed
  • 拿近幾個 sprint 的 completed 平均當產能，用來規劃下一個 sprint 與做 epic／version 預測
  • Commitment＝sprint 開始時的總估算；sprint 開始後加入的 issue 或改過的估點都不算進 commitment，但會算進 Completed
  • Y 軸用 board 的 estimation statistic：story points、original time、issue count，或任何數字型自訂欄位；sub-task 的估算不計
  • 黑色平均線＝畫面上所有 sprint 的 Completed 平均；sprint 越多預測越準
  • 只有用 Scrum 範本的 board 才打得開
圖 1　Burndown 只有一條「剩餘」線，所以 scope 增加和做完工作會混在同一條線上——這正是 Burnup 要解決的問題（圖 4）。
圖 2　Sprint report 是 retro 的素材：星號和「3 → 3.5」把「沒做完」的原因分成兩類——中途被塞了工作，還是原本就低估。
圖 3　Velocity 拿 Completed 的平均當團隊產能。sub-task 的估點不計；Y 軸用 board 的 estimation statistic。

圖 4　Burnup 比 burndown 多的一件事：把「scope 變了」和「做完了多少」分開畫，所以能一眼看出 scope creep。sub-task 的點數同樣不計。
Scrum

Epic 與 Version 的兩對報表

報表看什麼怎麼讀
Epic Report某 epic 在某時點的 完成／未完成／未估點 清單與進度線依 board 欄位判定 Done；story points 或 issue count 兩種視角；CMP Scrum 專屬
Epic Burndown依 sprint 排的柱狀：淺綠＝該 sprint 完成、淺藍＝原估剩餘、深藍＝sprint 中加入的 scope、灰＝預測的未來 sprint預測＝剩餘 ÷ 近三個 sprint 的 velocity（例：剩 12 點、每 sprint 2 點 → 還要 6 個）；目前 sprint 只有在完成量已超過預測時才計入；未估點超過 30% 會警告，預測不可信
Release Burndown同上，但以 version 為範圍（Jira 沒有 release 實體，version 就是 release）同樣用近三個 sprint 的 velocity預測（velocity 不含 scope change，但總剩餘量含）；未估點超過 30% 標紅；未對應到 column 的 status 完全不計；只在 CMP Scrum board
Version Report版本的完成趨勢線與預測 release 日三條預測：藍線＝依平均日進度；樂觀（左灰帶）＝平均速度 +10%；悲觀（右灰帶）＝−10%。版本估算工作要先完成 10% 才會出現預測；不含 sub-task；只在 CMP Scrum board；受 board 的 working days 設定影響（620.2.6）
「原估」與「scope」的分界
在 epic 開工前就估好的算 original estimate；開工後才加進來、或加進來後又改估點的，算 scope。考題喜歡問深藍段是什麼。
Version report 與 Release burndown 的四個官方細節
  • Version report 排除 sub-task 類型，而且顯示 Released 版本、不顯示 Archived 版本；它是 board-specific（只含 board saved filter 的工作），To Do／Done 依 board 的最左／最右欄判定。
  • Version report 要先完成該版本估算工作的 10% 才算得出預測；藍線是預測日，樂觀＝平均日速度 +10%、悲觀＝ −10%。
  • Release burndown：status 沒有對應到任何 column 的工作「完全不列入」——不進 sprint bar、不算進 % unestimated、也不算 remaining story points。「報表少了一批卡」先查 unmapped status。
  • Release burndown 的預測用近三個 sprint 的完成量；scope change 不列入這個 velocity 計算，但列入總剩餘量；未估點超過 30% 時標紅，預測不可靠。（此 velocity 與 Velocity Chart 的定義不同。）
  • Epic burndown 也一樣：status 沒對應到 column 的 issue 完全不列入。
  • 「近三個 sprint」通常不含目前的 sprint；例外是目前 sprint 的完成量已經超過預測，才會把它算進去。
  • 圖上第一個 sprint＝epic／version 裡第一張離開 To Do 的 issue 所在的 sprint；最後一個＝全部完成的那個，或預測完成的那個。Release burndown 底部顯示的 Planned start／end date 只是參考，不決定畫哪幾個 sprint。
  • sprint 以外發生的變動，會算在「變動日之前最晚開始的那個 sprint」。完成後又 reopen 的 issue，不會再出現在原本那個 sprint。
  • Version report 的橫軸從版本的 Start Date 開始；沒設就從第一張 issue 被加進版本那天開始。預測用的是「從版本開始到現在」的平均每日速度。
來源：Version report、Release burndown report（2026-09-08 查核）

圖 6　Epic burndown 用「還要幾個 sprint」回答進度；深藍段是考題最愛問的——epic 開工後才加進來的工作一律算 scope。

Control chart：cycle time 與可預測性

圖 9　Cycle time＝在所選狀態（columns）裡待了多久；Lead time＝從建立到完成。兩者都在這張圖上，用 columns 篩選切換。
元素官方定義
點一張 issue；Y＝經過時間、X＝離開所選狀態的時間
藍線 rolling average依 issue 數計算，不是依時間：每個 issue 取自己加前後各 X 個 issue 的平均，X＝顯示總數的 20%，最少 5、永遠取奇數。這樣離群點不會把整條線拉歪
藍帶標準差：實際值相對 rolling average 的變異量
可調Columns（要算哪些狀態）、Filters／Quick filters、Swimlanes、Timeframe、Non-working days（排除週末假日）
用途retro 看流程改善有沒有效、給利害關係人看、Kanban 團隊設定目標、找出無效離群點

點的位置橫向＝離開所勾選的最後一個狀態的時間；多張擠在一起會合成一個 cluster 點（高度取平均）；點一下可以看單張 issue

Cumulative flow diagram：色帶變寬的地方就是瓶頸

圖 10　CFD 是累積圖：進過 To do 的數字不會因為往前走而減少，只有新進來才會增加。Done 帶的上升斜率＝throughput。
  • 只含 board filter 內的 issue；顏色對應 board 的 columns。
  • Refine report 可加 filter；期間用下拉或拖曳下方 Overview。
  • 卡片往回拖，數字會減少：官方例子是把一張卡從 Done 拖回 To Do，Done 和 In Progress 各扣 1，To Do 維持不變（因為沒有新卡進來）。所以「每條線只升不降」只在工作一路往前走時成立。
  • 健康的樣子：各色帶平均地一起往上長，只有 Done 帶持續變厚。
  • 官方提醒：CFD 看的是累積 throughput，不等於傳統「同時進行中」的 WIP 數字——判讀時分清「帶在變厚」和「整體在上升」。
  • CFD 依日曆日，不受 working days 設定影響（官方清單：報表有 Burndown、Sprint report、Epic report、Version report、Control chart；gadget 有 Sprint Health 與 Burndown gadget。Velocity 以 sprint 為單位，也不受影響。見 620.2.6）。
讀值練習：累積上界 ≠ 該欄當下的卡數
CFD 是堆疊面積圖，每條線是「累積上界」，某個狀態的實際件數要看色帶厚度（相鄰兩條線的差）。

Issue analysis

非 board 的報表：11 張各長什麼樣子

這 11 張報表不綁 board，從 Reports → More reports 進去，來源選 project 或 filter。考題常用「畫面上有什麼」來出題，例如題幹寫「a chart and a table… unresolved… average age」，答案就是 Average Age。所以下面每張都畫出畫面的長相，粗體是用來分辨的線索。標 * 的 4 張要先開 time tracking。

Average Age Report
未解決的 issue 平均已經放了幾天？
X 軸：時間（每一期）　Y 軸：那個時間點未解決 issue 的平均年齡（天）

長條圖＋資料表；只算未解決的。長條一期比一期高＝舊案子堆著沒人處理，backlog 沒在更新

Resolution Time Report
解決一張 issue 平均要花多久？
X 軸：時間（每一期）　Y 軸：那一期解決的 issue 平均花了幾天

長條圖，只算已解決的。跟 Average Age 剛好相反：一個看還沒解決、一個看已經解決

Created vs Resolved
backlog 在變多還是變少？
X 軸：時間（每一期）　Y 軸：issue 數（逐期計數，或勾 Cumulative 變累積）。紅線＝建立、綠線＝解決

兩條線夾出紅色區（建立＞解決）或綠色區（解決＞建立）；可選 Cumulative Totals；可以標出版本的 release 日（虛線）

Recently Created Issues
團隊跟得上新進來的量嗎？
X 軸：時間（每一期）　Y 軸：那一期新建立的張數（綠＋紅的總高）

每期一根長條＝那期新建立的張數；綠色段＝其中已解決、紅色段＝還沒解決。紅色段越來越長＝跟不上

Time Since Issues
某個日期欄位在哪幾天被設定？
X 軸：時間（每一期）　Y 軸：所選日期欄位落在那一期的 issue 數

先選一個日期欄位（Created、Updated、Due、Resolved 或自訂日期），畫出每天有幾張被設定；可選 Cumulative Totals

Pie Chart Report
依某個欄位分，各佔多少？
沒有座標軸。每一塊扇形＝所選欄位（Statistic Type）的一個值，大小＝張數佔比

project 或 filter ＋ 一個欄位（Statistic Type），只能選值有限的欄位（status、priority、assignee…）

Single Level Group By
filter 的結果按一個欄位分組，每組進度如何？
沒有座標軸，是表格。每一組＝所選欄位的一個值，組內列出 issue，組標題旁的進度條＝該組完成比例

是表格，不是圖；只能用 filter；每組標題旁有進度條、底下列出 issue。最多顯示 1,000 筆

Workload Pie Chart *
每個 assignee 的工作量佔多少比例？
沒有座標軸。每一塊扇形＝一位 assignee，大小＝他手上剩餘工時的佔比（不是張數）

看起來跟 Pie Chart 一樣，但切的是剩餘工時，不是張數。要開 time tracking，靠 Original estimate／Time spent／Remaining 這些欄位，不看 story points

User Workload *
某一個人手上還有多少工作？
沒有座標軸，是表格。列＝project、欄＝未解決張數與剩餘工時，最後一列是合計

先選一個人；表格按 project 列出他的未解決張數與剩餘工時，最後一列是合計。可選要不要算未指派的 sub-task

Version Workload *
這個版本完成前，每個人還剩多少？
沒有座標軸，是表格。列＝assignee、欄＝各 issue type 的剩餘工時，最後是未指派的

先選一個版本（看 Fix Version）；先列每人依 issue type 的彙總，再逐人列出，最後是未指派的。可選是否顯示未估時的 issue

Time Tracking Report *
這個版本的估時準不準、超前還是落後？
沒有座標軸。上方兩條橫條的長度＝時間；下方表格列＝issue、欄＝Original、Remaining、Spent、Accuracy

上方兩條橫條：Progress（綠＝完成、橘＝未完成）與 Accuracy（藍）。Progress 比 Accuracy 長＝落後，反之超前；表格有 Original、Remaining、Spent、Accuracy，Σ 欄含 sub-task。必須有 Fix Version

四組最容易搞混的

這組差在哪一點
Average Age
vs Resolution Time		Average Age 看還沒解決的放了多久（backlog 有沒有在消化）；Resolution Time 看已經解決的花了多久（解決速度有沒有變快）
Created vs Resolved
vs Recently Created		Created vs Resolved 是兩條線，比較同一段時間的建立量與解決量（backlog 淨變化）；Recently Created 是一期一根長條，追蹤「這期建立的卡，後來解決了幾張」（綠＝已解決、紅＝未解決）
Pie Chart
vs Workload Pie
vs Single Level Group By		Pie Chart 算張數，任一個欄位都能切；Workload Pie 算剩餘工時、通常切 assignee、要開 time tracking；Single Level Group By 是表格、只吃 filter、可以看每組的進度
User Workload
vs Version Workload
vs Time Tracking		User Workload 以一個人為主角（跨 project）；Version Workload 以一個版本為主角、依人拆開；Time Tracking 也以版本為主角，但看的是估得準不準（Original vs 實際）
順帶一題：「看某個狀態待了多久」
題目問「一張或一群 issue 在某個 workflow status 停留多久」，答案是 Control Chart：Columns 只勾那個狀態，點圖上的一個點就是單張 issue。它不是 CFD（CFD 看的是各狀態的數量變化，看不到單張卡）。如果題目問的是 dashboard gadget，對應的是 Average Time in Status。

接上 Confluence 後還有兩個：Change Log（Jira issue 清單，可靜態或自動更新）與 Status Report（用 Jira Chart macro，依 status、priority、component、work type 畫圓餅圖）。更多報表在 Marketplace；filter 結果也能匯出到 Excel 自己做圖。

來源：Generate a report（General reports 段）；畫面組成參考 Atlassian 官方 Jira 使用手冊各報表頁（Average Age 等 11 頁，2026-09-24 查核）
Team-managed

TMP 的報表：只有四張，而且要先開功能

TMP 的報表是另一套，張數少很多，前面講的 CMP 報表大部分在 TMP 都看不到。考題常用「TMP 團隊想看某張報表」來設陷阱。

TMP 報表回答什麼前提
Burnup這個 sprint 完成了多少，對照原本計畫的量；紅線（scope）往上就是 scope creep要開 Sprints 功能
Sprint burndownsprint 還剩多少工作；圖下方附五張表：scope changes log、未完成、已完成、sprint 外完成、被移出要開 Sprints 功能
Velocity每個 sprint 的 Commitment（灰）與 Completed（綠），加一條平均線要開 Sprints 功能
Cumulative flow diagram各狀態的卡數隨時間累積，找瓶頸不需要 Sprints；預設顯示整個 project 的完整期間，可用上方日期篩選只看一個 sprint
打開報表的步驟
  • TMP 的 Reports 分頁預設可能不在導覽列，要由 space admin 用 Add to navigation（+）加進來
  • 資料不足的報表不會出現。例如沒開 Sprints 功能，Burnup 和 Velocity 就不會出現
縱軸用什麼算
  • 開了 Estimation 功能 → 用 story points
  • 沒開 → 用 issue 張數，每張卡權重相同
  • 完全不用 sub-task 的資料，就算 sub-task 自己有估點也一樣
TMP 沒有的報表
Control Chart、Sprint Report（清單併在 Sprint burndown 裡）、Epic Report、Epic Burndown、Release Burndown、Version Report。題目問「TMP 團隊想看 cycle time 的離散程度」，答案不會是 Control Chart。可以考慮 CFD，或改用 CMP。
官方兩頁說法不一致
Generate a report 頁的 TMP 段落只列 Burnup 與 Velocity；Enable reports 頁則列出四張（加上 CFD 與 Sprint burndown）。本頁以列得較完整的 Enable reports 為準。
來源：Enable reports、Burnup report、Sprint burndown report、Velocity report、Cumulative flow diagram（TMP）（2026-09-24 查核）
報表以外

Insights：board 上的小圖、backlog 的建議、space 的儀表板

「insights」在 Jira 裡指三種不同的東西。三種都不是傳統報表，但考題會把它們混進選項，所以要分得清楚。

在哪裡Insight它告訴你什麼
Board
（按 Insights 按鈕）		Sprint progress把 sprint 的工作依 status category 切成一條進度條（未開始／進行中／完成），可用 story points、張數或時間估計來算
Sprint burndown用百分比呈現剩餘量，灰線是參考進度；下方列出 sprint 開始後的 scope change
Work items for attention三個分頁：Stuck（在目前狀態停留超過第 85 百分位就自動標為卡住）、Blocked（有 Blocked by 連結）、Flagged（被插旗）
Time in status顯示最耗時的前 5 個狀態與平均停留時間，用來找瓶頸
Epic progress這個 sprint 的工作分別推進了哪些 epic；也會提示有多少工作沒掛 epic
Backlog
（CMP，排 sprint 用）		Sprint commitment拿最近 5 個 sprint 的平均完成量，建議下個 sprint 該承諾的範圍；排超過會提醒你
Work type breakdown這個 sprint 裡各種 work type 佔多少，檢查是不是被 bug 和技術債塞滿
Space insights
（點 Reports 先看到的）		Team overview 等儀表板可自訂的 widget 儀表板（Chart 有 7 種樣式、List、Smart Link、Activity stream）。範圍是整個 space，不受 board 或 board filter 限制。要看傳統報表得按 More reports
Space insights 的規則
  • 一個 space 最多 5 個儀表板
  • 有權限進 space 的人都能看、能篩選；只有 space admin 能建立、改名、編輯、刪除儀表板
  • 只能顯示一個 space 的資料；要跨 space 就改用 Jira dashboard（620.5.2）
  • 歷史資料：Standard 看得到 13 個月，Premium 3 年
兩種「cycle time」別搞混
  • Control Chart：依 board 的狀態計算，你勾哪幾個 column，就算卡片在那幾個 column 待了多久
  • Cycle time report（Reports → Overview）：從第一個 commit 到部署上 production。前提是接好 CI/CD 與原始碼工具、branch／commit／PR 裡要有 issue key，而且要有 View development tools 權限。只算 cycle time 少於 12 個月的 issue
考題長相
「傳統報表用哪個 board 的資料？」→ 目前選的那個 board。「Space insights 用哪些資料？」→ 整個 space。「要一張看多個 project 的總覽」→ 不是 space insights，要用 dashboard。
來源：Board insights、Backlog insights、Space insights、Cycle time report（2026-09-24 查核）

情境練習

先自己判斷，再點開解答

Kanban 團隊想知道「一張卡從開始做到完成平均要幾天」。
解答
用 Control Chart，在設定裡把 Columns 勾選成從 In progress 到 Done 之間的狀態，然後看那條藍色的 rolling average 線。它衡量的正是 cycle time（一張卡實際被處理花了多久）。這題也順便考了 Kanban 的報表範圍——Kanban board 只有 Control Chart 與 CFD 兩張報表，其他都是 sprint 相關的，沒有 sprint 就沒有那些圖。記得把 Non-working days 排除掉，否則週末會被算進等待時間。
Burnup 的紅線在 Day 5 突然往上，Day 8 又往上。
解答
代表 sprint 進行中有兩次追加了工作，也就是典型的 scope creep。Burnup 有兩條線要分清楚：紅線是 work scope（這個 sprint 總共要做多少），綠線才是 completed work（已經完成多少）。所以紅線往上跳絕對不是好消息——它表示目標被墊高了。判讀 Burnup 的訣竅是看兩條線會不會收斂：綠線追上紅線就是完成，紅線一直往上跑而綠線追不上，就是這個 sprint 註定做不完。
Sprint report 裡某張 issue 前面有星號、估點寫 3 → 5。
解答
星號（*）代表這張 issue 是 sprint 開始之後才被加進來的，也就是它不在原本的承諾範圍內。「3 → 5」則代表估點在 sprint 進行中被改過，從 3 點調成了 5 點。這兩個標記都是 retro 時很有價值的線索——它們把「這個 sprint 沒做完」的原因分成了兩類：是中途被塞了工作，還是原本就低估了。順帶記一個相關規則：Velocity Chart 的 Commitment 只計算 sprint 開始當下的量，這些後來加入或調高的都不算進 commitment，卻會算進 completed。
Burndown 沒有灰色 guideline。
解答
因為 sprint 開始的當下，board 上沒有任何有估點的 issue——最常見的操作順序錯誤就是「先按 Start sprint，才把 issue 拉進去」。guideline 這條灰線的定義是「從 sprint 開始時的總量直線降到 0」，起始總量是 0 的話，這條線自然畫不出來。其他可能的原因還有：issue 全都沒填估點、sprint 的日期被設成過去、或使用者時區與站台不一致。正確做法是先把估好點的 issue 放進 sprint，再 Start。
PM 給 sub-task 估了 story points，但 burndown 總量沒變。
解答
這是完全正常的行為，不是報表壞掉。sub-task 的 story points 不計入 burndown、burnup、sprint report 與 velocity，所有 sprint 類報表都只認 standard 層（也就是 parent）的估點——官方在 Velocity chart 的說明頁直接寫了「Estimates from sub-tasks are not included」。唯一的例外是：當 board 的 estimation 設定改成「Remaining estimate and time spent」時，sub-task 的工時（不是估點）會 roll-up 到 parent。所以實務建議是估點只估在 story 這一層，免得團隊誤以為有算到。
Epic burndown 預測還要 6 個 sprint，是怎麼算的？可信嗎？
解答
算法是 剩餘工作量 ÷ 最近三個 sprint 的平均 velocity——例如還剩 12 點、最近三個 sprint 平均每個做 2 點，就推估還要 6 個 sprint。注意它只看最近三個，不是全部歷史，因為近期的表現比較能反映團隊現況。可不可信要看一個警訊：如果這個 epic 底下未估點的 issue 超過 30%，報表會主動警告，這時預測不可靠——因為分子（剩餘量）本身就是低估的。看到警告時，先讓團隊把估點補齊再談預測。
Epic burndown 某個 sprint 的柱子有一段深藍。
解答
深藍色那一段代表該 sprint 期間新增的 scope，也就是 epic 開工之後才被加進來、或是加進來之後又被調高估點的工作。Epic burndown 的顏色要一起記：淺綠＝該 sprint 完成的量、淺藍＝原本估好的剩餘、深藍＝中途追加的 scope、灰＝預測的未來 sprint。判斷「原估」與「scope」的界線很單純：在 epic 開工前就估好的算 original estimate，開工後才進來的一律算 scope。深藍段一路長高，代表這個 epic 的範圍一直在膨脹，預測日期自然不斷往後推。
CFD 上 In review 的色帶三週來越來越厚。
解答
代表 In review 是目前的瓶頸：流進這個狀態的工作比流出去的多，所以在那裡累積。CFD 的判讀原則就是這一條——哪個色帶持續變厚，哪裡就是瓶頸。接下來該做的是查流入與流出的原因（是不是 reviewer 人手不足？是不是 PR 太大？），而不是直接下結論說某個人偷懶，也不該把 WIP limit 調高來讓警示消失——那只是把問題藏起來。另外要注意一個讀圖細節：色帶的「厚度」才是該狀態的件數，累積線的「高度」是上界（含底下所有狀態的總和），兩者不要看錯。
Control chart 的藍帶最近變得很寬。
解答
藍帶代表標準差，也就是實際數值相對於 rolling average 的變異程度。它變寬代表 cycle time 的變異變大、團隊的可預測性下降——同樣一張卡，有時三天完成、有時拖三週，這種團隊很難承諾交期。處理方式是先找出離群的那幾個點看發生了什麼事（是不是卡在等外部回覆？是不是那張卡本來就該拆小？）。如果查出來是無效資料（例如某張 issue 忘了關、掛了三個月），可以用 label 或 JQL 把它排除掉再看一次。
Control chart 的 rolling average 是「過去 7 天平均」嗎？
解答
不是，它跟時間窗完全無關。rolling average 是依 issue 的數量計算的：每一個點取它自己加上前後各 X 個 issue 來平均，而 X 是目前顯示總數的 20%，最少 5 個，而且永遠取奇數。這樣設計的用意是讓單一離群點不會把整條線拉歪，也讓工作量忽多忽少的期間不會產生假訊號。考題很愛拿「過去 7 天平均」這種聽起來合理的說法來設陷阱。
想看某版本預計哪天能 release。
解答
用 Version Report，它會畫出一條藍色的預測 release 日期線，兩側還有樂觀（平均速度 +10%）與悲觀（−10%）的灰帶。想改看「還要幾個 sprint」則用 Release Burndown。有幾個前提要記：Version report 必須先完成該版本估算工作的 10% 才算得出預測、它排除 sub-task、只在 CMP 的 Scrum board 上有，而且會受 board 的 working days 設定影響——沒排除週末的話預測日會偏樂觀。
CMP 有三個 board，開 Sprint report 卻看到別的 sprint。
解答
因為報表是以「目前正在顯示的那個 board」為範圍計算的，不是以整個 project。CMP 可以有多個 board，每個 board 有自己的 filter 與 sprint，所以開報表之前要先切換到正確的 board。這裡也順便區分一個容易混淆的概念：側欄 Reports 一進去先看到的 project insights 是整個 project 的資料，要按 More reports 才會進到這些以 board 為範圍的傳統報表。
跨五個 project 做容量規劃與情境模擬，該建議哪個工具？
解答
建議用 Plans（前身是 Advanced Roadmaps，需要 Jira Premium 或 Enterprise）。判斷的三個層級值得一起記：單一 project 的 epic 時程與依賴，用免費就有的 Timeline；跨多個 project 與團隊的規劃、容量管理與情境模擬，用 Plans；企業級的 portfolio、OKR 對齊、甚至橫跨多個 Jira 站台，才輪到 Jira Align（那是另一個獨立產品，給採用 SAFe、LeSS 這類框架的大型組織）。考試只會問「哪個問題該用哪個工具」，不會考操作細節。
常見陷阱

考題喜歡設的誤解

誤解事實
「Kanban 也有 burndown」沒有。Kanban board 只有 Control Chart 與 Cumulative Flow Diagram 兩張報表——沒有 sprint 就沒有 burndown、burnup、velocity 這些以 sprint 為單位的圖。
「Burnup 紅線是完成量」不是。Burnup 的紅線是 work scope（總共要做多少），綠線才是 completed work（已完成多少）；紅線往上跳代表中途被追加了工作。
「Sub-task 估點會算進 sprint 報表」不算。所有 sprint 類報表與 velocity 都只認 parent 的估點；唯一的例外是 board 改用「Remaining estimate and time spent」時，sub-task 的工時（不是估點）會 roll-up 到 parent。
「Rolling average 是依時間窗算」不是。它依 issue 的數量計算：每一點取自己加前後各 X 個 issue 的平均，X 為顯示總數的 20%，最少 5 個，且永遠取奇數。
「CFD 的帶厚度就是 WIP」不完全是。CFD 呈現的是累積的 throughput，官方特別提醒它與傳統「同時進行中」的 WIP 數字不是同一回事；判讀時要看色帶有沒有「持續變厚」，而不是讀它的絕對值。
「Epic burndown 用全部歷史 velocity 預測」不是。Epic burndown 與 Release burndown 的預測都只採用最近三個 sprint 的完成量，因為近期表現比較能反映團隊現況。
「Working days 影響所有報表」不是全部。官方清單只有報表 Burndown、Sprint report、Epic report、Version report、Control chart，加上 gadget Sprint Health 與 Burndown gadget。CFD 一律按日曆日計算；Velocity 以 sprint 為單位，也不受影響。
「TMP 也有 Control Chart」沒有。TMP 只有 Burnup、Sprint burndown、Velocity、CFD 四張；Control Chart、Sprint Report、Epic 與 Version 系列都只在 CMP。
「CFD 的線只會往上」工作一路往前走時才成立。卡片往回拖（例如 Done 拖回 To Do），下游狀態的數字會減少，To Do 則不變。
「看某狀態待多久用 CFD」CFD 只看各狀態的數量。要看單張或一群 issue 在某個狀態待多久，用 Control Chart（Columns 只勾那個狀態）。
「Workload Pie 跟 Pie Chart 一樣算張數」不一樣。Workload Pie 算的是剩餘工時，要開 time tracking，不看 story points；Pie Chart 才是算張數。
「Reports 頁一打開的儀表板也只看目前 board」那是 space insights，範圍是整個 space。只有按 More reports 進去的傳統報表才以目前 board 為準。
「Advanced Roadmaps 是免費的 Timeline」不是同一個東西。Timeline 免費，但只能看單一 project；Plans（前身 Advanced Roadmaps）是 Premium 以上才有的跨 project 規劃工具，還帶容量規劃與情境模擬。
實作（45 分鐘）

製造一個「有故事」的 sprint，再讀報表

  1. 開一個兩週 sprint，放 6 張有估點的 story。Day 3 加兩張、Day 6 把一張估點 3 改 5、Day 8 移除一張。
  2. 看 Burnup：紅線兩次往上；看 Sprint report：星號與 3 → 5；看 Burndown：guideline 與跳動。
  3. 給 sub-task 估點，確認三張報表都不變。
  4. Kanban board 上讓一張卡在 In review 停 5 天：看 Control chart 的離群點與藍帶；看 CFD 的 In review 帶變厚。
  5. Board settings → Working days 拿掉週末，比較 Version report 與 CFD 哪個變、哪個不變。
  6. Epic 掛 10 張 story，只估 5 張，開 Epic burndown 看 30% 警告。
  7. 用一個最小 sprint 對出 Velocity 的兩個欄位：建 5 點與 3 點兩張 Story，sprint 開始前加入（Commitment ＝ 8）→ 把 5 點移到最右欄 Done → 開始後再加一張 2 點（scope 升到 10、Sprint report 標星號）→ 把 2 點也完成、3 點留著 → 結束 sprint。 預期 Commitment 8、Completed 7（5＋2），未完成的 3 點回 backlog 或下一期。Completed 可以大於 Commitment（期間加入又完成），不是算錯。
  8. 對照 Sprint report 的逐筆清單解釋 8 與 7 的差，再看 Control chart 並記下所選欄位、期間與樣本數——短測試只能驗證「納入哪些欄位」，不足以證明 cycle time 趨勢。
