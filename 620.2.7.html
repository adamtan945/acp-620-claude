620.2.7 · Troubleshoot board and filter configurations

排查 board 與 filter 設定

這一節沒有新知識，全是前六節的組合題：使用者說「issue 不見了」「拖不動」「同事看不到 board」「勾了 quick filter 變更少」，你要能按固定順序找到原因。考題會給症狀，選「最可能的原因」或「第一步該檢查什麼」。

術語：考試用 project／issue；現行產品為 space／work item。本教材沿用考試用語。
這一節考什麼

四條 bullet，翻成考題語言

官方 bullet考題會怎麼問
Understand the relationship between the board filter and board columnsfilter 決定「哪些 issue」，columns 決定「這些 issue 的 status 顯示在哪」；filter 有、column 沒對到 → 不見
Understand the use of RANK in board filters沒有 ORDER BY Rank 會失去哪些功能；Add Rank 在哪
Understand the impact of filter permissions on board accessboard 沒有自己的分享設定；看不到 board ＝ filter 沒分享或沒 Browse Projects；board admin ≠ filter editor
Understand the behavior of stacked quick filters多選＝AND；只能縮小
核心模型

「這張 issue 為什麼不在 board 上」的檢查順序

圖 1　順序是「存在 → filter → columns → sub-filter → sprint／backlog → 檢視狀態」。考題問「第一步」幾乎都是 ②，問「最常見」多半是 ③。
互動

選一個症狀，看檢查順序

點左邊的症狀

    Bullet 1

    Filter 與 columns：一個管「誰」，一個管「在哪」

    圖 2　「搜尋得到、board 沒有」的第一嫌犯是 unmapped status。把 Cancelled 對到最右欄它才會回來（並被視為完成）。
    • 最右欄＝完成：sprint 完成、burndown、velocity 都以最右欄判定。Done／Cancelled／Won't Do 都要對到最右欄，否則 sprint 完不成、報表算不完。
    • Filter 加了新 project，新 project 的 status 名稱不同時會全部落在 Unmapped，整個 project 的 issue 都不出現。
    • Simplified workflow 下，在 board 加 column 會同時建 status；非 simplified 時只能對應既有 status（改 workflow 要 Jira admin）。
    • Kanban backlog：拖進 Kanban backlog 面板的 status，其 issue 只在 backlog 頁出現，不在 board——這不是 bug。
    • Epics panel 開著時，epic 會在 backlog 的面板裡而不是 board 卡片（KB）。
    Bullet 2

    RANK：一個子句，四個功能

    filter 有 ORDER BY Rank ASC沒有（或 ORDER BY 別的欄位）
    拖曳排序 backlog 與 boardboard 與 backlog 上的卡片都拖不動，Jira 沒有欄位可以記住新順序
    Scrum 可建 sprint、把 issue 拉進 sprint建不出 sprint，也沒辦法把 issue 拉進 sprint，等於整個 Scrum 規劃流程停擺
    Sub-task 自動排在 parent 下sub-task 不會跟在 parent 底下，而是散落在清單各處，很難閱讀
    Kanban 從 backlog 拉進 board沒辦法把 issue 從 backlog 拉進 board
    • 修法：Board settings → General → Add Rank，Jira 自動改 filter。
    • Rank 大小寫敏感；站台只該有一個 global context 的 Rank 欄位。
    • 從 saved filter 建的 board 最容易漏；CMP 自動建的 filter 預設就有。
    • 有時是刻意的：展示用 board 想固定照 assignee 或 due date 排，就不要 Rank。
    • Add Rank 改的是 saved filter 本身：其他共用同一張 filter 的 board 也會跟著變。而且 Rank 是全站共用的排序資料，在這塊 board 重排，另一塊以 Rank 排序的 board 也會看到新順序——不是每塊板各留一份優先順序。動正式共用 filter 前先另存測試 filter 驗證。
    Kanban 專屬

    Hide completed work：卡片自己消失、又自己回來

    項目官方說法
    可選的區間1 week、2 weeks、4 weeks，或完全關閉（顯示全部）。沒有 5 週、沒有自訂天數——選項就這四個。
    怎麼算「完成」Kanban board 用 status category 判斷：issue 進到 Done 類別的 status 就算完成。這一點和 Scrum「最右欄才算完成」不同。
    計時從何時起算任何編輯都會把「完成」計時重設。官方原句：Any edits to a work item reset the 'complete' timer——改 Description、改 Fix version 都算。
    後果已經完成很久的 issue，今天被編輯一下就重新出現在 board 上，直到區間再次跑完。這不是 issue 被重開，也不要為了讓它消失去改它的 status 或 version。
    「最近一週」不等於「本曆週」
    Hide completed work 設 1 week，是滾動的 7 天，而且受上面那條「編輯重設計時」影響。週三回看時，畫面上仍可能有上週完成的工作。如果需求真的是「這個曆週解決的工作」，要用 JQL 條件 resolved >= startOfWeek()，並確認時區、每週起始日與 workflow 有正確設定 Resolution。別拿一個只查已解決工作的 filter 去取代整張工作板——那會把未完成的工作也一起藏掉。
    Bullet 3

    Filter 權限決定 board 存取

    圖 3　board 本身沒有分享設定；「分享 board」實際上是分享它的 filter。
    症狀原因與修法
    同事找不到 board多半是 filter 沒有分享出去。到 Filters 頁把該 filter 分享給對應的 project、group 或 role（給 viewer 權限即可）
    同事看得到 board 但少了某個 project 的卡片他缺少那個 project 的 Browse Projects 權限。filter 只開第一道門，每張卡片還要看他對該 issue 所屬 project 有沒有瀏覽權
    我是 board admin 卻改不了 filter因為 board admin 不等於 filter editor。請 filter owner 把你加為 editor，或請 Jira admin 出面（Jira admin 也能變更 filter 的 owner）
    filter owner 離職，board 沒人能改請 Jira admin 到 Filters 的管理頁面把 owner 改成現任的人；這是離職交接時很容易漏掉的一項
    Board 突然消失通常是 board 的 location 掛在已被停用的 project 或已離職的使用者身上。由 board admin 或 project admin 到 Board settings → General 重新指定一個有效的 location 即可
    使用者 A 看到的 board 內容跟 B 不同filter 用了 currentUser()；或兩人 Browse Projects 不同；或各自勾了不同 quick filter
    Bullet 4

    Stacked quick filters：AND，而且只能縮小

    症狀解釋
    勾兩個 quick filter 結果比勾一個少這是正常的。多個 quick filter 之間是 AND，條件愈疊愈嚴格，結果當然愈少
    想看「我的 OR Bug」不能靠同時勾兩個達成，要另外建一個 quick filter，把 OR 直接寫進同一句 JQL，例如 assignee = currentUser() OR type = Bug
    勾了 quick filter 後 board 空白代表這個 quick filter 的條件與 board filter 的結果沒有交集，最典型的是 quick filter 裡寫了一個根本不在 board filter 範圍內的 project
    同事說他的 board 少很多卡片多半是他自己勾了某個 quick filter 忘了取消。quick filter 的勾選狀態存在各人的瀏覽器裡，你在自己畫面上看不出他勾了什麼
    quick filter 的 ORDER BY 沒作用這是預期行為。quick filter 的 JQL 只用來判斷「留下哪些卡片」，排序永遠由 board filter 的 ORDER BY 決定

    先把「管理 sprint」和「改 sprint 裡的工作」拆開

    想做的事要的權限／設定常見誤認
    建立、開始、結束 sprint，改期間或 goalManage sprints；跨 project 的 sprint 要每個相關 project 都有以為 Schedule ＋ Edit 就夠——不夠
    把工作加進／移出 sprint、重排順序Schedule work items ＋ Edit work items ＋ filter 有 Rank；Browse 是前提以為有 Manage sprints 就能改每一張 issue
    設定 board columns、quick filtersboard admin 或 board location 的 project admin；改 filter 另需 filter 編輯權以為 board admin 等於所有來源 project 的動作權
    兩個常被混淆的細節
    • 「建得出空 sprint」和「能把工作放進去」是兩件事，同時成立才叫可用；只有前者不矛盾。
    • Company-managed Scrum backlog 不把 sub-task 當成可獨立規劃的工作。官方明列 backlog 顯示條件之一是「the work item isn't a subtask」，所以 sub-task 不會出現在 backlog 讓你單獨排序。這不能推廣成「所有看板的子工作永遠不能排序」，也別和 parent 詳細頁裡的 sub-task 順序混為一談。
    情境練習

    先自己判斷，再點開解答

    使用者回報「MOB-88 搜尋得到，但 board 上沒有」。第一步檢查什麼？
    解答
    第一步永遠是檢查它符不符合 board filter 的 JQL（Board settings → General 就看得到查詢內容）。因為 filter 決定的是「母體」——不在母體裡，後面所有設定都救不回來。如果確認它有在 filter 範圍內，第二步才去看 status 有沒有對應到某一個 column（unmapped 的 status 不會顯示在 board 上）。第三、四步分別是 Kanban 的 sub-filter 與「Scrum 的 issue 不在 active sprint」。照這個順序查，幾乎所有「issue 不見了」都能定位。
    Jira admin 把 filter 從 project = A 改成 project in (A, B)，B 的所有 issue 都沒出現。最可能原因？
    解答
    最可能的原因是 B project 的 workflow 用的是另一套 status 名稱，這些 status 在這張 board 上從來沒有被對應過，因此全部躺在 Unmapped statuses 面板裡。母體有它們（filter 已經改好了），但沒有欄位可以放，board 自然一張也顯示不出來。到 Board settings → Columns 把 B 的 status 逐一拖進對應的欄位即可——記得把它代表結束的 status 拖到最右欄，否則之後完成 sprint 又會出事。擴大 filter 之後一定要回頭檢查 column mapping，這是跨 project board 的固定動作。
    Sprint 結束時 Jira 說還有 3 張未完成，但團隊確認都 Cancelled 了。
    解答
    因為 Cancelled 這個 status 沒有被對應到最右欄。Scrum 判定完成的唯一依據是 issue 落在最右邊那一欄，跟 status 叫什麼、屬於哪個 category 都無關——所以在 Jira 眼中這 3 張仍是未完成，會被帶到下一個 sprint。到 Board settings → Columns 把 Cancelled 拖進最右欄就解決了。順帶一提，Kanban 的隱藏機制剛好相反，它看的是 status category。
    從 saved filter 建的 Scrum board 沒辦法建 sprint。
    解答
    因為這份 saved filter 沒有以 ORDER BY Rank ASC 結尾。Rank 是 Jira 用來記住人工排序的特殊欄位，少了它不只是排序不同——拖曳、建立 sprint、把 issue 拉進 sprint、sub-task 歸到 parent 底下全都會失效。修法是到 Board settings → General 按 Add Rank，Jira 會自動幫 filter 補上這個子句。要注意這個動作改的是 saved filter 本身，其他共用同一份 filter 的 board 也會一起變。
    PM 想讓展示用 board 固定照 due date 排，且不希望別人拖動。
    解答
    把 filter 寫成 ORDER BY duedate，然後刻意不加 Rank。這是少數「沒有 Rank 反而是優點」的情境：沒有 Rank 就沒有拖曳功能，卡片會穩穩地照 due date 排，任何人都動不了順序，正好符合展示用途。這題想提醒的是——缺少 Rank 不一定是設定錯誤，也可能是刻意的；判斷前先問清楚這張 board 的用途。
    新同事有 project 的 Browse 權限，Boards 清單卻沒有團隊的 board。
    解答
    因為底層的 saved filter 沒有分享給他。board 沒有自己的分享設定，它的可見度完全跟著 filter 走；project 權限只決定「board 上他看得到哪些卡片」，決定不了「他找不找得到這張 board」。解法是到 Filters 找到那份 filter，把它分享給該 project、group 或 role。執行分享的人需要 Share dashboards and filters 全域權限。
    你是 board admin，想加一個 project 到 board，General 頁的 filter 是灰的。
    解答
    因為你不是這份 filter 的 owner 或 editor。board admin 管的是 board 的設定，跟 filter 的編輯權是兩回事——這是實務上最常被誤會的一組權限。三種解法：請 filter owner 把你加進 editors、請 Jira admin 協助（Jira admin 也能變更 filter 的 owner，這在原 owner 已離職時特別有用），或是用 Save as 另存一份自己的 filter 再把 board 指過去。最後這招最安全，因為完全不會動到別人共用的查詢。
    Kanban board 上 Task 全部消失，Bug 正常，搜尋都找得到。
    解答
    這是官方 KB 記載的經典陷阱：Task 這個 issue type 的 field configuration 把 Fix Version 設成了 hidden。欄位被隱藏之後，對 JQL 來說它「不存在」，因此既不符合 fixVersion in unreleasedVersions()，也不符合 fixVersion is EMPTY——而 Kanban 的預設 sub-filter 正是這兩個條件的聯集，於是整個 Task type 被濾光。Bug 沒事，是因為它的 field configuration 沒有隱藏這個欄位。修法：把 Fix Version 設回可見並重建索引（re-index），或是把 sub-filter 清空。
    使用者勾了 Only My Issues 與 Recently Updated，說「我今天改的 issue 明明有，卻不見」。
    解答
    因為多個 quick filter 之間是 AND 而不是 OR。他勾了兩個條件，那張 issue 必須同時「指派給他」而且「最近更新過」才會留下；它今天確實被更新了，但 assignee 不是他，所以被 Only My Issues 這一關擋掉。只要取消 Only My Issues 就會出現。想要「我的或最近更新」的效果，得另外做一個 quick filter，把 OR 寫在同一句 JQL 裡。
    Swimlanes by Epics 時某 epic 的 child 都在，epic lane 卻沒有。
    解答
    因為 epic 本身沒有落在 board filter 的母體內——最常見的情況是這個 epic 屬於另一個 project。swimlane by Epics 是用 epic 當 lane 的標題，epic 進不了母體，lane 就畫不出來，它底下的 child 會散落在下方那一區。解法是把 epic 所在的 project 也加進 board filter（記得接著檢查 column mapping），或是改用其他 swimlane 依據。
    Kanban board 上看不到 epic 卡片。
    解答
    因為 Epics panel 是開啟的。這個設定開著時，epic 會集中呈現在 backlog 左側的面板裡供你分組與篩選，而不是以卡片形式出現在 board 上——這是設計行為，不是 bug，也不代表 epic 被過濾掉了。到 Board settings → Columns 把 Epics panel 關掉，epic 就會回到 board 上變成一般卡片。
    兩位使用者看同一張 board，卡片數不同，filter 沒用 currentUser()。
    解答
    有兩個可能，而且都很常見。第一，其中一人自己勾了 quick filter——quick filter 的勾選狀態記在各自的瀏覽器裡，是個人設定，別人看不到他勾了什麼。第二，如果這是跨 project board，兩人對來源 project 的 Browse Projects 權限不同，少了某個 project 權限的人就少看到那批卡片。排查時先請對方清掉所有 quick filter，若張數還是不同，再去比對權限。
    常見陷阱

    考題喜歡設的誤解

    誤解事實
    「issue 不在 board 就是 filter 寫錯」不一定。filter 寫錯只是可能之一，實務上更常見的是 status 沒對應到 column、被 Kanban 的 sub-filter 濾掉，或是 Scrum board 上那張 issue 根本不在 active sprint 裡
    「board 可以單獨分享」不行。board 沒有自己的分享設定，真正要分享的是底層那份 saved filter；把 board 網址貼給別人並不會給他存取權
    「board admin 可以改 filter」不一定。改 filter 需要的是該 filter 的 owner 或 editor 身分，board admin 管的只是 board 本身的設定，兩者是不同層級的權限
    「沒有 Rank 只是排序不同」不只是排序。少了 Rank，拖曳排序、建立 sprint、把 issue 拉進 sprint、sub-task 歸到 parent 底下全部都會失效
    「Cancelled 放中間欄沒關係」很有關係。Scrum 只把最右欄視為完成，Cancelled 放在中間欄會導致完成 sprint 時被判定未完成、帶到下一個 sprint，burndown 也燒不完
    「quick filter 多選是 OR」是 AND。勾愈多條件愈嚴格、卡片愈少；要 OR 的效果得把 OR 寫在同一個 quick filter 的 JQL 裡
    「Release 會刪掉 issue」不會。Release 只是讓 issue 的 fixVersion 變成已發佈，於是被預設的 sub-filter 藏起來；issue 本身完好，JQL 搜尋照樣找得到
    實作（30 分鐘）

    故意弄壞，再照順序修

    1. 在 workflow 加一個 status「Cancelled」但不對應 column；把一張 issue 轉過去 → board 不見、搜尋有。對到最右欄修好。
    2. filter 改成 ORDER BY created → 拖曳與建 sprint 失效；Add Rank 修好。
    3. filter 設 private → 第二帳號找不到 board；分享給 project 修好。
    4. Kanban：Release 一個版本 → Done 卡消失；清空 sub-filter → 回來；再把 sub-filter 填回預設。
    5. 把 Fix Version 對 Task 設 hidden → Task 消失；還原。
    6. 同時勾兩個 quick filter，記下張數，證明是 AND。
    7. 把 board location 改到個人 profile，再改回 project，觀察 Boards 清單的位置變化。
    8. Hide completed work 實驗：Kanban board 設 1 week，找一張很久前完成的 issue，只改它的 Description → 它重新出現在 Done 欄（計時被重設）。確認你沒有改到它的 status 或版本。
    9. 驗收：你能在不更動任何 issue 業務資料的前提下，說明並修好兩種「卡片消失」（unmapped status 與 sub-filter／hide completed），而且知道「拖不動」是 Rank 問題、「移不到下一欄」是 workflow transition 問題——兩者不同。
