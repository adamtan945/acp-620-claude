620.2.3 · Configure board columns to match a workflow process

設定 board columns 對應 workflow

CMP 的 board columns 和 workflow statuses 是兩個獨立的東西，中間靠「對應」連起來。一欄可以裝多個 status；沒對到任何欄的 status，issue 就從 board 上消失；只有最右欄算完成。這一節的考題幾乎都從這三句話延伸。

術語：考試用 project／issue；現行產品為 space／work item。本教材沿用考試用語。本節內容針對 company-managed；TMP 的 column＝status 見 620.1.2。

核心模型

Column 是 status 的容器；位置決定類別

圖 1　預設 Jira workflow 的對應：To Do ← Open、Reopened；In Progress ← In Progress（自訂 status 如 In Review 也常放這）；Done ← Resolved、Closed。Simplified workflow 則是一對一。
三句話
  • 一欄多 status：把細的 status 收進少數幾欄，board 乾淨、workflow 仍精細。
  • 未對應＝隱形：status 在 Unmapped statuses 面板裡，issue 就不在 board 上。
  • 只有最右欄算完成：Done、Blocked、Canceled 這類「結束」的 status 都要放最右欄，否則完成 sprint 時它們會被當成未完成帶到下一個 sprint。

完成判定

Scrum 看最右欄，Kanban 看 status category

「完成」在 Jira 有四種訊號，考題最愛把它們混在一起。它們不能互相抵銷。

訊號代表什麼不保證什麼
Status目前 workflow 節點，例如 Closed、Canceled名稱含 Done 不代表任何報表都視為完成
Status category每個 status 所屬的 To do／In progress／Done 大類不等於這塊 board 的 column mapping
最右 columnScrum 完成 sprint 與多數 agile report 的完成依據不能直接套用到 Kanban 的 Hide completed work
Resolution結束的結果欄位（例如 Fixed）；空白＝unresolved拖進最右欄不保證任何 workflow 都會替你設定它；reopen 也要處理清除

Kanban 的 Hide completed work

官方 KB：Kanban 用 status category，不是最右欄
原文：Unlike Jira's scrum boards, Kanban boards use status category to determine whether a work item is complete.／When a work item reaches a status in the Done category, the Kanban board considers it complete, regardless of which column the status is mapped to.——所以同一張 issue，在 Scrum 完成判定與 Kanban 隱藏機制裡可能有不同表現。
項目內容
可選區間1 週、2 週、4 週，或完全不隱藏——官方只列這幾個，沒有 5 週之類的選項
判定依據status 落在 Done 類別即視為完成，與它對到哪一欄無關
計時起點任何欄位編輯都會重設計時器（官方點名 Description 等欄位）：改一下描述，早就完成的 issue 會重新出現在 board 上，直到區間再次經過
與 Scrum 的差別Scrum 完成 sprint 只認最右欄；Kanban 隱藏認category ＋ 計時
考題長相
「Kanban board 上出現一張三個月前就 Done 的卡」→ 有人編輯過它，計時器被重設。「Hide completed work 設 1 週，跟 resolved >= startOfWeek() 一樣嗎？」→ 不一樣：前者是滾動 7 天且會被編輯重設，後者是本曆週。
Team-managed 對照

TMP 沒有 workflow scheme，用 transition rules 限制誰能移動

CMP 靠 workflow 的 condition／validator／permission；TMP 則在 Space settings → Work types → 選 work type → Edit workflow → 選 transition → Rules 加規則，其中 Restrict who can move a work item 就是「誰能執行這個 transition」。

項目官方內容
現行五種 ruleAssign a work item to someone／Update a work item field／Restrict who can move a work item／Remind people to update empty fields／Check that a work item has been through a status
每個 transition 的上限10 組 Restrict transition rules，每組 50 條；Validate details 50 條；Perform actions 50 條；每個 transition 最多加 10 條規則
誰能設Role：Administrator；Permission：Administer spaces
官方提醒If you remove the role associated with the rule, your team may have trouble moving work items through your workflow.——移除規則綁定的 role 會讓團隊卡在 transition
證據界線
舊教材常斷言「只能選人與 role」。本次核對到的官方頁只確認規則的存在、上限與所需權限，未取得可選對象的逐項清單；實際下拉選單支援哪些對象（指定使用者／role／group／特定 permission）請以站台畫面為準。另外要分清兩件事：直接指定 group，與讀取某個 group picker 欄位的值當允許名單，後者不能從前者推得。
卡片不見了

官方的排查順序

  1. Board filter：Board settings → Details，確認 filter 涵蓋你要的 issue type 與 status。
  2. Status 對應：Layout → Columns，確認要看的 status 都對到某一欄。
  3. Backlog feature：Project settings → Features，確認 Backlog 有開（TMP）。
  4. Backlog 對應：要放在 backlog 的 status 有沒有對到 Backlog 欄（Kanban backlog）。
補兩條最常見的
Scrum board：issue 不在 active sprint 就不在 board 上，去 Backlog 找。Kanban board：status 落在 Done 類別且超過 Hide completed work 的區間就會被隱藏（與對到哪一欄無關）；反之被編輯過就會重新出現。
情境練習

先自己判斷，再點開解答

Jira admin 在 workflow 加了「In Review」，但 board 上進 review 的 issue 全部消失。
解答
因為新建的 status 一開始是沒有對應到任何 column 的，它躺在 Board settings → Columns 頁面的 Unmapped statuses 面板裡。board 只顯示「status 有對到某一欄」的 issue，所以一旦有人把 issue 轉到 In Review，那張卡就從 board 上消失了。要強調的是 issue 完全沒有被刪除，用 JQL 或直接開 issue key 都找得到。解法是到 Columns 頁把 In Review 從 Unmapped 拖進 In Progress 欄（或另外建一個新欄），卡片就會回來。
Complete sprint 時，Cancelled 的 issue 被帶到下一個 sprint。
解答
因為 Cancelled 這個 status 沒有被對應到最右邊那一欄。Scrum 判斷「這張 issue 完成了沒」的唯一依據，是它落在最右欄，跟 status 叫什麼名字、屬於哪個 category 都沒有關係。所以在 Jira 眼中，Cancelled 的 issue 只是還沒做完，完成 sprint 時當然會被帶到下一個 sprint。解法是到 Board settings → Columns 把 Cancelled 拖進最右邊的 Done 欄。
Board admin 刪掉了「Review」欄，工程師問 issue 是不是被刪了。
解答
沒有被刪。刪除一個 column 只會把它裡面的 status 退回 Unmapped statuses 面板，issue 本身、它的 status、歷史紀錄都原封不動，只是暫時不顯示在 board 上而已；用 JQL 搜尋或直接開 issue key 都還在。只要把那些 status 重新對應到某一欄，卡片就會回到 board 上。這也是為什麼刪 column 是一個相對安全、可還原的操作。
Board admin 把 Done 欄拖到中間、把「QA」欄放到最右。
解答
這個動作的後果比看起來嚴重。column 的位置決定 status 的類別，最右邊那一欄永遠代表「完成」，跟欄位叫什麼名字無關。所以搬動之後，只有 QA 欄裡的 issue 才算完成，原本 Done 欄裡那些真正做完的 issue 反而被降級成進行中；連帶 burndown 曲線、sprint 的完成判定、velocity 全都會算錯。要記住這句話：最右欄才是完成欄，Done 只是個名字。
Project admin 想在 board 上直接加一個 status，Columns 頁沒有 Add status。
解答
因為「在 board 上直接加 status」這個能力，只有在 project 使用 simplified workflow 時才會出現。它的條件很嚴格：board 的 filter 只能包含一個 project、該 project 的所有 issue type 共用同一個 workflow、這個 workflow 只用到 Atlassian 內建的 post function／validator／condition、而且每個 status 至少有一條出去的 transition。四個條件缺一個，Add status 按鈕就不會出現。不符合的話，就得請 Jira admin 到 workflow editor 裡加。
In Progress 設了 max 3，但團隊還是能拖第 4 張進去。
解答
因為 column constraints 只是視覺提醒，不具備強制力。超過上限時，欄位標題會變成紅色（低於下限則是黃色），但 Jira 不會阻止你把第 4 張卡拖進去。這是刻意的設計——WIP 限制是團隊自律的工具，不是系統的鎖。想真正擋住轉換，得靠 workflow 的 condition 或 validator，那是另一回事。
用 quick filter 只看自己的 issue，In Progress 只有 2 張，欄頭卻是紅的。
解答
因為 constraints 計算的是整欄的實際總數，跟你眼前看到幾張卡片無關。quick filter 只是暫時把不符合條件的卡片藏起來，它們仍然待在那一欄裡、仍然被計入。所以會出現「畫面上只有 2 張、欄頭卻是紅的」這種看似矛盾的情況。想看真實數量，把 quick filter 關掉即可。
Scrum 團隊開了 constraints，sub-task 一多欄頭就紅。
解答
把 constraint 的計算方式從 Issue count 改成 Issue count, excluding sub-tasks。Scrum 團隊在意的 WIP 是「同時進行幾張 story」，而不是「畫面上有幾張卡」；一張 story 底下拆五個 sub-task 是很正常的事，用預設的計算方式當然一下就爆表。這個選項就在 Board settings → Columns 的 Column constraints 下拉裡。
誰能改一個 board 的 columns？
解答
兩種人可以：該 board 的 location 所在 project 的 project admin，以及被列在 Board settings → Administrators 裡的 board admin（Jira admin 因為權限涵蓋一切，當然也可以）。要注意的是其他 project 的 admin 沒有這個權限——跨 project board 上，來源 project 的 admin 並不會因此取得管理權。
Simplified workflow 下想刪掉「Blocked」status，按鈕是灰的。
解答
有兩個可能。第一，還有 issue 停在 Blocked 這個 status——官方規定要刪除 status，該 status 底下必須沒有任何 issue，先用 JQL 找出來轉走即可。第二，你不是 project admin，simplified workflow 的 status 增刪只有 project admin 做得到。另外補充一個容易誤解的行為：如果站台上別的 workflow 也在用 Blocked，那麼這個刪除動作只是把它從目前這個 workflow 移除，status 物件本身還存在。
Jira admin 建了自訂 status「Waiting」，board 的 Unmapped 面板卻沒有它。
解答
因為 Unmapped statuses 面板只列出「board filter 涵蓋的 project，其 workflow 真的有用到」的 status。Jira admin 在站台上建立一個 status，只是產生了一個物件；除非有人把它加進某個 workflow、而那個 workflow 又被這個 project 使用，否則 board 根本不知道它的存在。解法是請 Jira admin 先把 Waiting 加進對應的 workflow，它才會出現在 Unmapped 面板供你對應。
Kanban board 設了「隱藏 2 週前完成的工作」，卻出現一張半年前就 Closed 的卡。
解答
因為有人編輯過那張 issue，讓完成計時器被重設了。Hide completed work 的計時起點不是「它什麼時候變成 Done」，而是「它最後一次被更新是什麼時候」——官方 KB 特別點名連改一下 Description 這種無關緊要的編輯都會重設。所以一張半年前就 Closed 的卡，只要昨天有人補了一句說明，它今天就會重新出現在 board 上，要等 2 週的區間再次經過才會消失。
某 status 的 category 是 Done，但在 Kanban board 被對到中間的欄位。它會被 Hide completed work 隱藏嗎？
解答
會被隱藏。這是 Scrum 與 Kanban 最容易混淆的一組規則：Kanban board 是用 status category 判定完成的，官方原文明講「當 issue 到達 Done 類別的 status，Kanban board 就視它為完成，不管那個 status 被對應到哪一欄」。而 Scrum 完全相反，只認最右欄。所以同一張 issue，在 Scrum 的完成 sprint 判定與 Kanban 的隱藏機制底下，可能出現完全不同的行為。
選項寫「Hide completed work 可以設 5 週」。
解答
錯的。官方文件列出的選項只有四個：1 週、2 週、4 週，以及完全不隱藏，沒有 3 週、5 週或自訂天數這種東西。考題很喜歡用一個「看起來很合理的數字」來設陷阱，這幾個硬性選項值得直接記起來。
TMP 團隊想限制只有特定角色能把 issue 移到 Done。
解答
TMP 沒有 CMP 那套 workflow scheme 與 condition，取而代之的是 transition rules。路徑是 Space settings → Work types → 選一個 work type → Edit workflow → 點該 transition → Rules，加上 Restrict who can move a work item 這條規則。操作者需要 Administrator role 或 Administer spaces 權限。有一個官方特別提醒的坑：如果日後把規則所綁定的那個 role 刪掉，團隊就會卡在這個 transition 動彈不得，所以調整 role 之前記得先檢查有沒有 rule 依賴它。
常見陷阱

考題喜歡設的誤解

誤解事實
「Column 就是 status」（CMP）在 CMP，column 與 status 是兩個獨立的物件，中間靠對應關係連起來，一欄可以裝好幾個 status；只有 TMP 才是「column 就是 status」的一體兩面
「刪 column 會刪 issue」不會。刪 column 只是把裡面的 status 退回 Unmapped 面板，issue、status、歷史紀錄全都還在，只是暫時不顯示在 board 上
「加 column 就會出現新 status」只有使用 simplified workflow 的 project 會同時建一個同名 status；一般 workflow 底下加 column 就只是多一個空欄，還得自己把既有 status 拖進去
「叫 Done 的欄就是完成欄」不對。決定完成的是最右邊那一欄的位置，跟它叫不叫 Done 完全無關；把 Done 欄拖到中間，它裡面的 issue 就不再算完成了
「Constraints 會擋住超量」不會。超過上限只會讓欄位標題變紅（低於下限變黃），Jira 不會阻止你把卡片拖進去，它是提醒而不是鎖
「Quick filter 隱藏的不算 constraint」照算。constraints 算的是整欄的實際總數，quick filter 只是把卡片藏起來，被藏的仍然計入
「Project admin 隨時能加 status」不是。只有在 project 使用 simplified workflow（四個條件全部符合）時，Columns 頁才會出現 Add status；否則就得請 Jira admin 到 workflow editor 加
「改欄名會改 status 名」不會。column 與 status 是分開的物件，改欄名只是改 board 上的顯示文字，status 名稱不受影響（simplified workflow 也一樣）
「Kanban 也是最右欄才算完成」不是。Kanban 的完成判定看的是 status category（只要落在 Done 類別就算完成，不管對到哪一欄）；只認最右欄是 Scrum 的規則
「完成超過設定區間就一定看不到」不一定。任何欄位的編輯都會重設那個計時器，連改一下 Description 都算；被編輯過的卡片會重新出現在 board 上，直到區間再次經過
「一個 status 可以同時對到兩欄」不行。在同一塊 board 上，一個 status 只能對應到一個 column；反過來則沒有限制，一個 column 可以裝很多個 status
實作（30 分鐘）

把三句話做出來

  1. 請 Jira admin 在 LAB 的 workflow 加「In Review」與「Cancelled」；回 board 觀察這兩個 status 的 issue 消失，到 Columns 看 Unmapped 面板。
  2. 把 In Review 拖進 In Progress 欄、Cancelled 拖進 Done 欄；建一個 sprint 含一張 Cancelled 的 issue，Complete sprint 確認它算完成；再把 Cancelled 拖到中間欄重做一次，看它被帶到下一個 sprint。
  3. 把 Done 欄拖到中間，看 burndown 變化，再拖回去。
  4. 開 constraints（excluding sub-tasks），In Progress 設 max 2，拖第 3 張進去看欄頭變紅；用 quick filter 隱藏一張，確認仍紅。
  5. 建一個只含 LAB、用專屬 workflow 的 board → Columns 頁出現 Add status；把 filter 改成兩個 project → 按鈕消失。
  6. Hide completed work：在 Kanban board 設「隱藏 1 週前完成的工作」，把一張 issue 移到 Done 類別的 status（刻意對到中間欄）→ 確認它仍被視為完成而隱藏；接著編輯它的 Description → 確認它重新出現。
  7. 安全重現 Unmapped：新增一個「Review view」欄並把測試 status 對進去 → 卡片出現 → 只刪這個欄 → status 回到 Unmapped、卡片從 board 消失；用 issue key 直接開或 JQL 搜尋，確認 issue 與 status 都沒變（刪欄 ≠ 刪 issue）→ 再把 status 對回原欄，卡片恢復。
