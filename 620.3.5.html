620.3.5 · Configure and troubleshoot automatic issue assignment (project default, components)

設定與排查自動指派：project default、components、automation

「Automatic」這個 Assignee 選項到底會把 issue 丟給誰？官方主頁只講了兩層（component → project default），多個 component 的優先順序藏在 KB 裡。這一節把三個設定位置、一條完整的決策鏈與排查步驟整理成一張圖與一個可以自己按的實驗。

術語：考試用 project／issue／project lead；現行產品為 space／work item／space owner。本教材沿用考試用語。
這一節考什麼

兩條 bullet，翻成考題語言

官方 bullet考題會怎麼問
Understand how components, project default and automation rules can be used to auto-assign issues「要讓某模組的 issue 自動給負責人，該設哪裡？」「project default 只能設誰？」「輪流指派要用什麼？」——三種手段各自的能力邊界
Understand auto-assignment behavior when there are multiple components「issue 同時掛 Backend 與 Alpha 兩個 component，lead 不同，誰被指派？」「lead 沒有 Assignable User 會怎樣？」——優先序與字母序
核心模型

Automatic 的完整決策鏈

官方主頁的敘述只有兩句：有 component 帶 default assignee 就用它，沒有就用 project 的 default assignee。KB 補上了多 component 時的規則：依 default assignee 的「類型」分優先序，同一優先序再依 component 名稱字母序，而且被指派者一定要有 Assignable User 權限。

圖 1　主頁只有前三格；第四格的優先序與第五格的權限檢查來自 KB「Manage components default assignee」。
考題最愛的那一句
多個 component 且 lead 不同時，Jira 依 component 名稱的字母順序（不是 lead 名字、不是加入順序）取第一個 component 的 lead。

    設定位置

    三個地方、三種能力邊界

    手段在哪設、誰能設能設成誰適合
    Project default assigneeProject settings → Details；project admin只有兩種：Unassigned 或 Project lead（官方原句：「the default assignee can only be either Unassigned, or the Space owner」，2026-09-08）。要指派別人得先換 project lead／ownerOpen project 讓全站丟需求，由 lead 先收單分派
    Component default assigneeProject settings → Components；project admin（只有 CMP 有 components）Component lead／Project lead／Unassigned／Project default 四選一。Component 的設定會覆蓋 project default依模組、團隊分工，各自的負責人自動接手
    Automation「Assign issue」Project settings → Automation；project admin（project rule）指定人、Unassigned、群組中的人（平衡工作量／隨機／輪流）、觸發者、欄位或 smart value 指定的人、相關 issue 的 assignee、on-call…輪流、平衡負載、依欄位值分流、跨 project 複製 assignee
    兩個常被忽略的前提
    • 被指派者要有 Assignable User 權限（CMP permission scheme）。Component lead 沒有 → Jira 跳過他，往優先序的下一個候選人（KB 原句：「Although Jupiter is a Component Lead, she doesn't have the Assignable user permission in the project. Thus, Jira can't assign the new issue with the Zeta component to Jupiter.」，2026-09-08 查核）。若所有候選人都不合格會落到 project default 或 Unassigned；混合多種 default 類型的極端情境官方未逐一列出，實機驗證。
    • Default assignee 想設 Unassigned，⚙ → System → General configuration 的「Allow unassigned issues」必須是 ON；關著的話 Details 頁根本不給選。

    Component 的四個 default assignee 選項

    選項意思多 component 時的優先序
    Component lead指派給這個 component 的 Lead 欄位所填的人；官方建議優先使用這一種，人員異動時只要改 component 的 lead 即可1（最高）
    Project lead指派給整個 project 的 lead（現行 UI 稱 Space owner），不管這個 component 自己的 lead 是誰2
    Unassigned刻意不指派任何人；前提是站台的「Allow unassigned issues」開關是開著的，否則這個選項不會出現3
    Project default不自己決定，退回去採用 project 的 Default assignee 設定；在多 component 比較時它的優先序最低4（最低）

    同一優先序有多個 component → 依 component 名稱字母序取第一個。現行 UI 把 Project lead 標示為「Space owner」、Project default 標示為「Space default」。

    用 Automation 取代

    Components 做不到的，交給「Assign issue」action

    Component 只能指到「一個固定的人」；一旦需求是輪流、平衡負載、依欄位值分流，就要用 automation。官方列出的指派方式：

    從一組人裡挑
    • Balanced workload：在指定的 JQL 範圍內比較每個人目前手上的 issue 數量，指給最少的那一位，讓負載趨於平均
    • Random：從名單中隨機挑一位，不考慮工作量或順序
    • Round robin：照名單順序輪流指派，每個人接到的張數大致相同
    • 可排除特定人、限定群組
    從 issue 本身推導
    • Copy from field：例如指給 Reporter、前一任 assignee、某個 user picker 欄位的人
    • Smart value：例如留言者 {{comment.author}}
    • Related issue：複製 parent／linked issue 的 assignee
    • Automatic：走上面那條 component／project default 決策鏈
    • Event triggerer、指定人、Unassigned、user group、團隊中的特定 role、on-call responder（多個輪值時隨機）
    考題型態
    「支援團隊三人輪流接單」→ Automation：Issue created → Assign issue → Round robin。「Bug 要自動給開單者的主管」→ 不是 component，用 automation 的 smart value／欄位複製。「前端 issue 自動給前端負責人」→ component default assignee＝Component lead，最省事。

    Automation 規則本身的觸發、條件、actor 權限，在 620.4 詳講；這裡只要記得它是第三種指派手段，且 actor 也要有 Assign Issues 權限，被指派者也要 Assignable User。

    兩個「Automatic」不是同一件事
    Automation 的 Assign work item action 文件把 Automatic 描述為「指派給 project 的 default assignee」；而建立畫面 Assignee 欄的 Automatic 走的是上面那條完整的 component → project default 決策鏈。比較兩種入口時要看實際 action 設定與 audit log，考題沒說有 automation 時，不要自行假設存在改寫規則。來源：Jira automation actions、Automatic assignee（2026-09-08 核對）
    「建好時是 Amy，幾秒後變 Ben」怎麼查
    先看 issue 的 History（誰改的、什麼時間），再查同一時段的 automation audit log。建立當下是 Amy → component 決策鏈本身正確；之後變 Ben 是另一個事件（automation 或 workflow post function）。不要靠改 component 名稱去修正 automation 造成的結果。
    排查

    「明明設了自動指派，為什麼沒指到？」

    症狀依序檢查
    選了 Automatic，結果是 Unassigned① issue 有沒有掛 component ② component 的 default 是不是 Unassigned ③ 沒 component 時 project default 是否為 Unassigned ④ 候選人有沒有 Assignable User
    指到「另一個」component 的 lead多 component：先看 default assignee 類型優先序，再看 名稱字母序（Alpha 排在 Backend 前）
    Component lead 明明是他，卻指給 project lead該 lead 沒有 Assignable User 權限，Jira 跳到下一層（Project lead）
    Details 頁 Default assignee 選不到 Unassigned⚙ General configuration 的 Allow unassigned issues 是 OFF
    想設某位 PM 當 default，選單裡沒有Project default 只能 Unassigned／Project lead；先把 PM 設成 project lead，或改用 automation
    TMP 找不到 ComponentsTMP 沒有 components；用 automation 或改建 CMP
    不確定是「一開始就指錯」還是「後來被改掉」先開 issue History 看建立當下的 assignee 與後續每次變更的人與時間；再比對同時段 automation audit log。分清「初始指派」與「後續覆寫」再往下查
    Component 的 default 指不到有效的人記錄實際 fallback／錯誤結果，不要假設所有失效情境都有同一種 fallback；把設定、版本與 History 一起留存（實機驗證）
    Automation 規則有跑但沒指派Audit log 看 actor 是否有 Assign Issues、目標是否有 Assignable User；Balanced workload 的 JQL 範圍是否為空
    情境練習

    先自己判斷，再點開解答

    Issue 掛了 Backend（lead 阿宏，default＝Component lead）與 Alpha（lead 小傑，default＝Component lead），建立時選 Automatic。誰被指派？
    解答
    是小傑。判斷分兩步：第一步比較兩個 component 的 default assignee 類型優先序——兩者都設成 Component lead，屬於同一級，分不出高下；第二步才依 component 名稱的字母序取第一個，Alpha 排在 Backend 之前，所以由 Alpha 的 lead 小傑接手。特別注意比的是 component 的名稱，不是 lead 的姓名，也不是誰先被建立或先被掛上去。
    承上，小傑沒有 Assignable User 權限。誰被指派？
    解答
    改成阿宏。因為自動指派有一個必要條件：被指派的人必須具備 Assignable User 權限。小傑雖然在字母序上勝出，但他不是合格的候選人，Jira 會跳過他、往決策鏈的下一個候選人找，於是輪到 Backend 的 lead 阿宏。官方 KB 有一句對應的原文（Jupiter 雖然是 Component Lead，但沒有 Assignable user 權限，所以 Jira 無法把 issue 指派給她）。如果所有候選人都不合格，最後會落到 project default 或 Unassigned。
    Issue 只掛 Zeta（default＝Project default），project 的 Default assignee 是 Project lead 小美。結果？
    解答
    是小美。因為 Zeta 這個 component 的 default assignee 設定是「Project default」，意思就是「我不做決定，退回去用 project 的設定」；而 project 的 Default assignee 是 Project lead，也就是小美。這個選項存在的意義是讓某些 component 明確表態「照 project 的規矩來」，跟「沒有設定」在多 component 比較時的優先序不同——Project default 的優先序是最低的第 4 級。
    PM 想把 project 的 Default assignee 設成 QA 小傑，但小傑不是 project lead。怎麼辦？
    解答
    因為 Project default assignee 的下拉永遠只有兩個選項：Unassigned 或 Project lead（官方原句寫的是 Unassigned 或 Space owner），它不是一個可以自由挑人的 user picker。所以有兩條路：把小傑改設成 project lead（副作用是他會連帶接收 project lead 的通知與某些權限），或是改用 automation——建一條 Issue created → Assign issue → 指定小傑的規則，彈性高得多，也不用動 project 的組織設定。
    三位客服要輪流接單，該用哪個手段？
    解答
    要用 automation：建一條 Issue created 觸發、動作是 Assign issue 並選 Round robin（依序輪流）的規則，把三位客服放進名單即可。如果希望依照每個人手上的工作量分派而不是硬性輪流，改選 Balanced workload。這題的關鍵是認清能力邊界：component 的 default assignee 只能指向「一個固定的人」，做不出輪流、隨機或負載平衡，那是 automation 的守備範圍。
    Component default 設成 Unassigned，卻存不了或選不到。原因？
    解答
    因為站台層級的開關 Allow unassigned issues 被關閉了（⚙ → System → General configuration）。這個開關關著的時候，整個站台不允許存在沒有 assignee 的 issue，所以任何地方的 Unassigned 選項都會消失或存不起來——不只 component，project 的 Details 頁也一樣。要開啟只能請 Jira admin 處理，這是全域設定，改了會影響所有 project。
    Issue 掛了 Docs（default＝Unassigned）與 Zeta（default＝Project default），project default 是 Project lead。結果？
    解答
    結果是 Unassigned。這題考的是四級優先序：Component lead（1）＞ Project lead（2）＞ Unassigned（3）＞ Project default（4）。Docs 的設定是 Unassigned（第 3 級），Zeta 是 Project default（第 4 級），Docs 的優先序比較高就直接勝出，根本輪不到比字母序（字母序只在同一級時才用得上，而且 Docs 的字母序本來也在 Zeta 之前）。很多人會直覺認為「有人可指派總比不指派好」，但 Jira 的規則是照這張表走，不看結果好不好。
    TMP 團隊想「前端 issue 自動給前端負責人」，Components 頁找不到。
    解答
    因為 TMP 根本沒有 components 這個功能，找不到是正常的。替代做法是用 automation：例如 Issue created 觸發，加一個條件判斷某個欄位或 label 是不是「前端」，成立就執行 Assign issue 指定前端負責人。如果這類依模組自動分派的需求很多、又希望有內建的 lead 與報表支援，那更根本的建議是改用 company-managed project。
    某條 automation 的 Assign work item action 選了「Automatic」，團隊以為它會走 component 決策鏈，結果全部指到 project lead。為什麼？
    解答
    因為這是兩個同名但不同行為的「Automatic」。automation 的 Assign work item action 裡的 Automatic，官方文件描述的是「指派給 project 的 default assignee」；而建立畫面上 Assignee 欄位的 Automatic，走的才是完整的 component → project default 決策鏈。團隊誤以為兩者相同，結果 automation 直接跳過 component 這一層，全部落到 project lead 身上。要按 component 分流，正確做法是在規則裡加條件判斷 component，再用「指定人」或「從欄位複製」來指派。
    Issue 建立時 assignee 是 Amy，幾秒後變成 Ben。第一步該查哪裡？
    解答
    第一步一定是開這張 issue 的 History，看清楚「誰在什麼時間把 assignee 改掉了」。這一步的價值在於分辨是「一開始就指錯」還是「後來被改掉」——建立當下是 Amy，代表 component 的決策鏈本身完全正確，幾秒後變 Ben 是另一個獨立事件造成的，通常是 automation 規則或 workflow 的 post function。第二步再去比對同時段的 automation audit log 找出是哪一條規則。切記不要用改 component 名稱字母序的方式去「修正」這種問題——病因不在那裡，改了只會讓設定變得難以理解。
    手動在建立畫面選了 Kevin，issue 同時掛了 Backend（lead 阿宏）。誰被指派？
    解答
    是 Kevin。整條 component → project default 的決策鏈，只有在 Assignee 欄位維持 Automatic 時才會啟動；一旦有人手動指定了對象，就是直接照他選的走，自動規則完全不介入。這也提醒排查時要先確認一件事：使用者抱怨「自動指派沒生效」時，先去看那張 issue 建立當下 Assignee 欄位到底是不是 Automatic，很多時候只是有人順手選了人。
    常見陷阱

    考題喜歡設的誤解

    誤解事實
    「多個 component 時取『先加的』或『lead 名字字母序』」都不是。比的是 component 的名稱字母序，而且要先比 default assignee 的類型優先序（Component lead ＞ Project lead ＞ Unassigned ＞ Project default），同一級才輪到字母序
    「Project default 可以設任何人」不行。它的下拉永遠只有兩個選項：Unassigned 或 Project lead（owner）；想指派其他人，得先換 project lead 或改用 automation
    「Component lead 一定會被指派」不一定。被指派者必須具備 Assignable User 權限，沒有的話 Jira 會跳過他，往決策鏈的下一個候選人找
    「Project default 比 component 優先」剛好相反。component 的 default assignee 會覆蓋 project 的設定；只有在 issue 沒掛任何 component、或 component 明確選了「Project default」時，才會退回 project 的設定
    「TMP 也能用 components 自動指派」不行，TMP 完全沒有 components 這個功能；要在 TMP 做依模組自動指派，只能靠 automation
    「輪流指派可以用 component 做」不行。component 的 default assignee 只能指向一個固定的人，輪流與負載平衡要用 automation 的 Round robin 或 Balanced workload
    實作（30 分鐘）

    在試用站台上驗證決策鏈

    1. CMP 建三個 component：Alpha（lead＝B，default＝Component lead）、Backend（lead＝A，default＝Component lead）、Zeta（default＝Project default）。
    2. 建 issue 同時掛 Alpha＋Backend，Assignee 選 Automatic → 觀察是 B。
    3. 把 B 從 Assignable User 的 role 拿掉，再建一張同樣的 issue → 觀察變 A。
    4. 只掛 Zeta → 觀察是 project lead；把 Details 的 Default assignee 改 Unassigned 再試（若選不到，去 General configuration 開 Allow unassigned issues）。
    5. 建一條 project rule：Issue created → Assign issue → Round robin（三個帳號），建三張 issue 看輪流。
    6. 區分「名稱字母序」與「建立順序／ID」：先建 Zebra 再建 Alpha（讓建立先後與字母序相反），兩者都設 Component lead 並指向不同的合格帳號。建 issue 選 Automatic，記錄兩個 component 的名稱、ID、default 類型與當下 assignee；再把兩個 component 的名稱互換重測一次。官方 KB 支持「名稱字母序」；若有教材寫「最小 component ID」，用這個實驗判定，不要直接背。
    7. 每次結果都記錄「是初始指派還是後續覆寫」：對照 issue History 與 automation audit log 的時間戳。完成後還原設定並移除測試資料。
