620.2.5 · Determine the effects of estimation and time tracking on Scrum boards

Estimation 與 time tracking 對 Scrum board 的影響

Scrum board 的 Estimation 頁只有兩個旋鈕：用什麼估（estimation statistic）和用什麼追蹤進度（time tracking）。這兩個旋鈕決定 burndown 的縱軸、velocity 的單位、sub-task 算不算——考題就是問「轉了哪個旋鈕，報表會變成什麼樣」。

術語：考試用 project／issue／sub-task；現行產品為 space／work item／subtask。本教材沿用考試用語。

Bullet 1

在哪裡改、誰能改

Company-managed Scrum board
  1. Board 名稱旁 ••• → Board settings
  2. 左側選 Estimation
  3. Estimation method 下拉：Story points／Original time estimate／Issue count／自訂數字欄位
  4. Time tracking：None，或 Remaining estimate and time spent

誰能改：board admin，或 board 所在 project 的 project admin。官方註明「This setting can only be changed for company-managed scrum teams」——Kanban board 沒有這一頁。

Team-managed project
  1. Project settings → Features
  2. 打開 Estimation（預設關閉）
  3. 選 Story points 或 Time

開啟 estimation 會改變 TMP 的欄位與報表（官方提醒「causes several changes」）；TMP 沒有 issue count 與自訂欄位的選項，也沒有獨立的 time tracking 旋鈕。

沒選 statistic 會怎樣
官方：「If you don't select an estimation statistic, work will be measured by the work item count」——也就是退回 issue count；仍可記工時，但 velocity 沒有意義。
兩個容易被當成同一件事的欄位
  • statistic 是「每一張 board」的設定，不是 project 的。同一個 project 掛兩張 board，可以一張用 Story points、一張用 Issue count，兩張的 velocity 尺度就不同。
  • TMP 的欄位叫 Story point estimate，CMP 的叫 Story Points，不是同一個欄位。issue 從 TMP 搬到 CMP（或跨板做報表）之前要先確認值有沒有帶過去，別假設自動對應。
Bullet 2

Burndown 沒有 guideline？（官方 KB）

原因修法
Sprint 開始時 board 上沒有任何 issue，或 issue 都沒填估點先把有填估點的 issue 放進 sprint，再按 Start sprint，guideline 才有起始總量可以畫
Sprint 開始時間被設成過去、時區不一致用 Edit sprint 把開始與結束日期修正到合理範圍，並確認個人設定的時區與站台一致
Issue 在 sprint 開始後才加入（顯示為 scope change，不在 guideline 內）這是正常行為，不是設定錯誤。guideline 只反映 sprint 開始當下的承諾量，之後才加進來的工作會被畫成 scope change
完成的 issue 沒對到最右欄到 Board settings → Columns，把 Done、Closed、Cancelled 這些代表結束的 status 全部拖到最右欄，burndown 才會認定它們完成
用了自訂「Remaining Story Points」之類欄位不會被採用。burndown 只認得三種來源：Story Points、Original Estimate，以及 log work 產生的 Remaining Estimate；自己造的數字欄位它讀不到
最常考

Sub-task 規則：估點永遠不算，工時看旋鈕 2

圖 2　官方原句：Story Points on subtasks are not included in the Burndown Chart；Estimates from sub-tasks are not included in the Velocity Chart's calculation.
情境Time tracking = NoneTime tracking = Remaining estimate and time spent
Sub-task 的 story points不計入 burndown／velocity仍不計入（statistic 永遠只看 parent）
Sub-task 的 remaining estimate各自獨立計算，sub-task 的剩餘時間不會捲到 parent 身上捲上 parent，parent 顯示所有 sub-task 剩餘時間總和
Sprint 進行中新增 sub-task算 scope change，但圖上看不到算 scope change，圖上看得到（紅線往上跳）
Sprint 承諾量怎麼估官方建議用 velocity（statistic）決定，不要用 sub-task 捲上來的工時——velocity 已經把干擾與雜務算進去了
「有欄位」「可填值」「報表計入」是三件事
CMP 可以把 Story Points 的 field context 擴充到 sub-task，讓 sub-task 也填得了估點——但填得了不等於算得到：Burndown 與 Velocity 仍然只加總 parent。看到「sub-task 上有 story points」不能推論它進了報表；反過來，看不到某欄位時要查的是 context／screen／field configuration，不是 board 設定。
陷阱

中途改設定會怎樣

  • 改 estimation statistic：報表立刻改用新欄位；舊 sprint 若沒填新欄位，velocity 歷史會出現斷層。官方建議 statistic 選定後不要換。
  • Sprint 中改 issue 的估點：Sprint report 顯示 3 → 5，velocity 用新值；官方建議「保留原估點」——估得一致比估得準重要，改估會污染 velocity。
  • Estimation 欄位不在 screen 上：使用者填不了 story points → burndown 全是 0、沒有 guideline。這是 Jira admin 要處理的 screen 問題，不是 board 設定。
  • TMP 開啟 Estimation：會新增欄位並改變報表行為，官方要你先讀「changes that happen when enabling estimation」再開。
  • 未估算不會擋住 sprint 啟動：Jira 頂多提醒，不會禁止你 Start sprint。「規劃前要估完」是團隊紀律，不是產品的硬性門檻——考題把「警告」寫成「無法啟動」就是錯的。
  • Burndown 上的 estimation statistic 下拉是「檢視選擇」：在報表裡換一個單位看，只影響你眼前這張圖，不等於改了 Board settings → Estimation 的共用設定。
情境練習

先自己判斷，再點開解答

Board admin 想把 Kanban board 的估算單位改成小時，卻找不到 Estimation 頁。
解答
因為 Estimation 這一頁只有 company-managed 的 Scrum board 才有，官方原文寫得很明確：這個設定只能為 company-managed scrum teams 變更。道理不難理解——estimation statistic 存在的目的是餵養 burndown 與 velocity，而這兩張圖都以 sprint 為單位；Kanban 沒有 sprint，自然也沒有這一頁。Kanban 團隊想衡量效率，看的是 control chart 的 cycle time 而不是估點。
團隊用 story points，但工程師抱怨 log 了工時 burndown 都不動。
解答
因為第二個旋鈕 Time tracking 停在 None。這時候 burndown 的縱軸是 estimation statistic（也就是 story points），而 story points 是整張 issue 一次結算的：只有當 issue 被移進最右欄、視為完成時，曲線才會一口氣往下掉那幾點。無論中間 log 了多少工時，曲線都不會動。想看到「工時一小時一小時燒掉」的效果，要把 Time tracking 改成 Remaining estimate and time spent，縱軸才會換成剩餘時間。
Story 5 點、底下三個 sub-task 各 2 點，sprint 開始時 burndown 起點是多少？
解答
起點是 5，不是 11。sub-task 的 story points 永遠不計入 burndown 與 velocity，統計只認 standard 層（也就是 parent）的數字——官方在 velocity chart 的說明頁裡也直接寫了「Estimates from sub-tasks are not included」。所以 sub-task 上那三個 2 點雖然填得進去、畫面上看得到，統計上完全不存在。這也是為什麼實務上建議估點只估在 story 這一層，免得團隊誤以為有算到。
PM 在 sprint 中間把一張 Story 從 3 點改成 8 點，sprint report 會怎麼顯示？velocity 用哪個值？
解答
Sprint report 會把它顯示成 3 → 8，明白標示這張 issue 在 sprint 進行中被改過估點；velocity 的完成量則採用新值 8。官方的建議是盡量不要在 sprint 中途改估點：velocity 的價值來自「用同一把尺量很多個 sprint」，估得一致比估得準重要；中途改估雖然讓這個 sprint 的數字好看，卻污染了往後的預測基準。
Sprint 開始後才加的 sub-task，什麼情況下會在 burndown 上看到 scope change？
解答
只有在 Time tracking 開成 Remaining estimate and time spent 時，圖上才畫得出來。原因是 sub-task 的 story points 不計入統計，所以在 Time tracking = None 的情況下，新增一個 sub-task 對縱軸的數字毫無影響——它本質上仍然是 scope change，只是圖表沒有任何東西可以往上跳。一旦切換成工時模式，sub-task 的 remaining estimate 會捲上 parent，這時新增 sub-task 就會讓範圍線往上跳一階。
Burndown 完全沒有灰色 guideline。
解答
guideline 是那條「從 sprint 開始時的總量直直畫到 0」的參考線，它需要一個起始總量才畫得出來。最常見的原因就是這個總量是 0：sprint 開始的當下 board 上沒有任何 issue，或是 issue 全都沒有填估點。其次是時間問題——sprint 的開始日期被設成過去，或使用者的時區與站台不一致。另外還有兩個較少見但官方列出的原因：完成的 issue 沒有對應到最右欄，以及團隊自己造了一個「Remaining Story Points」之類的自訂欄位（burndown 只認 Story Points、Original Estimate 與 log work 產生的 Remaining Estimate）。修法是先把有估點的 issue 放進 sprint，再重新 Start。
團隊想用 issue 數量而不是點數來看 velocity，該改哪裡？
解答
到 Board settings → Estimation → Estimation method 選 Issue count。改完之後 velocity 與 burndown 的縱軸都會換成「張數」，也就是不管一張 issue 多大都算 1。這種做法適合工作顆粒度相當平均的團隊，省去估點的爭論；代價是失去對「大小」的敏感度，一張兩天的和一張兩小時的在圖上完全一樣。順帶一提，如果你根本沒選 statistic，官方的行為就是自動退回用 issue count 計算。
TMP 團隊說他們的 board 沒有 story points 欄位。
解答
因為 TMP 的 Estimation 功能預設是關閉的，欄位當然不會出現。到 Project settings → Features 把 Estimation 打開，再選 Story points 就有了。有兩件事要一併提醒團隊：第一，官方警告開啟 estimation 會連帶造成好幾項欄位與報表行為的變化，建議先看過說明再開；第二，TMP 的欄位名稱叫 Story point estimate，跟 CMP 的 Story Points 是兩個不同的欄位，日後要搬 issue 或跨 board 做報表時，別假設數值會自動對應過去。
Jira admin 換了 board 的 statistic 成一個新的自訂數字欄位，velocity 圖前幾個 sprint 變成 0。
解答
因為過去那些 sprint 的 issue 根本沒有填過這個新欄位，Jira 拿不到值，自然畫成 0。這正是更換 estimation statistic 的代價：報表是即時用「目前設定的欄位」重算歷史的，不是把當年的數字存起來。補救只有兩條路——回頭把舊 issue 的新欄位補齊（工作量通常很大），或是接受這段歷史斷層。官方的建議因此很直接：statistic 一旦選定就不要再換。
Burndown 到 sprint 結束還有一段沒燒完，但 issue 明明都關了。
解答
因為那些 issue 的 status 沒有對應到 board 的最右欄（很典型的是 Cancelled 被放在中間某一欄）。burndown 判斷「燒掉了沒」的依據不是 issue 看起來關了沒、也不是 status 的名字，而是它落在不落在最右欄。到 Board settings → Columns 把所有代表結束的 status（Done、Closed、Cancelled…）通通拖到最右欄，曲線就會正確地燒到底。
常見陷阱

考題喜歡設的誤解

誤解事實
「開了 time tracking，velocity 就用小時算」不會。velocity 永遠使用 estimation statistic（例如 story points），跟 time tracking 無關；第二個旋鈕只改變 burndown 追蹤進度的方式
「sub-task 的 story points 會加總到 parent」不會。統計永遠只看 parent 的估點；只有工時（remaining estimate）會在 time tracking 開啟時捲上 parent，估點不會
「Kanban board 也能設 estimation」不能。Estimation 這一頁只有 company-managed 的 Scrum board 才有，Kanban board 的設定裡根本沒有這個項目
「burndown 沒 guideline 是 bug」多半不是 bug。最常見的是 sprint 開始當下 board 上沒有 issue、或 issue 都沒估點，導致起始總量為 0；其次是 sprint 日期被設成過去或時區不一致
「換 statistic 不影響歷史」會影響。報表是即時用目前設定的欄位重算歷史的，舊 sprint 的 issue 沒填新欄位，那幾個 sprint 就會變成 0，出現明顯斷層
「沒選 statistic 就不能用 burndown」還是能用。官方明講沒有選 statistic 時，工作量會改以 issue count（張數）衡量；只是這時候的 velocity 參考價值不高
實作（30 分鐘）

親手轉兩個旋鈕

  1. CMP Scrum board：建 3 張 Story（5、3、2 點），其中一張加 2 個 sub-task 各填 3 點。開 sprint，看 burndown 起點是 10 不是 16。
  2. Board settings → Estimation 把 statistic 改成 Issue count，回 burndown 看縱軸變成 3。改回 Story points。
  3. Time tracking 改成 Remaining estimate and time spent；給 Story 填 Original estimate 6h、sub-task 各 2h；看 Story 的 time tracking 面板顯示加總，burndown 縱軸變小時。
  4. Sprint 中新增一個 sub-task 填 1h，看 burndown 出現 scope change；把 time tracking 改回 None，同樣操作圖上不顯示。
  5. 把一張 Story 從 3 改 8，開 Sprint report 看 3 → 8。
  6. 新開一個 sprint 但不放任何 issue 就 Start，看 burndown 沒 guideline；關掉重來。
  7. planning 與 execution 並存：對同一張 Story，story points 維持 5、Original estimate 10h、記 4h 工時、Remaining 填 8h。開 issue 確認三個數字同時存在（5 點沒有被換算成小時），並說明「最新預測 12h ＞ 原估 10h」是合理的——不要為了讓曲線好看把 Remaining 硬填成 6h。做完把 board 設定還原。
