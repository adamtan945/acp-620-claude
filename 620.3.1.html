620.3.1 · Determine appropriate permissions for project team members (project, global)

為專案成員決定適當的權限

這一節是 620.3 的第一站，也是整份考試「為什麼他做不了 X」類題目的來源。視角是 project admin：你不能改 permission scheme，但你要能判斷某個功能需要哪幾個權限、哪些是 Jira admin 才動得了的全域設定，以及該把人放進哪個 role。

術語：考試用 project／issue；現行官方文件為 space／work item。本教材沿用考試用語，引用現行文件時保留其用語。

核心模型

四層權限，各有各的主人

官方把權限分成全站與 project 兩層，加上 workflow condition 與 issue security 兩個「再收緊」的機制。一個人能不能做某件事，要四層都放行；而每一層由誰設定並不相同——這正是 project admin 最常卡住的地方。

圖 1　由上往下每一層都要放行。Project admin 真正能動的只有第 ② 層的「role 成員」和第 ④ 層的「在 issue 上選 level」。
考題長相
「某人在 project 有 Browse 與 Edit，但仍看不到 MOB-88」→ 第 ④ 層 issue security。「某人有 Transition Issues，但某個轉換按鈕不出現」→ 第 ③ 層 workflow condition。先判斷是哪一層，再判斷該找誰。
Bullet 1

全域權限怎麼影響 project 裡的功能

全域權限只有 8 個，而且只能授予群組（不能給個人、不能給 project role）。Project admin 沒有任何一個全域權限的設定權，但其中 5 個會直接影響 project 成員的日常操作。

全域權限缺了會發生什麼（project 內的症狀）誰能給
Browse users and groups@提及、User picker 只看得到「同一個 project 有 Browse Projects 的人」，找不到別的部門同事。官方特別說這是限制資訊外流的常用手法，不一定是錯Jira admin（給群組）
Share dashboards and filters建得了 filter 與 dashboard，但分享選單是空的 → 跨 project board 沒人看得到、dashboard 只能自己看Jira admin
Make bulk changes搜尋結果頁沒有 Bulk change 選項。有了它還要配合 project 權限（Edit／Move／Delete／Transition）Jira admin
Create team-managed projects看不到 Create project；只影響 TMP，CMP 永遠要 Administer JiraJira admin
Administer Jira建 CMP、custom field、workflow、各種 scheme、全站的 issue linking 與 time tracking 開關。Project admin 需要這些時只能開單Org／Site admin 把人加進 jira-administrators
Manage group filter subscriptions不能建群組訂閱Jira admin
Manage custom onboarding與 project 無關Jira admin
Atlassian Home 連線連結 work item 到 Projects；安裝 Connect addon 後出現Jira admin
兩個「全域開關」不是全域權限，但一樣是 Jira admin 的事
Issue linking（⚙ → Issues → Issue linking）與 Time tracking（⚙ → Issues → Time tracking）關掉時，project 裡就算有 Link Issues／Work On Issues 權限也做不了。考題把它們歸在「project 權限與全域設定的關係」。

兩個容易反直覺的組合
  • Create Issues 不要求先有 Browse Projects。因此「建得出來，卻打不開自己剛建的那張」是權限設計的正常結果，不是壞掉。Reporter 身分也不會自動帶來 Browse，除非 scheme 另外把可見性授予 Reporter。新增成功不能拿來證明閱讀或編輯權限完整。

考題長相
「使用者有 Manage Sprints 卻無法把 issue 拖進 sprint」→ 缺 Schedule Issues（或 Edit Issues）。「有 Move Issues 但目的 project 找不到」→ 目的地沒有 Create Issues。「有 Link Issues 但 Link 選單不見了」→ 全域 issue linking 關閉，或對方 project 沒給 Link Issues。

批次編輯：權限齊全，還有欄位條件

Make bulk changes 是全站入口，Edit Issues 必須涵蓋每一張選取的 issue——但即使兩者都有，欄位本身還有條件。官方現行頁只寫「可用的批次編輯操作取決於所選的工作與欄位性質」，實務上這三個欄位最常卡住：

要批次改的欄位還要滿足什麼
Components這批 issue 屬於同一個 project、該 project 已經有 components、欄位未被 field configuration 隱藏
Fix versions／Affects versions同上的單一 project 條件。即使兩個 project 都有「秋季版」，那仍是兩個不同的 version 物件，只能分批處理
Sprint可以批次指定實際的 sprint ID
Due date另需 Schedule Issues；只有 Edit Issues 不夠

issue 已經 resolved 不會把「修改 Components」變成 Resolve Issues 的操作；仍要看它目前是否可編輯。上限 1,000 張。（欄位層條件為實務歸納，官方現行頁未逐項列出）

考題長相
「最少需要哪些權限？」的題目要先列能力再找角色聯集，不要背數量。例如「指派來源 project 的工作，再批次搬到另一個 project」＝來源 Browse ＋ Assign ＋ Move、目標 Create、全域 Make bulk changes；目標 Browse 決定搬完後讀不讀得到，和 Create 是兩回事。舊題庫常把 Edit Issues 一律算進「指派」的必要權限——依官方重疊規則，只有 Assign、沒有 Edit 的人也能改 Assignee。
規則

兩個權限重疊時，最具體的那個決定

When two permissions overlap, the most specific applicable permission determines who can perform an action.— Atlassian, How permissions interact with each other

圖 2　Scheme 裡沒定義 Assign Issues 時，有 Edit Issues 的人也能改 Assignee；一旦定義了，Assignee 就只聽 Assign Issues 的。
情況誰能改 Assignee
Scheme 只設定 Edit Issues所有有 Edit Issues 的人
Scheme 另外設定了 Assign Issues只有有 Assign Issues 的人；只有 Edit 的人可以改其他欄位
只有 Assign Issues、沒有 Edit Issues能改 Assignee，其他欄位都不能
Workflow 加了 jira.issue.editable=false 或 jira.permission.* 屬性依狀態再收緊，同樣「具體優先」
同一個 project，也可能只有部分 issue 能轉移

Permission scheme 除了 group／role，也能授權 Current assignee、Reporter、User custom field value 這種「由每張 issue 決定」的對象。例如 Transition Issues 只授予 Current assignee：小美是 ACLAB-1 的 assignee、卻不是 ACLAB-2 的，兩張同屬 ACLAB、共用同一份 scheme，她的轉移資格仍然不同。

所以排查時要逐張看，不能用「這個 project 有一張成功」推論全部都會成功，也不要把同 project 的部分失敗當成資料損壞。還要各自檢查 workflow condition、validator、目前狀態與 issue security。

Bullet 5

Administer Projects 的邊界

官方把它定義為「指派 role 成員、編輯 components／versions、修改 project details」。以下是考試最愛問的「能／不能」對照：

能做
  • Project settings → People：把 user／group 放進任何 role（含 Administrators）
  • Versions：建立、release、archive、merge、delete（官方頁另需 Manage Versions）
  • Components：建立、設 lead 與 default assignee、刪除時重新連結
  • Project details：名稱、key、avatar、category（選）、lead、default assignee
  • Issue layout：前提是 screen 沒被其他 project 共用
  • Workflow：前提是 workflow 為本 project 專用且用新編輯器（Edit Workflows 權限）
  • 看到 Project settings 側欄的各 scheme 名稱、換不了
不能做（要 Jira admin）
  • 改 permission scheme 的任何一條規則、換 scheme
  • 建立新的 project role（⚙ → System → Project roles）
  • 建 custom field、issue type、screen、field configuration
  • 改被共用的 workflow 或 layout（需 Administer Jira）
  • 建 issue security scheme、掛 security scheme
  • 任何全域權限、issue linking／time tracking 開關
  • 把 CMP 丟進 trash（Jira／site admin）
TMP 對照
TMP 沒有 permission scheme：project admin（Administrator role）可自建 role、勾權限、改 access level，這些在 CMP 全是 Jira admin 的事。詳見 620.1.2。
Bullet 4

權限與 role 的關係：scheme 寫角色名，project 填人

Permission scheme 可以把權限給 11 種對象；其中 project role 是一個「佔位符」——Jira admin 在 scheme 裡寫角色名，各 project 的 admin 自己決定誰是那個角色。這讓一份 scheme 掛 20 個 project 仍能各自不同，而且不必驚動 Jira admin。

授權對象什麼時候用誰維護成員
Project role各 project 人不同、想把權限管理下放Project admin（People 頁）
Group跨 project 同一批人（如 jira-administrators、全公司開發群組）Org／Site admin
Single user極特殊情況；官方不建議因為 scheme 共用時會一起生效Jira admin 改 scheme
Reporter／Current assignee／Project lead「只有開單的人能刪」「只有被指派者能轉狀態」這類動態授權不用維護，隨 issue 資料變
User／Group custom field value每張 issue 各自指定的人（如 Approver 欄位）填欄位的人
Application access／Any logged in user／Public廣泛授權；Public 用於公開 project—

Role 除了在 permission scheme 用，官方還列了四個用途：notification scheme 的收件人、issue security level 的成員、workflow condition、filter 與 dashboard 的分享對象。怎麼把人放進 role、role 的預設成員與 atlassian-addons-project-access，在下一節 620.3.2。

情境練習

先判斷「哪一層、缺哪把鑰匙、該找誰」

小傑能看 issue、能留言，但拖曳 backlog 排序時卡片彈回去。他有 Edit Issues。
解答
缺 Schedule Issues（rank 與 due date 被它接管）。請 project admin 把小傑放進有 Schedule Issues 的 role；若 scheme 沒把該權限給任何 role，要 Jira admin 改 scheme。
Scrum master 有 Manage Sprints，能開始 sprint，卻不能把 issue 從 backlog 拖進 sprint。
解答
Manage Sprints 只管 sprint 本身；拖 issue 進 sprint 需要 Schedule Issues（與 Edit Issues）。組合題的標準答案。
使用者有 Move Issues，把 issue 從 MOB 搬到 WEB 時目的地清單沒有 WEB。
解答
他在 WEB 沒有 Create Issues（也需要 Browse）。跨 project 動作要兩邊都有權限。
team 想用 Link Issues 把 MOB 與 WEB 的 issue 連起來，Link 選項根本不出現。
解答
先查全域 Issue linking 是否啟用（Jira admin）；再查兩個 project 是否都有 Link Issues。
阿宏建了跨 project board，同事說「看不到這個 board」。
解答
阿宏缺全域 Share dashboards and filters，board 的 saved filter 分享不出去；或同事在其中一個 project 沒有 Browse Projects。
PM 想一次把 80 張 issue 改優先度，搜尋結果頁沒有 Bulk change。
解答
缺全域 Make bulk changes；有了之後還要 project 的 Edit Issues。
Project admin 小美想讓 Reviewer role 多一個 Edit Issues，在 Project settings 找不到地方改。
解答
CMP 的權限規則在 permission scheme，只有 Jira admin 能改；小美只能填 role 成員。若 scheme 被多個 project 共用，改動會影響所有 project。
Scheme 只設定了 Edit Issues。後來 Jira admin 把 Assign Issues 給了 Administrators role。工程師抱怨突然不能改 Assignee。
解答
「最具體者勝」：一旦定義 Assign Issues，只有拿到它的人能改 Assignee；工程師仍能改其他欄位。
Kevin（外包）能被指派 issue，但他自己改不了 Assignee；小美想確認這是不是設定錯誤。
解答
不是錯誤：Assignable User（可被指派）與 Assign Issues（可改欄位）是兩個獨立權限，Kevin 只有前者。
小美有 Edit Workflows，卻改不了本 project 的 workflow。
解答
該 workflow 被其他 project 共用；共用的 workflow 需要 Administer Jira。請 Jira admin 複製一份專用 workflow 與 workflow scheme。
使用者有 Work On Issues，issue 上卻沒有 Log work。
解答
全域 time tracking 未啟用，或 time tracking 欄位不在 screen 上——兩者都是 Jira admin。
@提及時只找得到本 project 的人，找不到法務同事。
解答
缺全域 Browse users and groups；沒有它只看得到「同 project 有 Browse 的人」。官方說這可能是刻意限制。
常見陷阱

考題喜歡設的誤解

誤解事實
「全域權限可以給 project role」只能給群組
「有 Edit Issues 就什麼欄位都能改」Assignee、Reporter、Due date／rank 一旦在 scheme 定義了專屬權限，就只聽專屬權限
「Manage Sprints 可以拖 issue 進 sprint」只管 sprint；拖 issue 要 Schedule Issues
「Move Issues 就能搬到任何 project」目的地要有 Create Issues
「Project admin 可以調 permission scheme」只能填 role 成員；scheme 是 Jira admin
「Browse Projects 不重要」幾乎所有 issue 權限的前提；排查永遠先看它
「Link Issues 給了就能連」還要全域 issue linking 開啟，跨 project 兩邊都要
「看不到某張 issue 一定是 Browse 問題」也可能是 issue security level，或 issue 被 archive
「能建 issue 就一定看得到它」Create Issues 不要求 Browse Projects；可能建完就打不開
「同一個 project 的權限對每張 issue 都一樣」Current assignee／Reporter／User custom field value 讓資格逐張不同
「有 Make bulk changes 就能批次改任何欄位」Components／versions 還有單一 project 等欄位條件；Due date 另需 Schedule Issues
實作（45 分鐘）

親手踩一次每個組合

  1. 在 CMP 建 role「QA」，請 Jira admin（或自己）在 scheme 把 Schedule Issues 從 Any logged in user 改成只給 Administrators。用非 admin 帳號拖 backlog → 彈回。把該帳號放進 Administrators → 可拖。
  2. 把 Assign Issues 加進 scheme 只給 QA；用只有 Edit Issues 的帳號改 Assignee → 欄位唯讀；改 Summary → 可以。
  3. Jira admin 把 ⚙ → Issues → Issue linking 停用；確認有 Link Issues 的人 Link 選單消失；再啟用。
  4. 建第二個 project WEB 但不給測試帳號 Create Issues；用該帳號 Move MOB 的 issue → 目的地清單沒有 WEB。
  5. 拿掉測試帳號群組的全域 Share dashboards and filters → 建 filter 時分享選項消失。
  6. 用 Manage Sprints 的帳號開始 sprint，再試拖 issue 進 sprint → 失敗；補 Schedule Issues → 成功。
  7. 用一般帳號逐步驗證（A 版 lab）：請 Jira admin 複製一份測試用 permission scheme、只套用到 ACLAB（記錄原 scheme，避免動到其他 project）。先只給測試角色 Browse Projects ＋ Add Comments，建一張 Task。
  8. Project settings → People／Access 把測試帳號加進該角色，用另一個瀏覽器工作階段登入測試帳號：預期能開、能留言、不能改 Summary。
  9. 加上 Edit Issues 後重整、改 Summary → 應該成功；接著看 Due date：若 scheme 把 Schedule Issues 只給管理者，不能因為 Edit 成功就推論排程也可用。
  10. 指派測試前分別確認「操作者有 Assign Issues」與「目標有 Assignable User」。記錄成「操作／授權路徑／結果」三欄，不要只截管理者看到的設定頁。
  11. 收尾：移除測試成員、還原 scheme；若帳號仍看得到 project，列出其他 group／role／直接授權的路徑。Free 方案不提供 permission scheme 編輯，改用閱讀與預測表完成演練。
