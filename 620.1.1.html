620.1.1 · Recommend a project implementation

選擇 project 的實作方式：
company-managed、team-managed、template、shared configuration

官方只給一個連結，但那頁是一個 hub，底下還有四個子頁。這一節把五頁的內容整理成一個模型：兩種 project 的差別不在功能，而在「設定屬於誰」。看懂這件事，其餘差異都推得出來。

術語：考試（2023 V2）使用 project／issue；現行 Jira Cloud 已改稱 space／work item。本教材沿用考試用語。
這一節考什麼

兩條 bullet，翻成考題語言

官方 bullet考題會怎麼問
Understand use cases for each project type「某團隊有 X 需求，該建哪種 project？」——情境選型題
Know feature differences between company-managed and team-managed projects「team-managed 有沒有 components？」「誰能改 CMP 的 workflow？」——功能有無／誰負責

標題裡另外兩個關鍵字也會考：project templates（建 project 時選的模板）與 shared configuration（建 CMP 時「跟既有 project 共用設定」）。

核心概念

差別不在功能，在「設定屬於誰」

The core functionality of these are the same, but there are key differences you should know in order to decide what's right for your team.— Atlassian, What are team-managed and company-managed spaces?

兩種 project 都能建 issue、跑 board、做報表。真正的分水嶺是設定物件放在哪裡、誰有權改。按下面的按鈕看「改一個設定」在兩邊分別發生什麼事。

左邊改一次全部生效；右邊只影響自己。
圖 1　記憶口訣：CMP ＝「scheme 掛在 project 上」；TMP ＝「設定長在 project 裡」。
從這個結構可以推導出幾乎所有考點
  • CMP 能標準化、TMP 不能 → 因為 TMP 沒有可共用的 scheme。
  • CMP 要 Jira admin、TMP 不用 → 因為 scheme 是全站物件，只有 Jira admin 能碰。
  • CMP 改設定會影響別的 project、TMP 不會 → 因為共用。
  • TMP 的 custom field 不能跨 project 用 → 因為它「長在 project 裡」。
官方選型準則

先背原文的意思，再看流程圖

選 Team-managed 當
  1. 團隊想要簡單設定、快速開始（easier configuration to get started quickly）
  2. 想要一個自給自足的空間管自己的工作（self-contained space）

官方定位詞：autonomous teams（自主團隊）

選 Company-managed 當
  1. 想在組織內多個 project 之間標準化設定（standardize configuration across multiple projects）
  2. 需要複雜的權限與 workflow 客製（complex customization for permissions and workflows）

官方定位詞：work with other teams across many projects in a standard way

關鍵字 → 答案
看到「autonomy」「self-contained」「quick start」「no admin available」→ TMP；看到「standardize」「across teams」「shared workflow」「compliance」「complex permissions」→ CMP。
圖 2　選型決策流程。第三個問題是「TMP 做不到的四件事」，任何一項成立就回到 CMP。
功能差異全表

考「有沒有」「誰負責」

Work types differ（子頁）

TMP：work type 是容器，custom field 綁在 project 裡不能共用。CMP：work type 是標籤，欄位透過 screen scheme 跨 project 共用。

Settings differ（子頁）

最大差別是誰管設定。TMP 每個人都必須有一個 role，權限綁 role；CMP 透過 permission scheme 給 user／group／role。

Features differ（子頁）

TMP 隨時開關 features；CMP 被 template 鎖定。CMP 想從 Kanban 改跑 Scrum，是在同一 project 再建一個 Scrum board。

深入：權限與存取

同一個需求，兩邊怎麼做

貫穿的例子：Acme 公司的「Mobile App」專案，成員有 PM 小美、工程師阿宏、QA 小傑、外包設計師 Kevin，HR 偶爾會開幾張敏感的 issue。

1. 模型：權限「長什麼樣子」

CMP：permission scheme ＝「權限 × 對象」對照表
權限（39 項之一）授權對象（11 種之一，可多個）
Browse Projectsrole Developers、role Viewers
Assign Issuesrole Administrators
Resolve Issuesrole Developers、User custom field: QA Owner
Delete IssuesReporter
Transition IssuesCurrent assignee

11 種對象讓你做到「只有開單的人能刪自己的單」「每張 issue 各自填的 QA 才能 resolve」這種動態授權。

TMP：access level ＋ role，每個 role 是一組勾選框
PeopleRole
小美Administrator
阿宏、小傑Member
KevinReviewer（自訂：只勾 View、Comment）

權限「勾在 role 上」，沒有「給 Reporter」「給某欄位的人」這種動態對象。CMP 是關聯表，TMP 是人 → role → 固定勾選。

2. 誰授權：「讓 Kevin 只能留言」

CMP 的分工
  1. Jira admin：建 role「Reviewer」；在 scheme 裡把 Browse Projects、Add Comments 加給 Reviewer
  2. Project admin 小美：Project settings → People → Kevin → Reviewer

小美改不了第 1 步。想讓 Reviewer 多一個 Edit Issues，得請 Jira admin 改 scheme——而且會影響所有掛同一份 scheme 的 project。

TMP 的分工
  1. 小美自己：Access → Manage roles → Create role「Reviewer」，勾 View、Comment
  2. Access → Add people → Kevin → Reviewer
  3. 之後想加 Edit？自己回去勾，只影響這個 project
考題長相
「Project admin 想讓某個 role 多一個權限，卻改不了」→ 這是 CMP，權限在 scheme 上，要找 Jira admin。反過來「哪種 project 讓 project admin 不需 Jira admin 就能自訂角色權限？」→ TMP。

3. 匿名／公開、issue security、留言限制

需求（Acme 例）Company-managedTeam-managed
不登入的訪客也能看「公開 roadmap」project可：Browse Projects → Public（不是 Any logged in user）；站台層要允許匿名不可：Open／Limited／Private 都是「站台使用者」的範圍；Open ≠ 公開給網際網路
HR 開的 MOB-88 只有 HR 與該員主管能看，其他人連搜尋都不出現Issue security scheme：level「HR only」= role HR + Reporter + Current assignee；阿宏有 Browse 仍看不到 MOB-88；sub-task 自動繼承無此功能。替代：對 issue type「HR Case」鎖 role（只影響之後新建）、或整個 project 設 Private（得把 HR 案件搬去獨立 project）
阿宏在 MOB-45 留一則「這是 Kevin 改壞的」給內部看留言鎖頭 → Restrict to role Developers；Kevin 看不到那一則。前提：⚙ General configuration 的 Comment visibility 設「Groups & Project Roles」留言框沒有鎖頭（官方 KB：只能靠 REST API 硬塞）
一句話判斷
TMP 適合「一組人、幾種角色、全部互相看得到」；一旦出現「同一個 project 內要對不同人藏不同東西」，就是 CMP 的領域。
Team-managed 的三個存取等級

Open／Limited／Private 決定「沒被加入的人」的預設待遇

Acme 站台有 200 個 Jira 使用者。Mobile App 只明確加了小美、阿宏、小傑、Kevin。其他 196 人（例如剛入職、沒被加進 project 的阿強）會遇到什麼，就由 access level 決定。

Open

全站使用者自動拿到 Member

  • 阿強能看、建、編、拖 board、轉狀態
  • 官方用途：打破部門穀倉
  • 風險：任何人都能改你的 issue
Limited

全站使用者自動拿到 Viewer

  • 阿強能看、留言、加附件
  • 不能建 issue、不能編輯、不能轉狀態
  • 典型：透明給全公司，只有團隊能動
Private

只有被點名的人與 Jira admin

  • 阿強完全看不到：目錄沒有、JQL 搜不到、直連被拒
  • Jira admin 永遠能進 project settings
  • 典型：HR、法務、資安事件

規則 1：指派的 role 是「疊加」，不是「覆蓋」

Assigned roles add to (rather than override) access granted by the space's access level.— Atlassian, Manage how people access your team-managed space

自己動手試：切換 access level、勾選要指派給某人的 role，看最終權限怎麼加總。

Access level
明確指派的 role
Access level 給的預設 role（地板）
∪
被指派的 role（往上疊）
=
最終權限（0 項）

試試看：Open ＋ 只勾 Reviewer——結果仍是 Member 的全部權限。想限制人，先降 access level，再用 role 往上加。

規則 2：Access level 跟「匿名」無關

三個等級的範圍都是「Jira site 上有帳號的人」。Open ≠ 公開給網際網路。TMP 不支援匿名，這是 CMP 才有的（Browse Projects → Public）。

操作位置

  • Project settings → Access → Change project access → 選一個 → 確認。需要 Administrator role（Jira admin 也可）。
  • Free 方案：不能改 permissions／roles，但 access level 仍可切換。
Project templates

三個選擇的順序：type → template → 管理方式

  • Create project
    • Software
      • Scrum sprint、backlog、估點、velocity
      • Kanban 連續流、WIP、無 sprint
      • Bug tracking 簡化，以 list 視圖為主
    • Business Work management：Project management、Task tracking…
    • Service management JSM，queues 取代 board
    • Product discovery JPD
  • 選完 template 才問：Team-managed？Company-managed？

620 只考 Software 的 Scrum／Kanban（Bug tracking 偶爾出現）。Template 決定：預設 issue types、預設 workflow、board 類型、哪些 features 開著。

  • CMP：建完後 Jira admin 可換 scheme，但 features 被 template 鎖定；想換打法要再建一個 board（CMP 允許多 board）。
  • TMP：建完後 project admin 可在 features 開關 Sprints／Backlog，等於 Scrum ↔ Kanban 可以事後切換。
Shared configuration

只在 company-managed 建立流程出現

圖 3　Create project → Company-managed → Advanced → ☑ Share settings with an existing project → 選 Project X。新 project 直接掛上 X 目前的全部 scheme。
優點限制／代價
新 project 零設定，立即與 X 一致之後任何一方想改 workflow 都會影響另一方
Jira admin 改一次，全部生效（治理）想「只改我的」→ 得先 copy scheme 再指派，是 Jira admin 的工作
減少 scheme 數量，站台乾淨X 的設定本來就不理想的話，新 project 也繼承問題

三個很像、承諾卻不同的做法

做法建立當下之後改設定
兩個 project 用同一個 template預設 issue types／workflow／features 相同各走各的；改一邊不會影響另一邊
Jira admin 複製 scheme 再指派起點與來源一模一樣是兩份不同的 scheme，各自獨立
Share settings with an existing project直接掛上對方現有的那一份 scheme同一個物件；任一方改，兩邊同時變
證據界線：官方明列共用哪六項

Create a new space 列出 shared configuration 共用的是 work types（issue types）、workflows、screens、fields、permissions、notifications，並註明改其中一個 project 的設定會影響所有共用的 project。

  • 只有 Jira admin 能建立共用設定的 project，且Free 方案沒有這個選項。
  • 官方清單裡沒有 components、versions、board 設定與 issue 資料——這些屬於各 project 自己，不會因為共用設定而共用。
  • 共用的是設定不是成員：permission scheme 用 role 授權，而 role 的成員各 project 各自指定，所以「共用 scheme」不等於「同一群人有權限」。

來源：Create a new space

考題型態
「A 部門要開三個新 project，都要跟 DEV 一樣的流程與權限，最省事？」→ 建 CMP 並 share settings with DEV。追問「其中一個之後要加 QA 狀態但不影響其他人」→ 請 Jira admin 複製 workflow 與 workflow scheme 給該 project 單獨用。
遷移（Migrate）

沒有一鍵轉換：建新 project → bulk move issues

Issue key 會換成新 project 的 key（舊連結自動轉址）。考的是「會掉什麼」。

方向保留遺失
CMP → TMPissue、留言、附件、歷史；全域 custom field 值（暫時空白，搬回去可恢復）Sprint、Components（不可恢復）、Versions（不可恢復）、story points、報表歷史與 velocity（parallel sprints 兩種 project 現行都支援，遷移不因此受限）
TMP → CMPissue、keycustom field 要重建、status 要 Jira admin 重做 workflow、issue types 要重建、story points、報表歷史、權限要重設 scheme
一句話
兩個方向都掉 story points 與報表歷史；CMP → TMP 還會掉 sprint、components、versions。官方建議先在 sandbox 試。
情境練習

先自己判斷，再點開解答

新成立的 5 人團隊想這週就開始用 Jira，公司唯一的 Jira admin 出差兩週。
解答
TMP：不需 Jira admin、快速開始。
法遵部門要求所有軟體團隊的 bug 都走同一套 workflow，審計時要能證明流程一致。
解答
CMP + 共用 workflow scheme：只有 CMP 能跨 project 標準化。
團隊需要把 issue 依「前端／後端／資料庫」分組，並讓各模組負責人自動被指派。
解答
CMP：components 只有 CMP 有，且 component default assignee 可自動指派。
團隊要對外部承包商開放看板，但其中幾張 HR 相關 issue 只能內部看。
解答
CMP：需要 issue security scheme；TMP 只能整個 project Private 或限制 issue type，達不到「同一 project 內幾張隱藏」。
三個團隊共用一個 backlog，各自有自己的 board 看不同切面。
解答
CMP：TMP 一個 project 只能一個 board。
團隊想試驗新的工作流程，改來改去，且不想影響任何人。
解答
TMP：self-contained，改設定不影響他人。
已有 DEV project，現在要為新產品線開 project，流程與權限完全照 DEV。
解答
CMP，Share settings with existing project（DEV）。
一個 TMP 團隊用了半年，公司要把它納入標準流程，遷移時 PM 最擔心哪些資料？
解答
Story points 與報表／velocity 歷史會掉；custom field、issue types、workflow 要重建；權限要重設。遷移前先把 sprint 結束。
Open 的 project，小美建了「唯讀」role 給實習生，實習生還是能編輯，為什麼？
解答
Open 讓全站都是 Member，指派的 role 是疊加；要先切成 Limited，再給實習生「唯讀」role（Viewer 就夠）。
Private 的 project，外部客戶要看，怎麼辦？
解答
客戶得先有站台帳號（請 admin 邀請為 guest），再被明確加入；TMP 不支援匿名，Private 也不例外。
常見陷阱

考題喜歡設的誤解

誤解事實
「TMP 功能比較少所以比較差」官方說 core functionality 相同；差在管理模型
「TMP 給小團隊、CMP 給大團隊」官方準則是自主 vs 標準化，不是人數
「Project admin 可以把 TMP 轉成 CMP」沒有轉換按鈕；是建新 project + bulk move，且需 Jira admin 建 CMP
「CMP 的 project admin 什麼都不能改」能改 details、role 成員、versions、components、layout（screen 未共用時）、專用 workflow（新編輯器）
「TMP 可以設公開讓匿名看」不行，TMP 不支援匿名
「TMP 的 custom field 別的 project 也能用」不行，只屬於該 project
「Shared configuration 之後可以各自獨立改」改的是同一份 scheme，會互相影響
「CMP 建完可以把 Kanban 改成 Scrum」Features 被 template 鎖定；要再建一個 Scrum board
「用同一個 template 建的兩個 project 會一起更新」template 只決定建立當下的起點；之後各自獨立
「兩個 TMP 有同名欄位＝同一個欄位」名稱一樣也是兩個不同物件；值不互通、報表不會合併
「一個 board 同時看兩個 project＝它們共用設定」board 只是 filter 的呈現，跟 scheme 無關；跨 project board ≠ shared configuration
「Scrum master 或 project lead 自動是 board admin／Jira admin」三者互相獨立：board admin 在 board settings 指定，Jira admin 是全域權限，project lead 只是 details 上的欄位
實作（20 分鐘）

建立肌肉記憶：「設定屬於誰」

  1. 建一個 TMP Scrum：流程中沒有問你 scheme；建完到 Project settings 看側欄——Issue types、Fields、Workflow 都在，可直接改。
  2. 建一個 CMP Scrum（需 Jira admin）：建立時展開 Advanced 看 Share settings with an existing project；建完看側欄——每項都寫「Scheme」，點進去多半是「Actions → Use a different scheme」而非直接編輯。
  3. 兩邊各嘗試：加 issue type、加 custom field、加 workflow status。記下哪邊能直接做、哪邊要 Jira admin。
  4. 在 TMP 找 Components——確認沒有。在 TMP 的 Access 頁找「Public／anonymous」——確認沒有。
  5. 在 CMP 建第二個 board；在 TMP 試著建第二個 board——確認只能透過 saved filter。
  6. TMP 的 Access 切 Open → Limited → Private，用第二個帳號各看一次；在 Open 下給第二帳號一個「唯讀」自訂 role，驗證疊加規則。
  7. 共用設定實驗（需 Jira admin）：建 CMP-A；再建 CMP-B 時展開 Advanced，勾 Share settings with an existing project 選 CMP-A。到 CMP-B 的 workflow 加一個 Review status。
    預期：CMP-A 的 workflow 也多了 Review（同一份 scheme）；但 CMP-A 的 issue 清單完全不變——共用的是設定，不是資料。
  8. 對照組：用同一個 template 再建 CMP-C（不勾 share settings），一樣加 Review status。
    預期：只有 CMP-C 變，A／B 不受影響——證明「同一個 template」≠「共用設定」。順手在 CMP-B 的 Project settings 找 Components 與 Versions，確認它們沒被共用。
