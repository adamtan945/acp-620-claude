3 分鐘速覽

Rule＝trigger → condition → action（＋branch）

  1. Trigger 只能一個Issue created、transitioned、field value changed、scheduled、manual…
  2. Condition 不符＝No actions performed不是錯誤。
  3. Branch 對相關 issue 各跑一次Branch 裡的 {{issue}} 是相關 issue；觸發的那張用 {{triggerIssue}}。
  4. Scope 只有四種你常錯Single project、Multiple projects、Project type、Global。Issue type 不是 scope（要用 condition）。
  5. Actor 決定權限預設 Automation for Jira；project admin 只能設成自己或 Automation for Jira。
  6. {{issue}} 是觸發當下的快照Edit 之後要讀新值，先 Re-fetch issue data。
資料來源（5）有疑慮時點開看官方原文
  • What are flow details and settings?Space type: Flow will run across all spaces of a specific type (either software, service, or business).
  • What is a flow actor?In Jira automation, the default flow actor is the “user” called Automation for Jira.
  • Run Jira flows as another userProject admins can only choose themselves or the Automation for Jira user as the flow actor.
  • Automation smart values - issuesRefers to the original issue that triggered the flow; used when you branch the chain.
  • Jira automation actionsBy default, the {{issue}} reference is not updated during flow execution, and contains the same values as when the flow originally triggered.

Rule details

Scope、actor、owner

Scope範圍誰能建
Single project一個 projectProject admin
Multiple projects自選幾個Jira admin
Project type某類型的全部 projectJira admin
Global全部 projectJira admin
身分是誰用途
Owner建立 rule 的人負責維護、出錯時收通知；不決定權限
Actor預設 Automation for Jira（系統帳號）rule 的每個動作都用它的身分與權限執行
你問過的：rule 是 Daniel 建的，為什麼看的是 actor 的權限？

Owner 是「誰建的、誰負責」，actor 是「誰去做」。權限問題一律看 actor，不看建立者或觸發者。

  • Rule 會一直自動跑，建立者離職照樣跑，所以不能用建立者的權限。
  • Actor 預設是 Automation for Jira；它的權限來自 permission scheme（通常透過 atlassian-addons-project-access），scheme 由 Jira admin 改。
  • Project admin 只能管 role 的成員，不能改 role 有哪些權限；actor 只能設成自己或 Automation for Jira，設成任何其他人要 Jira admin。
你問過的：兩個 project 的 admin，為什麼不能建跨 project 的 rule？

跨 project 的 rule＝Multiple projects scope＝Jira admin。「supposing she has all the necessary project permissions」是陷阱：她缺的是全域的 Jira admin，不是 project 權限。

  • Actor 權限很大又會一直自動跑，所以 Jira 用 scope 當圍籬：rule 只能動 scope 內的 project。
  • RUN＋DEV 這個組合不屬於任何一個 project，是站台層的東西（放在 ⚙ → System → Global automation），站台層歸 Jira admin。
  • 其他跨 project 的事不一定要 Jira admin：跨 project board、JQL、搬移 issue、連結 issue、跨 project sprint，看的都是每個 project 各自的權限。
你練習時錯過

Automation 的 scope 只有 Single project、Multiple projects、Project type、Global（現行文件另有 team 相關 scope，不在考試範圍）。「Multiple issue types」不是 scope，要用 condition 限定。

類型常考

Smart values

雙大括號裡的動態值

值意思
{{issue}}目前這一輪的 issue（branch 裡是相關 issue）
{{triggerIssue}}觸發 rule 的那張
{{createdIssue}}這次 rule 最近建立的一張
{{now.plusDays(5)}}五天後
{{issue.assignee.displayName|"未指派"}}有預設值
{{#issue.comments}}…{{/}}逐項處理 list
你練習時錯過：parent 的 Due date＝sub-task 最晚的那天

子改了、要更新父 → Branch For Parent；父改了、要更新子 → Branch For Sub-tasks。

  1. Trigger：Value changes for Due date（trigger issue＝sub-task）
  2. Condition：Parent exists
  3. Branch：For Parent（之後的 {{issue}} 變成 parent）
  4. Condition：parent 的 Due date 早於 {{triggerIssue}} 的 Due date（子比較晚才更新＝取最大值）
  5. Action：Edit Due date

錯誤選項：沒有 branch（改到 sub-task 自己）、Branch For Sub-tasks（sub-task 沒有 sub-task）、Issue updated＋after（trigger 太廣、方向相反）。

易錯觀念

考題愛用的錯誤說法

同時是兩個 project 的 admin，就能建一條跨兩個 project 的 rule（例：RUN 的 issue clone 到 DEV）。
Rule 只能動 scope 內的 project；跨 project 要 Multiple projects scope，只有 Jira admin 能建。Project admin 只能建 Single project rule。
題目寫「supposing she has all the necessary project permissions」是陷阱：project 權限再多也不夠，差的是 global 的 Jira admin。
你練習時錯過官方來源
All projects 不是有效的 automation scope；Project category 才是。
反了。All projects＝Global，是有效 scope。無效的是 Project category（scope 選單沒有這項）和 Cross-site projects（rule 只在自己這個 site 跑）。
四種 scope：單一、多個、類型、全部（Global）。「類型」是 Software／Business／Service 的 project type，不是 project category。
你練習時錯過官方來源
Multiple issue types 是一種 automation scope。
Scope 只有 Single、Multiple projects、Project type、Global。
你練習時錯過官方來源
Condition 不符會記成 failure。
記成 No actions performed。
官方來源
Project admin 可以把 actor 設成任何人。
只能自己或 Automation for Jira。
官方來源
Rule 用建立者（owner）或觸發者的權限執行。
用 actor 的權限，預設是 Automation for Jira；owner 只負責維護與收錯誤通知。
Daniel 建了 rule、也建了 issue，但 Priority 沒被改 → 缺的是 actor 的 Edit Issues。
你練習時錯過官方來源
{{#lookupIssues}} * {{key}} {{/}} 是錯的 smart value 語法。
這是合法的清單迴圈：{{#清單}} 開頭、{{/}} 結尾，中間對每一筆各跑一次。
你練習時錯過官方來源
新 issue 要繼承 epic 的 due date，要用 Branch For Epic (Parent)。
不用 branch：要改的是新 issue 自己，Edit 的值用 smart value 讀 epic 的 due date 就好；用 For Parent 分支反而會改到 epic 自己。
讀 epic 的寫法官方說法不一：smart values 頁有 {{issue.epic.欄位}}（讀 issue 所屬 epic 的欄位）；教材原本寫的 {{issue.parent.duedate}} 是 Epic Link 改由 Parent 取代後的寫法，但同一頁字面上寫 {{issue.parent}} 只能用在 sub-task，並註明 Epic Link／Parent Link 淘汰會影響這些值。實際用哪個以站台測試為準；TMP 另有限制：Issue created trigger 讀不到 parent 的值。
要改誰就 branch 到誰；只是讀值用 smart value。沒有「Issue Created AND Associated to Epic」這種 trigger。
你練習時錯過官方來源
Sub-task 改了要更新 parent，branch 選 For Sub-tasks。
選 For Parent；For Sub-tasks 是父改了要更新子。
你練習時錯過官方來源

動手做

實作 Lab：Sub-task 改日期，自動更新 parent

約 30 分鐘WEB 的 project admin（你）；Jira admin（看 global automation）

第一次做 Lab？先看 Lab 環境準備：用測試站台、準備測試帳號。畫面名稱可能隨 Atlassian 更新而不同，以下以現行畫面為準。

目標：從零建一條「sub-task 的 Due date 改了就更新 parent」的 rule，看 branch 裡 {{issue}} 和 {{triggerIssue}} 各指誰，再看 scope、actor、owner 在哪裡。

這個 Lab 對應的考點

Trigger 只有一個；condition 不符＝No actions performed；子改父用 Branch For Parent；branch 裡 {{issue}} 是相關 work item、{{triggerIssue}} 是觸發的那張；actor 決定權限，project admin 只能選自己或 Automation for Jira；改完要讀新值先 Re-fetch。

準備

  • WEB 有一張 Story，底下兩個 sub-task，都填了 Due date；Story 的 Due date 比兩個都早。

步驟

  1. 你應該看到：進入 flow builder，第一步要選 trigger。
  2. 你應該看到：流程最上面只有一個 trigger；condition 接在下面。
  3. 你應該看到：Branch 底下有兩個 action。
  4. 你應該看到：Scope 是這個 space（WEB）；Owner 是你；Actor 預設 Automation for Jira。
  5. 你應該看到：Story 的 Due date 變成那一天。
  6. 你應該看到：Status 是 Success；Log 那行寫 issue＝Story 的 key、trigger＝sub-task 的 key。
  7. 你應該看到：Audit log 這次是 No actions performed：condition（必須是 sub-task）不符，不是失敗。

試試看：改一個設定，觀察差異

T1把 branch 改成 For Sub-tasks，再改一次 sub-task 的 Due date。看結果
Story 不會被改：sub-task 底下沒有 sub-task，分支找不到對象。子改父選 For Parent，父改子才選 For Sub-tasks。
T2另建一條 Manual trigger 的 rule：Edit work item 把 Priority 設成 Highest → Comment 寫 {{issue.priority.name}}。在 work item 的 Actions 執行。然後在兩個 action 中間插入 Re-fetch work item data 再跑一次。看結果
第一次留言寫的是舊的 priority（{{issue}} 是觸發當下的快照）；加了 Re-fetch 之後才是 Highest。
T3把 Leo 暫時加進 WEB 的 Administrators，用 Leo 打開這條 rule 的 Actor 下拉。看結果
Leo 只能選自己或 Automation for Jira；要選其他人得是 Jira admin。跨 project 的 rule 要到 ⚙ Settings → System → Global automation 建，也是 Jira admin 的事。
心像錨點：閉上眼睛想一次這個畫面

Audit log 展開後那一行 Log：issue＝STORY、trigger＝SUBTASK。分支裡的 issue 換了人，trigger 永遠是起點。

收尾

  • 停用（或刪除）這兩條 rule。
  • 把 Leo 移出 WEB 的 Administrators，留在 Developers。
