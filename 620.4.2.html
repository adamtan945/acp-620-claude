620.4.2 · Create an automation rule based on business requirements

依需求建立 automation rule：
trigger、condition、action、branch 與 smart values

考題給一段業務需求，要你選出正確的 trigger、對的 condition、對的 action，以及該不該用 branch。這一節把 rule 拆成可以「組裝」的零件，並讓你自己組一條看結果。

術語：考試用 rule／issue；現行文件稱 flow／work item，介面上「Automation Studio」也在改版中。本教材沿用考試用語。

零件 1

Triggers：常考的十幾個

Trigger什麼時候跑陷阱
Issue created建立時要注意 CSV 匯入建立的 issue 不會觸發這個 trigger，大量匯入資料時別指望自動化會跟著跑
Issue transitioned從 A 狀態到 B 狀態（可只指定 To 或 From）凡是「狀態改變時要做什麼」都用這個，不要用 Issue updated；可以只指定 To（轉到某狀態）、只指定 From，或兩者都指定
Issue updated欄位被改不含 Link、Assign、Log work 造成的更新——這三個有各自的 trigger
Field value changed指定欄位改變（可限 added／deleted、可 regex）比 Issue updated 精準，也省執行次數
Issue commented新留言編輯既有留言不會觸發，只有新增留言才算；設定裡可以區分一般留言與 transition 時附帶的留言
Issue assigned／linked／moved／deleted各自事件—
Scheduled固定間隔或 cron；可附 JQL，對每個結果跑兩個重點：連續失敗 10 次會被自動停用（所以要留意 owner 收到的錯誤信）；附帶的 JQL 是以 actor 的權限執行，actor 看不到的 issue 就不會被處理
Manual trigger使用者在 issue 上按可以限制哪些 group 或 role 才看得到這個按鈕，也可以要求使用者按下時先填入資料；拿來測試 smart value 最方便，搭配 Log action 就能安全地印出任何值
Sprint／Version 事件sprint started／completed、version released…—
DevOps 事件branch created、PR merged、build failed、deployment successful…需連接 Bitbucket／GitHub 等
Incoming webhook外部系統 POST 到專屬 URL用 secret 驗證；可帶 issue key 或 JSON
零件 2

Conditions：不符就靜靜停下

Condition用途備註
Issue fields condition比較某欄位（= / ≠ / 含 / 空…）官方建議優先用它，不用寫 smart value
JQL conditionissue 是否符合一段 JQL以 actor 權限執行，看不到的 issue 就不符
User condition某人（initiator／assignee…）是否是某人或在某 group／role可 AND／OR 多條
Related issues conditionparent／sub-task／linked／epic 是否存在或符合 JQL不需要進 branch 就能檢查相關 issue
Advanced compare（smart values）兩個 smart value 比較，支援 regex最彈性也最容易寫錯
If／else block依條件分流到不同 action最多兩層巢狀
考點
Condition 不符的執行在 audit log 是 No actions performed，不是 failure。題目說「rule 沒錯誤但沒動作」→ 先看 condition。
零件 3

Actions：常考的與它們的細節

Action細節
Edit issue預設是整組取代多選欄位；Labels 要用「Add／remove values」才會保留既有；要保留其他多選欄位的值用「Copy from issue」＋新值；進階可用 JSON
Assign issue指定人、Balanced workload（給最少未完成 issue 的人）、Round robin、Random、或 smart value（例如 {{issue.reporter}}）
Transition issue要選目標狀態；transition 有必填欄位或 validator 時要一併填，否則失敗
Create issue／Create sub-tasks／Clone新建的 issue 之後要用 {{createdIssue}}（最近一個）或 branch「All created issues」才能繼續操作
Comment on issue可用 smart value；可限制可見 role／group
Re-fetch issue data更新 smart value 讀到的欄位值。官方原文：預設 {{issue}} 在整條 rule 執行期間不會更新，一直是觸發當下的快照。Edit 之後還要讀新值，就在那一步之前插入這個 action
Send email／Slack／Teams收件人可用 smart value；Free 方案每 24 小時 100 封 email
Lookup issues跑 JQL 把結果放進 {{lookupIssues}}，最多 100 個
Create variable定義自己的 smart value，後面的 action 重用
Log action把文字寫進 audit log，除錯 smart value 用
Send web request呼叫外部 API；回應可用 {{webResponse}}
Link issues／Manage watchers／Delete issue—
Clone issue 不是「完整複製」
官方 Clone work item 原文：會複製「所有可能的欄位資料」，附件要另外在欄位清單選 Attachment 並指定來源 issue 才會一起複製；新 issue 的 status 回到目的 workflow 的第一步、Resolution 被清空；不是 true clone、不會自動連結回原 issue，也不複製 issue links 與 comments。要留關聯就自己加 Link action；要對新卡留言要切到 created issues branch。

零件 4

Branches：讓 action 對相關 issue 各跑一次

圖 2　Branch 裡的 {{issue}} 是「這一輪的相關 issue」；要引用觸發的 Story 用 {{triggerIssue}}。
Branch 類型對誰跑
Sub-tasks／Parent／Epic（parent）／Stories（children）對 issue 階層上的相關項目逐一執行，例如把 action 套用到每一個 sub-task，或往上套用到 parent
Linked issues對所有被連結的 issue 逐一執行，可以指定只處理某一種 link type（例如只處理 blocks）
JQL對符合一段 JQL 的 issue 逐一執行；要注意 JQL 是以 actor 的權限執行的，而且單次執行處理的相關 issue 有數量上限
Current issue對觸發的 issue 自己再開一個分支區塊，通常用來把一連串步驟分段整理，或做 if／else 以外的流程切分
Most recently created issue／All created issuesCreate／Clone 之後才有；不進 branch，後面的 action 仍作用在觸發 issue 上
Advanced（smart value）對任何一個 list 型別的 smart value 逐項執行，例如把每一則留言（{{triggerIssue.comments}}）或 webhook 傳進來的 JSON 陣列各處理一次
Branch at the same timePremium／Enterprise：多段互不相依的步驟同時跑
兩個常考行為
① 分支平行、順序不保證，分支 A 改的值不要指望分支 B 讀得到。② 每次執行最多處理 5,000 個相關 issue；Lookup issues 只取前 100。
零件 5

Smart values：雙大括號裡的動態值

語法
  • 點記法：{{issue.assignee.displayName}}；多字屬性用 camelCase（issueType、fixVersions）
  • 函數有括號：{{now.plusDays(5)}}、{{issue.summary.toLowerCase()}}；可串接
  • List 逐項：{{#issue.comments}}{{author.displayName}}{{/}}
  • 數學：{{#=}}{{issue.Story Points}} * 2{{/}}
  • 預設值：{{issue.assignee.displayName|"未指派"}}
  • List 工具：.first、.last、.size、.join(", ")
最常考的幾個
值意思
{{issue}}目前這一輪的 issue（在 branch 裡＝相關 issue）
{{triggerIssue}}觸發 rule 的那張，任何地方都指它
{{createdIssue}}／{{createdIssues}}本次 rule 最近建立的一張／全部
{{lookupIssues}}Lookup issues 的結果（≤100）
{{initiator}}做出觸發動作的人
{{now}}現在；.plusDays()、.format("yyyy-MM-dd")
{{issue.parent}}／{{issue.subtasks}}／{{issue.epic}}階層
{{fieldChange.fromString}}／{{fieldChange.toString}}Field value changed 的前後值
怎麼找某欄位的 smart value、怎麼測
官方做法：用 Manual trigger ＋ Log action，在 log 裡寫 {{issue.某欄位}}，手動觸發後到 audit log 看值；或把值包在 {{#debug}}…{{/}} 裡不用另加步驟。
Smart value 與 JQL 是兩種語法，別混用
Smart value 用 dot notation 包在雙大括號裡（{{object.property.subProperty}}，多字屬性用 camelCase），函式一律帶括號（{{now.plusDays(5)}}、{{issue.summary.toLowerCase()}}）。JQL 是查詢語言，寫在 Scheduled trigger、JQL condition、Lookup issues 裡，用的是 project = FOOD AND status = Done 這種欄位運算子語法。 Scheduled trigger 的查詢要寫 project = FOOD，不是 {{project}}；JQL 的 now() 也不是 smart value 的 {{now}}。自訂欄位在不同站台的 ID 不同，不要把別的站台的 customfield_10001 直接照抄。
來源：What are smart values?（2026-09-08 查核）
情境練習

先自己判斷，再點開解答

Story 轉到 Done 時，它底下所有 sub-task 也要自動 Done。
解答
組法是：Trigger 選 Issue transitioned（To 設成 Done）→ Branch 選 for sub-tasks → Action 用 Transition issue 轉到 Done。關鍵在為什麼需要 branch：action 預設只作用在觸發的那一張 issue 上，要對「一群相關的 issue」各做一次，就必須先開一個分支把範圍切換過去。這題不需要 condition；但如果只想在 Story 這個 type 上生效、Task 不要，就在 branch 之前加一個 Issue fields condition 判斷 issue type。
承上，PM 希望在 Story 上留言「已自動關閉 N 個 sub-task」。留言該放哪、N 怎麼寫？
解答
留言的 action 必須放在 branch 外面——放在裡面的話，分支會對每一個 sub-task 各跑一次，結果是留了 N 則重複的留言，而且留在 sub-task 上而不是 Story 上。數量用 {{triggerIssue.subtasks.size}}。這裡也順便釐清一個高頻考點：在 branch 裡面，{{issue}} 指的是「這一輪的 sub-task」；在 branch 外面，{{issue}} 才等於觸發的那張 Story。想在任何位置都穩定指向觸發的 issue，就用 {{triggerIssue}}，它不受分支影響。
需求：新 Bug 建立時，若 priority 是 Highest 就指派給值班工程師並通知 Slack。
解答
組法是：Trigger 用 Issue created → Condition 用 Issue fields condition 檢查 Issue type = Bug 且 Priority = Highest（也可以拆成兩個 condition 串著，效果相同，rule 裡的多個 condition 之間是 AND）→ Action 先 Assign issue 指派給值班工程師，再 Send Slack message。官方特別建議優先使用 Issue fields condition 而不是自己寫 smart value 比較，因為它不用處理格式與空值，出錯機率低得多。
想在 issue 加 label「reviewed」，但既有的其他 label 都被清掉了。
解答
因為 Edit issue 對多選欄位的預設行為是「整組取代」，你填進去的值會覆蓋掉原本的整個清單，不是附加上去。要保留既有的 label，必須在該欄位的 ••• 選單改用 Add／remove values 模式，明確告訴 Jira「我只是要新增這一個」。這個陷阱在 Labels、Components、Fix versions 這些多選欄位上都會出現，是實務上最容易造成資料損失的自動化錯誤之一——而且 issue 歷史雖然留有紀錄，但要一張張還原非常痛苦。
Rule 用 Create issue 建了一張新 issue，接著的 Comment action 卻留在原本的 issue 上。
解答
因為建立新 issue 並不會把 rule 的「當前對象」切換過去，後面的 action 預設仍然作用在觸發的那張 issue 上。要對新建的 issue 動作有兩種寫法：一是加一個 branch 選 Most recently created issue（或 All created issues，如果建了好幾張），把範圍切換過去；二是不開分支，直接在 action 的欄位裡用 smart value {{createdIssue}} 指名它。這個「範圍不會自動跟著移動」的觀念，跟前面 branch 的道理是同一個。
每天早上 8 點，把逾期且未指派的 issue 全部加 label「overdue」。
解答
用 Scheduled trigger：設定 cron 每天 08:00 執行，附上 JQL duedate < now() AND assignee is EMPTY AND resolution is EMPTY，並且勾選「對每個結果執行」（不勾的話 rule 只會跑一次，而不是對每張 issue 各跑一次，這是很常見的錯誤）。動作用 Edit issue 加 label，記得選 Add／remove values 模式以免洗掉既有 label。兩個要注意的地方：JQL 是以 actor 的權限執行的，actor 看不到的 issue 就不會被處理；另外 Scheduled rule 連續失敗 10 次會被自動停用。
想用 Issue updated 抓「assignee 改變」，卻從來沒觸發。
解答
因為 Issue updated 這個 trigger 並不涵蓋三種操作：Assign（指派）、Link（建立連結）與 Log work（記錄工時）——這三件事各自有專屬的 trigger。改用 Issue assigned，或是用更精準的 Field value changed 指定 Assignee 欄位。實務上也建議優先選 Field value changed 而不是 Issue updated：它只在你關心的欄位真的變動時才觸發，既精準又省執行次數（automation 的用量是有上限的）。
Rule A 改了 Priority，Rule B 的 trigger 是 Field value changed（Priority），但 B 沒跑。
解答
因為 Rule B 的設定裡 Allow rule trigger 預設是關閉的——這個開關決定「別的 rule 造成的變更，能不能觸發我」。預設關閉是刻意的安全設計，避免規則之間意外連鎖。到 Rule B 的 rule details 把它打開就會生效。打開之後要小心兩件事：A 改 B、B 又改回 A 這種互相觸發會形成迴圈，Jira 偵測到連續 10 次就會把執行標記為 LOOP 並中止；另外每一次連鎖觸發都會消耗執行次數。「rule 明明沒錯卻沒跑」的排查，第一個就該看這個開關。
Project admin 想把 rule 的 actor 改成部門主管，讓歷史紀錄顯示主管做的。
解答
做不到。project admin 能選的 actor 只有兩個：自己，或是系統使用者 Automation for Jira；要把 actor 設成其他人，必須由 Jira admin 操作。這個限制是為了防止有人藉由 automation「冒用」他人身分做事。另外還有一個前提常被忽略：被設為 actor 的那個人必須真的具備該 project 的操作權限，否則 rule 執行時會因為權限不足而失敗。順帶區分一組容易混淆的概念：actor 是「以誰的身分執行」（會顯示在 issue 歷史紀錄上），owner 是「誰建立了這條 rule」（出錯時收信的人），兩者可以是不同人。
Comment 裡想寫「由 {{initiator.displayName}} 於 {{now}} 觸發」，日期格式要 2026-09-08。
解答
寫成 {{now.format("yyyy-MM-dd")}}——{{now}} 直接輸出會帶著時間與時區，用 .format() 才能指定格式。這裡也介紹官方推薦的除錯法：不確定某個 smart value 會輸出什麼時，先用 Manual trigger 加上 Log action 試，把要測的值寫進 log，在 issue 上手動觸發一次，再到 audit log 看實際輸出。這樣做完全不會動到任何資料，比直接寫進 Comment 或 Edit 安全得多。
Balanced workload 和 Round robin 差在哪？
解答
差別在要不要看目前的工作量。Balanced workload 會比較候選名單中每個人手上未完成 issue 的數量，指派給最少的那一位，所以負擔會自然趨於平均；Round robin 則單純依名單順序輪流，不管對方手上已經積了多少工作。實務上的選擇：工作大小相近、希望絕對公平就用 Round robin；工作大小差異大、有人可能卡在大案子上，用 Balanced workload 比較合理。兩者都可以排除特定人或限定群組。
常見陷阱

考題喜歡設的誤解

誤解事實
「Condition 不符會顯示錯誤」不會。condition 不符時，audit log 顯示的是 No actions performed（正常結束，只是沒事情可做），不是錯誤。所以看到「rule 有跑、沒報錯、也沒動作」，第一個要檢查的就是 condition
「Branch 裡的 {{issue}} 是觸發的那張」不是。在 branch 內部，{{issue}} 指的是這一輪正在處理的相關 issue；要穩定指向觸發 rule 的那一張，任何位置都用 {{triggerIssue}}
「分支會依序執行」不會。分支是平行執行的，順序不保證；所以分支 A 寫進去的值，不要指望分支 B 讀得到
「Create issue 之後的 action 會作用在新 issue」不會。建立新 issue 不會切換 rule 的作用對象，後續 action 仍然作用在觸發的 issue 上；要對新的那張動作，得用 branch「Most recently created issue」或 smart value {{createdIssue}}
「Edit issue 加 label 會保留舊的」不會。Edit issue 對多選欄位預設是整組取代，會洗掉既有的值；要附加請改用該欄位的 Add／remove values 模式
「Issue updated 什麼改變都抓」不會。Issue updated 不包含指派（Assign）、建立連結（Link）與記錄工時（Log work）這三種變更，它們各自有專屬的 trigger
「一條 rule 可以有多個 trigger」不行。一條 rule 只能有一個 trigger；需要涵蓋多種事件時，改用 Multiple issue events 這個 trigger 一次勾選多個事件
實作（40 分鐘）

三條 rule 把零件都摸過

  1. Rule 1：Issue created → Issue fields condition（type = Bug）→ Assign（Balanced workload，候選 2 人）→ Comment「{{initiator.displayName}} 建立，指派給 {{issue.assignee.displayName}}」。建三張 Bug 看分配。
  2. Rule 2：Issue transitioned（To Done）→ Branch for sub-tasks → Transition to Done；branch 外再 Comment「已關閉 {{triggerIssue.subtasks.size}} 個 sub-task」。看 audit log 的分支紀錄。
  3. Rule 3：Manual trigger → Log action 寫 {{issue.key}} / {{issue.fixVersions.name}} / {{now.plusDays(5).format("yyyy-MM-dd")}}，在 issue 上手動觸發，到 audit log 讀值。
  4. 把 Rule 1 的 actor 改成自己，重跑，看 issue 歷史紀錄的作者變化。
  5. 在 Rule 2 的 Edit issue 試 Labels「整組取代」vs「Add／remove values」的差別。
  6. 四個反例（來自另一套教材的 lab，逐一製造一種差異）：
    （a）錯誤欄位路徑：Log 印 {{issue.notARealField}} 再改 {{issue.key}} → 前者空值，證明 smart value 可單獨測；
    （b）快照未更新：Log Priority → Edit Priority → Log Priority → 讀到舊值；中間插入 Re-fetch issue data 再 Log → 讀到新值；
    （c）上下文：在 parent 的 Sub-tasks branch 內同時印 {{issue.key}} 與 {{triggerIssue.key}} → 前者每圈不同、後者固定；
    （d）重跑安全：同一條加標籤 rule 手動跑兩次 → 標籤集合一致；但若含 Comment，會留兩則，需要自己設重複判斷。
  7. 記錄表：rule 名稱與版本、Actor、觸發 issue key、預期、audit log ID、實際結果、issue History。一次只改一個設定再重測，最後把 demo rule 關掉。
