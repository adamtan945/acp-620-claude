620.4.3 · Troubleshoot Jira automation

排查 Jira automation：
權限、audit log、上限與迴圈

Rule 沒照預期跑，九成是四種原因：根本沒觸發、condition 沒過、actor 沒權限、撞到上限。這一節把它們排成一棵決策樹，並解釋 automation 和 project 權限之間的關係——那是官方 bullet 特別點名的。

術語：考試用 rule／issue；現行文件稱 flow／work item。本教材沿用考試用語。
這一節考什麼

兩條 bullet，翻成考題語言

官方 bullet考題會怎麼問
Understand the relationship between project permissions and automation rules「rule 顯示 permission 錯誤」→ actor 是誰、透過哪個 role 拿權限、TMP Private 為何失敗、project admin 能把 actor 設成誰
Understand the typical root causes for rule failure「audit log 沒紀錄／No actions performed／Some errors／LOOP／THROTTLED」各代表什麼、先查哪裡
核心關係

Rule 不是萬能鑰匙：它以 actor 的身分行事

圖 1　「rule 顯示沒權限」的檢查順序：actor 是誰 → 該 actor 在這個 project 有沒有這個 action 需要的權限。
問題答案
誰能建 ruleCMP：Administer Projects ＋ Browse Projects；TMP：Administrator；global／multi-project：Administer Jira。Jira admin 可在 Global configuration 關掉 project admin 的建 rule 權
Actor 可以是誰Project admin 只能選自己或 Automation for Jira；Jira admin 可選任何人（Marketplace app 使用者除外）。若目前 actor 是別人，project admin 得先改回自己或 Automation for Jira 才能編輯
Actor vs OwnerActor 執行動作、需要 project 權限、歷史紀錄顯示它；Owner 收錯誤 email、可批次轉移。Actor 只能逐條改
JQL 也算JQL condition、Scheduled trigger 的 JQL、Lookup issues 都以 actor 權限執行——actor 看不到的 issue 就像不存在
Issue securityissue 有 security level 時，actor 也要在該 level 內才動得了

Audit log：每次執行的紀錄

在哪裡
  • 單一 rule：rule 頁 → Audit log
  • 整個 project：Project settings → Automation → Audit log
  • 全站：⚙ → System → Global automation → Audit log（Jira admin）
  • 保留 90 天，之後自動刪除、不可復原
每筆顯示
  • 觸發時間、audit log ID、rule 名稱
  • Status、總時間（含排隊與處理）
  • 展開看每一步的執行結果與時間
Status意思先查
Success所有 action 都順利執行完畢，沒有任何一步報錯若結果仍不對，看是不是改到別張 issue（{{issue}} vs {{triggerIssue}}）
No actions performedrule 確實被觸發了，但因為某個 condition 判定不符（或 JQL 查不到結果），所以後面的 action 全部跳過——這是正常結束，不是失敗先看 condition 的判定；如果用的是 JQL，記得它以 actor 的權限執行，actor 看不到的 issue 一律判定不符
Some errors有些 action 執行成功、有些失敗；rule 沒有中斷，所以資料可能處於「改了一半」的狀態，要展開細節逐步確認展開錯誤訊息：permission、欄位、smart value
Failure整條 rule 執行失敗，沒有任何動作生效同上；web request 回錯也算
Loop偵測到規則之間互相觸發形成迴圈，連鎖達到 10 次時被系統強制中止，以免耗盡站台的自動化資源檢查 Allow rule trigger 是否有必要開著，以及能不能加一個 condition 讓規則在條件已滿足時停下來（讓規則具備冪等性）
Throttled超過了處理時間或同時執行數的服務上限，執行被暫時擋下；這個狀態不計入每月用量常見原因是 trigger 設得太寬（每次更新都跑）、分支數量太多，或是 Send web request 等外部呼叫回應太慢，這些都會吃掉處理時間額度
Config change這不是執行紀錄，而是「有人修改了這條 rule」的異動紀錄，可以用來追查是誰在什麼時候改了什麼查看是誰在什麼時候修改了這條 rule，排查「昨天還好好的」這類問題時很有用
狀態名稱依官方 audit log 與用量計算頁；計入用量的狀態為 SUCCESS、NO_ACTIONS_PERFORMED、SOME_ERRORS、ABORTED、NO_MATCH，THROTTLED 不計。

會讓 rule 被 throttle 或停掉的數字

上限數字
同時執行的 rule 數Free 5／Standard 10／Premium 20／Enterprise 30（多產品取最高）
處理時間（daily processing time）每 12 小時 60 分鐘；外部呼叫慢、分支多都會吃掉，超過會被 THROTTLED

每月用量配額（usage limit）現行模型（2025 起）：以「步驟」計，trigger／condition／action／branch 各算一步，整個 organization 共用一個池；Jira 的每月額度 Free 150／訂閱、Standard 400／人、Premium 750／人、Enterprise 1,000／人。到 80%、100% 會通知 admin；100% 後 rule 停跑到下個計費日，除非開啟額外用量計費。查看：Atlassian Administration → Insights → Platform usage。
考試版（2023 考綱年代）：以「rule 執行次數／月」計，單一 project 的 rule 不限量、只有 multi-project／global rule 計入配額，Enterprise 無上限。題目若用舊說法，照舊模型作答。
考點
「rule 突然停掉」的三個典型答案：Scheduled trigger 連續失敗 10 次自動停用；撞到 service limit（處理時間、排隊數）被 THROTTLED；或整個 product 的每月用量配額用完（usage limit）而全部停跑到下個月。「rule 跑很慢」→ 外部 web request 等待與分支數量會計入處理時間。

情境練習

先自己判斷，再點開解答

Rule 在 audit log 顯示「Some errors」，展開寫「actor does not have permission to transition」。actor 是 Automation for Jira。
解答
問題出在 atlassian-addons-project-access 這個 role 沒有 Transition Issues 權限。關鍵觀念是：Automation for Jira 這個系統使用者，是透過 atlassian-addons-project-access role 取得 project 權限的——它不是萬能的系統帳號，一樣受 permission scheme 管轄。所以只要有人在整理權限時把這個 role 的某項權限拿掉（或誤以為「這個 role 沒人在裡面」而刪掉它），相關的 automation 就會開始失敗。解法有兩個：請 Jira admin 在該 project 的 permission scheme 把 Transition Issues 補給這個 role，或是把 rule 的 actor 改成一位確實有權限的真人。
同一條 rule 在 CMP 正常，在一個 Private 的 TMP 就失敗。
解答
因為 TMP 沒有 permission scheme，權限完全靠「有沒有被加進這個 project 並拿到 role」決定。當 TMP 設成 Private（或 Limited）時，沒有被明確加入的人就沒有權限——而 actor（Automation for Jira 或某位使用者）正是沒被加進去的那一個。CMP 那邊之所以正常，是因為 permission scheme 已經把權限給了 atlassian-addons-project-access role。解法是把 actor 加進這個 TMP 並給予足夠的 role，或（在資安允許的前提下）把 access level 改成 Open。這是官方 KB 專門立了一篇來說明的常見狀況。
Rule 從沒在 audit log 出現過紀錄。
解答
audit log 完全沒有紀錄，代表 rule 根本沒有被觸發——這是排查的第一個分岔點，跟「跑了但失敗」要走完全不同的方向。依序檢查四件事：① rule 是不是被停用了（或 Scheduled rule 連續失敗 10 次被系統自動停用）；② scope 有沒有涵蓋這個 project；③ trigger 選錯（最典型的是用 Issue updated 想抓指派變更，但它不含 Assign、Link、Log work）；④ 變更是由另一條 rule 造成的，而這條沒開 Allow rule trigger。四項都排除還是沒紀錄，才需要懷疑是產品面的問題。
Audit log 每次都是「No actions performed」，沒有錯誤。
解答
「No actions performed」不是錯誤，它代表 rule 有正常被觸發、也正常執行完畢，只是某個 condition 判定為不符，所以後面的 action 全部跳過。查的方向是 condition 而不是權限。有一個很容易忽略的陷阱：如果用的是 JQL condition（或 Scheduled trigger 的 JQL、Lookup issues），它們都是以 actor 的權限執行的——actor 看不到的 issue，對這段 JQL 而言就等於不存在，於是永遠判定不符。這時要檢查的是 actor 的權限，而不是 JQL 寫錯。
Rule A：Priority 改變就加 label；Rule B：label 改變就把 Priority 調高。兩條都開了 Allow rule trigger，結果狀態變 LOOP。
解答
因為兩條 rule 互相觸發形成了無限迴圈：A 改 Priority → 觸發 B 加 label → 又觸發 A…… Jira 偵測到連鎖達到 10 次就會把執行標記為 LOOP 並強制中止，避免耗盡整個站台的自動化資源。修法有三種，由好到壞排序：① 在其中一條加上 condition 讓它有機會停下來（例如「label 已經存在就不做」，這是最正確的做法，讓規則具備冪等性）；② 關掉其中一條的 Allow rule trigger；③ 重新檢視這兩條規則是不是本來就該合併成一條。
Project admin 想把 rule actor 改成主管，下拉選單裡只有自己和 Automation for Jira。
解答
這是刻意的設計，不是 bug。project admin 能選的 actor 只有自己與系統使用者 Automation for Jira 兩個，理由很直接——否則任何 project admin 都能建一條「以老闆的身分」執行的規則，等於繞過權限體系冒用他人身分。要把 actor 設成主管，必須請 Jira admin 操作，而且主管本人得有該 project 的對應權限，否則 rule 一樣會失敗。另外提醒一個編輯上的限制：如果一條 rule 目前的 actor 是別人，project admin 得先把它改回自己或 Automation for Jira，才能編輯這條 rule。
Scheduled rule 上週還在跑，這週發現被停用了，沒人動過。
解答
最可能的答案是 Scheduled trigger 連續失敗 10 次，被系統自動停用了。這是保護機制，避免一條壞掉的排程規則持續消耗資源。正確處理順序是：先看 audit log 找出那 10 次為什麼失敗（常見的是 JQL 語法因欄位被刪而失效、actor 權限被調整、或目標欄位不在 screen 上），把根因修掉之後再重新啟用——直接啟用不修原因，很快又會被停用一次。順帶一提，rule 的 owner 在失敗時會收到錯誤通知信，所以這種事通常不該拖到「這週才發現」。
Branch for sub-tasks 裡用 {{issue.parent.summary}} 想拿 Story 的 summary，有時是空的。
解答
在 branch for sub-tasks 裡面，{{issue}} 指的是「這一輪的 sub-task」，所以 {{issue.parent.summary}} 是繞了一圈去讀 parent；直接寫 {{triggerIssue.summary}} 才可靠——它在任何位置都穩定指向觸發 rule 的那張 issue，不必經過階層查詢。另外要記住兩個相關的觀念：分支是平行執行的，順序不保證，所以不要指望讀到其他分支剛寫入的值；而且 {{issue}} 是觸發當下的快照，rule 執行過程中被改掉的欄位不會自動更新，需要新值就要先插入 Re-fetch issue data。
Edit issue 設定 custom field「Severity」失敗，錯誤說欄位不可用。
解答
因為這個欄位沒有出現在該 issue type 所使用的 screen 上（也可能是 custom field 的 context 沒有涵蓋這個 project 或 issue type）。automation 不能寫入「這張 issue 上根本不存在」的欄位，這一點跟人工編輯的限制是一致的。這是 Edit issue 失敗最常見的原因，而且很容易誤判成權限問題。解法是請 Jira admin 把欄位加進對應的 screen、並確認 context 涵蓋這個 project。要注意就算改用進階的 JSON 寫法也繞不過去——欄位必須真的可用才行。
Rule 執行成功，但改到的是 parent 而不是觸發的 sub-task。
解答
這是作用範圍搞錯的典型症狀，rule 本身沒有壞。要核對兩件事：第一，逐一確認每個 action 是放在 branch 裡面還是外面——如果它被縮排在 branch for parent 底下，那它作用的對象就是 parent，不是觸發的 sub-task。第二，檢查 action 裡用的 smart value，是不是寫成了 {{issue.parent}}。修法是把該 action 拖到 branch 外面，或把 smart value 改成 {{triggerIssue}}。排查時把 audit log 的每一步對照 issue 的 History，很快就能看出是哪一步寫錯了對象。
想知道某 custom field 的 smart value 名稱。
解答
用官方推薦的安全做法：把 trigger 暫時改成 Manual trigger，加一個 Log action 寫上 {{issue.欄位名稱}}，在一張測試 issue 上手動按一次，再到 audit log 讀輸出。這樣做完全不會修改任何資料，也不必等真實事件發生。另一個更省事的技巧是 {{#debug}}…{{/}}：把要觀察的 smart value 包起來，它會照常參與運算，同時把值印進 audit log，連額外的 Log action 步驟都不用加。
常見陷阱

考題喜歡設的誤解

誤解事實
「Rule 是系統跑的，不受 permission scheme 限制」不對。rule 是以 actor 的身分執行的，一樣受 permission scheme 管轄；系統使用者 Automation for Jira 是透過 atlassian-addons-project-access 這個 role 取得權限的
「Owner 收到錯誤信，所以 owner 沒權限」沒有關係。owner 只是「建立這條 rule、出錯時收信」的人；真正需要權限的是 actor，兩者可以是不同人
「No actions performed 是錯誤」不是錯誤。它代表 rule 正常觸發並執行完畢，只是 condition 判定不符所以沒有動作；要查的是 condition，不是權限
「一條 rule 改了欄位，另一條 rule 自然會接著跑」預設不會。要讓「別的 rule 造成的變更」能觸發自己，必須在 rule details 打開 Allow rule trigger；開了之後要小心互相觸發形成 LOOP
「Audit log 永久保存」不是。audit log 只保留 90 天，之後自動刪除且無法復原；需要長期追溯的紀錄要自己另外匯出
「Project admin 可以把 actor 設成任何人」不能。project admin 只能把 actor 設成自己或 Automation for Jira；要設成其他人必須由 Jira admin 操作，而且那個人得有對應的 project 權限
「Lookup issues 會拿到全部結果」不會。Lookup issues 最多只取前 100 筆；需要處理更多 issue 請改用 branch 搭配 JQL（單次執行的相關 issue 上限是 5,000）
實作（30 分鐘）

故意弄壞三次，看 audit log 怎麼說

  1. 把一條會 Transition 的 rule 的 actor 改成一個沒有 Transition Issues 權限的測試帳號 → 觸發 → 讀 audit log 的錯誤字句。
  2. 在 TMP 把 project 改成 Private、不加 Automation for Jira → 觸發 → 觀察失敗；改回 Open 或加進去再試。
  3. 建 Rule A（Priority 改變→加 label）與 Rule B（label 改變→改 Priority），兩邊開 Allow rule trigger → 觸發 → 看 LOOP 出現需要幾次。
  4. 把一條 rule 的 condition 改成永遠不符 → 觸發 → 確認 status 是 No actions performed 而不是錯誤。
  5. 用 Manual trigger ＋ Log action 印 {{#debug}}{{issue.fixVersions.name}}{{/}}，讀 audit log。
  6. 做「快照」實驗：Log Priority → Edit Priority → Log Priority（仍舊值）→ 插入 Re-fetch issue data → Log Priority（新值）。把「需要最新值的步驟放 re-fetch 之後」變成肌肉記憶。
