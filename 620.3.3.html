620.3.3 · Implement versioning, manage releases and roadmaps, and predict the impact of scope changes

Versions、releases、roadmap 與範圍變動

Version 是 project 裡的「時間點」：把工作打包成一個可以 release 的東西。這一節有四件事要會：version 的建立與狀態操作、release page 能看出什麼、timeline（roadmap）怎麼排、以及範圍變了會在哪些報表上顯示出來。

術語：考試用 version／roadmap／issue；現行官方文件為 release／timeline／work item。本教材沿用考試用語，引用現行文件時保留其用語。

核心模型

Version 的三個狀態與六個動作

官方定義三種狀態：Unreleased（開著的包裹）、Released（打包好的）、Archived（歷史快照，從報表與下拉選單隱藏）。狀態決定 version 出現在哪些下拉選單（例如 Fix version）與報表裡。

必考

Fix versions vs Affects versions

Fix versions

這張 issue 的工作在哪個版本釋出。官方例子：bug 修好、隨 3.6.2 出貨 → Fix version = 3.6.2。

  • 填了就等於把 issue 加進該 version
  • Release page、Version report、Release burndown 都看它
  • Kanban 的 sub-filter 也看它（released 就從 board 消失）
Affects versions

這個 bug 影響哪些版本。可能好幾個舊版都有。

  • 填了不會把 issue 加進 version
  • 用途是搜尋：「哪些 issue 影響 3.5？」
  • 不影響 release 與報表
Team-managed：有 Releases ≠ 兩種版本欄位都有

TMP 在 features 開啟 Releases 後可以使用 Fix versions，但不要因此推論 Affects versions 也能用。官方功能請求 JRACLOUD-85690「Affects Version/s in team-managed projects」在 2026-09-08 查核時仍是 Gathering Interest／未解決。

遇到欄位不見時，先核對 project 類型與功能支援，不是加一個同名的文字 custom field 就好——自己新增的文字欄位沒有系統版本欄位的語意與關聯（不會進 release 範圍、不會被 Version report 認得）。

「直接從 board 發布版本」是 CMP Kanban 的入口

題目若指定「要能直接在 board 上 release」，那是 company-managed Kanban board 的功能。這和「這個 project 能不能管理 versions」是兩個不同條件：TMP 能用 Releases，不代表有相同的 board 操作入口。反過來，「依 issue type 使用不同 workflow」兩種管理模式都做得到，不能只憑這一項就判定必須用 company-managed。

Bullet 3

Timeline（roadmap）：單一 project 的 Gantt

圖 2　Scrum project 的 child 依所屬 sprint 的日期排（也可用 Start／Due date）；Kanban project 只用 Start／Due date。
規則（官方）內容
範圍一個 timeline 只能顯示一個 project；跨 project 規劃要 Plans（Premium／Enterprise）
Parent 的排程可以手動指定 parent 的起訖日期，也可以讓 Jira 依底下 child 的日期自動推算出範圍
Child 的排程（Scrum）優先採用它所屬 sprint 的起訖日期，沒有 sprint 時才看 Start date 與 Due date——所以 Scrum 的 issue 就算沒填日期也畫得出長條
Child 的排程（Kanban）只能依 Start date 與 Due date 來畫，因為 Kanban 沒有 sprint 可以借用時間框架；沒填日期就沒有長條
沒有 parent 的 childShow inline hierarchy 開啟（預設，考試作答用這版）：child 縮排在 parent 下，沒有 parent 的 child 不會出現；只顯示 level 1 與 level 0，sub-task 不顯示。
關閉：官方原句「The timeline uses a flat layout and shows work items without their parent and subtasks」——改成平面清單，可含沒有 parent 的工作（Timeline limits，2026-09-08）
DependenciesTimeline 上的 dependency 其實就是 issue links（現行稱 work item links），用來表達「這件事要等那件事完成」的先後關係
畫面元素週／月／季切換、sprint（Scrum）與 release 標記、圖例、全螢幕、點 bar 開側欄直接編輯
Parent 的 type預設是 Epic，但 Jira admin 可以指定別的 work type 當作 parent 層（設定後畫面上的按鈕會跟著變成 Create Feature 之類的字樣）

Timeline 的內建 filters（官方清單未列 Sprint）

現行單一 project Timeline 的內建 filters 是：assignee、status、versions、type、label、component、keyword、goals。官方清單沒有列出 Sprint。Scrum 的 child 可以「依 sprint 日期排長條」，不代表畫面上一定有獨立的 Sprint filter。

CMP 可用 board quick filters、TMP 可用 custom filters 補足；新篩選功能也可能分批推出。要按 sprint 限縮時核對站台實際的自訂篩選能力，別斷言「Timeline 永遠無法依 sprint 篩選」。

比 Timeline 更大的規劃：Plans（Premium／Enterprise）

Saved views
  • 同一份計畫，管理者看高階進度、團隊看 sprint capacity、協調者看 blockers
  • 調整 filters／columns／grouping 後存成 view：More on current view → Save current view
  • 這和「把欄位變更寫回 Jira issue」是兩種不同操作；計畫內的變更要經 review／save 才寫回，模擬中的日期不是對團隊的承諾
  • 多人同時改同一個 view 時，另存新 view 可保留對方的設定
Goals 分組與自訂階層
  • Plans 可依 Goals 分組，也可依 team、sprint、release 分組 → 不能說「Plans 與 Goals 完全無關」
  • 但也不能因此推論它有完整的預算／投資組合管理能力
  • Epic 之上的自訂階層（年度目標 → Epic → Story → Sub-task）：要由 Jira admin 先建立標準 work type、加進適當 scheme，再關聯到高層級
  • 只把某個 type 命名成「Initiative」不會讓它自動位於 Epic 之上；階層變更會影響既有 Plans 與 parent 關係，不是個人顯示偏好

判斷功能時找具體能力（容量規劃、相依性、多情境比較），「Portfolio」「Lean」這種泛稱不足以判定支援與否。

Bullet 4

範圍變了，報表上長怎樣

「預測範圍變動的影響」在考試裡通常是問：某個動作之後，哪張報表會怎麼變。把三個東西對起來——動作 → 報表 → 視覺特徵。

報表範圍變動的視覺特徵預測的依據
Release burndown（Scrum，依 version）每個 sprint 一根長條；scope added 以深色段標示；預測還要幾個 sprint近幾個 sprint 的 velocity；未估點比例高時預測不可靠
Version report預測 release 日期線；scope 增加時預測日往後移受 version 的 start date 與 working days 影響
Epic burndown同 Release burndown，但以 epic 為範圍；scope added 深色段近 3 sprint velocity；>30% 未估點則不準
Sprint reportsprint 開始後加入的 issue 標「*」；估點改變顯示「3 → 5」用來判斷 overcommit 與 scope creep
Burnup紅線（scope）往上跳＝中途加了工作；紅綠交會＝完成—
Burndown剩餘工作線往上跳；guideline 不變sprint 開始時沒有 issue 就沒有 guideline
考題長相
「PM 在 sprint 中途把兩張 story 加進 sprint，哪張報表會標記？」→ Sprint report 的星號、Burnup 紅線上升、Burndown 往上跳。「v2.0 加了 10 張 story，主管想知道會延多久？」→ Version report 的預測線，或 Release burndown 的預估 sprint 數。
情境練習

先自己判斷，再點開解答

PM 把 bug 的 Affects versions 填成 v2.0，卻發現 v2.0 的 release page 沒有這張 bug。
解答
因為 Affects versions 不會把 issue 加進 version，它記錄的是「這個 bug 影響到哪些版本」，純粹是給搜尋與分類用的資訊。真正把一張 issue 納入某個版本範圍的欄位是 Fix versions——填了它，這張 issue 才會出現在 release page、Version report 與 Release burndown 裡。記法很簡單：Affects 是「哪裡壞了」，Fix 是「哪一版修好出貨」，只有後者會影響 release 與報表。
Release v1.0 時有 3 張 issue 未解決，PM 想讓 release 內容與實際一致。
解答
在按下 Release 之後跳出的對話框裡選「把未解決的 issue 移到另一個 version」（例如 v1.1），不要選忽略。差別在於：選忽略的話，那 3 張沒做完的 issue 仍然掛在 v1.0 底下，等於這個 release 宣稱交付了實際上沒交付的東西，Version report 也會跟著失真；把它們移到 v1.1，v1.0 的內容就與實際出貨一致，剩下的工作也自然滾進下一個版本。Jira 不會阻止你發佈一個有未完成工作的版本，它只會問你怎麼處理——這一點常被考題拿來設陷阱。
Release v1.0 之後，Kanban board 上原本 Done 的卡片全部消失，團隊以為出錯。
解答
這是正常且刻意的設計，不是出錯。Kanban board 的預設 sub-filter 是 fixVersion in unreleasedVersions() OR fixVersion is EMPTY，意思是只顯示「還沒發佈」或「沒填版本」的工作。v1.0 一旦被 release，掛在它底下的 issue 就不再符合這個條件，自然從 board 上消失——這正是 Kanban 用來清空 Done 欄的機制（Scrum 則是靠完成 sprint）。要強調的是資料完全沒有被刪除，JQL 搜尋、release page 都還找得到。
v1.1 與 v1.2 內容重疊，PM 想合併成一個，且不想逐張改 Fix version。
解答
用 Merge（••• → Merge → 選目標 version）。把 v1.1 併入 v1.2 之後，原本掛在 v1.1 的 issue 會自動改成 v1.2，完全不用逐張編輯。要提醒的是兩個後果：來源 version（v1.1）會消失，而且這個動作不可逆，Jira 不會幫你留備份，也沒有「拆回來」的功能。所以合併前先確認方向對不對——併錯了只能手動一張張改回去。
刪除 v0.9 時，Jira 問了一個問題，是什麼？
解答
Jira 會問你掛在 v0.9 底下的那些 issue 該怎麼辦：是要把它們移到另一個 version，還是單純把版本關聯拿掉（issue 的 Fix versions 變成空白）。這個提問的用意是避免資料悄悄消失——刪除 version 不會刪掉 issue，issue 一定會留著，只是它們的版本歸屬需要你做決定。Delete 跟 Merge 的差別在這裡：Merge 是把 issue 全部搬到目標版本，Delete 則讓你選擇搬走或斷開關聯。
Release page 上同事看不到「open pull request」的 warnings，但 PM 看得到。
解答
因為同事缺少 View Development Tools 這個 project 權限。release warnings 要出現必須三個條件同時成立：站台已經連接了開發工具（Bitbucket、GitHub 等）、看的人擁有 View Development Tools 權限、而且 warnings 功能沒有被關掉（Work items 區的 ••• 裡由 project admin 設定）。PM 看得到代表前後兩個條件都沒問題，差別就在權限這一項。排查順序建議：先確認同事的權限，再去看 warnings 設定。
Version report 的預測日期明顯太早，PM 說「我們規劃很早但實際兩個月後才開工」。
解答
在這個 version 上補設 Start date。Version report 是用「起點到現在的實際完成速度」來推估 release 日期的；如果沒有設 start date，它會拿版本建立的時間當起點，於是把中間那兩個月完全沒動工的空窗期也算進去，平均速度被稀釋、預測自然失準（通常是預測得過於悲觀或過於樂觀，端看資料分佈）。設定 start date 之後，報表就會從真正開工的那天開始算。
Timeline 上看不到某張 Task，它明明在 sprint 裡。
解答
因為這張 Task 沒有 parent（沒有掛在任何 epic 底下）。在 Show inline hierarchy 開啟的狀態下（這是預設值，也是考試作答的依據），timeline 是以階層方式呈現的：child 縮排在自己的 parent 下方，沒有 parent 的工作就沒有位置可以放，因此不會顯示；sub-task 也同樣不會出現。解法有兩個：把它掛到某個 epic 底下，或是關閉 Show inline hierarchy 切換成平面清單（官方原文說這時會顯示沒有 parent 的工作）。答題時記得預設是開啟。
PM 想在同一張 timeline 看 MOB 與 WEB 兩個 project。
解答
做不到。官方規定一個 timeline 只能顯示一個 project，這是硬性限制，沒有設定可以打開。要在同一個畫面上跨 project 規劃，得用 Plans（需要 Premium 或 Enterprise 方案）——Plans 才是為多團隊、多 project 的長期規劃設計的，還帶有容量規劃、相依性與多情境比較的能力。這也是考題常見的對照：Timeline 是單一 project 的戰術視圖，Plans 是跨 project 的規劃工具。
Kanban project 的 timeline 上 story 沒有長條。
解答
因為 Kanban project 的 child 只能依 Start date 與 Due date 來畫長條，沒有填日期就沒有東西可以畫。這一點與 Scrum 不同：Scrum 的 child 可以依所屬 sprint 的起訖日期自動產生長條，就算沒填日期也看得到。原因很單純——Kanban 沒有 sprint 這個時間框架可以借用。解法是替這些 story 補上 Start date 與 Due date。
Sprint 中途加了兩張 story，主管問「哪裡看得出來是中途加的？」
解答
有三個地方看得出來。第一，Sprint report 會在 sprint 開始後才加入的 issue 旁邊標一個星號「*」，這是最直接的證據。第二，Burnup chart 的紅線（scope 線）會在那一天往上跳一階，視覺上非常明顯。第三，Burndown chart 的剩餘工作線也會往上跳，但要注意guideline 那條斜線不會跟著改變——它反映的永遠是 sprint 開始當下的承諾量，所以圖上會出現實際線跑到 guideline 上方的情況，這正是 scope creep 的樣子。
v2.0 突然多了 10 張 story，主管想知道預計還要幾個 sprint。
解答
看 Release burndown：它以 sprint 為單位畫出這個版本的剩餘工作，新增的範圍會以深色的 scope added 段標示出來，並根據最近幾個 sprint 的 velocity 推估還需要幾個 sprint 才收得完。另一個可以參考的是 Version report 的預測日期線。但有一個前提要先講清楚：如果新加進來的 story 大多沒有估點，這個預測是不可靠的（官方對 Epic burndown 的說法是未估點超過 30% 就別信），所以正確順序是先讓團隊估點，再拿預測去跟主管報告。
常見陷阱

考題喜歡設的誤解

誤解事實
「Affects versions 也會把 issue 放進 release」不會。只有 Fix versions 才會把 issue 納入 version 的範圍；Affects versions 記錄的是「這個問題影響哪些版本」，純供搜尋分類，不影響 release 與報表
「Release 會擋住有未解決 issue 的版本」不會擋。Jira 只會跳出對話框問你這些未解決的 issue 要忽略還是移到另一個 version；真的要擋住 release，得用 release 的 Require approvals 設定
「Merge 之後還能拆回來」不能。Merge 是不可逆的動作，來源 version 會直接消失，issue 的 Fix version 全部改成目標版本；併錯了只能一張張手動改回去
「連了 Bitbucket 就一定看得到 warnings」不一定。warnings 要三個條件同時成立：已連接開發工具、看的人有 View Development Tools 權限、而且 warnings 沒有被 project admin 關掉
「Timeline 可以跨 project」不行。一個 timeline 只顯示一個 project，這是硬性限制；要跨 project 規劃必須用 Plans（Premium／Enterprise）
「Timeline 會顯示所有 issue」預設（inline hierarchy 開）沒有 parent 的 child 不顯示，sub-task 也不顯示；關掉 inline hierarchy 才變平面清單
「Archive 等於刪除」不是。Archive 只是把 version 從報表與欄位下拉裡隱藏起來（也不能再指派新的 issue），資料完好，隨時可以 Unarchive 拿回來
「任何人都能 release」不是。發佈版本需要 project admin 身分，官方列出的權限是 Administer Projects 加上 Manage Versions
「TMP 開了 Releases 就有 Affects versions」只有 Fix versions；Affects Version/s 的官方需求 JRACLOUD-85690 仍未解決（2026-09-08）
「Timeline 可以用 Sprint 篩選」官方內建 filters 清單是 assignee／status／versions／type／label／component／keyword／goals，未列 Sprint
「把 issue type 命名成 Initiative 就會在 Epic 之上」要 Jira admin 建標準 work type、加進 scheme 並關聯到自訂階層層級
實作（40 分鐘）

把一個版本從建立走到封存

  1. 建 v1.0（設 start date 與 release date）、v1.1。在 backlog 的 Versions panel 把 5 張 issue 拖進 v1.0；再對其中一張改用 Fix versions 欄位加入 v1.1，觀察兩種方式等價。
  2. 對一張 bug 只填 Affects versions = v1.0 → 確認 v1.0 的 release page 沒有它。
  3. 留一張 issue 未完成就 Release v1.0 → 選「移到 v1.1」；到 Kanban board 看 Done 卡片消失。
  4. Unrelease → Release → Archive → Unarchive，觀察 Fix version 下拉選單裡 v1.0 的出現與消失。
  5. Merge v1.1 into v2.0，確認 issue 的 Fix version 變成 v2.0、v1.1 消失。
  6. Release page：設定一個 approver 並勾 Require approvals；連接 Bitbucket 後用沒有 View Development Tools 的帳號看 warnings 是否消失。
  7. Timeline：建 epic 掛三張 story 分到三個 sprint，畫一條 dependency；建一張沒有 parent 的 task 確認不出現，再關掉 Show inline hierarchy 看它以平面清單出現；切到 Kanban project 只填 Start／Due date 看長條。
  8. Sprint 中途加兩張 story，開 Sprint report（找星號）、Burnup（紅線跳）、Release burndown（scope added 段）。
  9. 範圍變動的可追蹤練習（A 版 lab）：完成 v1.0 其中一張 Task 後記錄 release progress，再把一張新的 Task 納入 v1.0 → 預期「完成張數不變、總範圍增加」，比例因此下降。
  10. Timeline 練習：切換 Weeks／Months／Quarters 觀察長條，確認這只是觀看尺度，不是把 issue 工期換算成不同承諾。
