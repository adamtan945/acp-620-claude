620.1.2 · Create and configure team-managed projects

建立與設定 team-managed project

這一節要回答三個問題：team-managed project（以下簡稱 TMP）怎麼建、建好之後存取與權限是怎麼運作的、以及怎麼把人加進來。官方在考綱列的四個有效連結，加上 hub 底下的子頁「Create and edit team-managed projects」，我都讀完了；建立流程真正的細節其實藏在那個子頁裡，而不是在 hub 頁上。

術語：考試用 project／issue；現行產品為 space／work item。本教材沿用考試用語。
這一節考什麼

三條 bullet

官方 bullet考點
Understand how to create team-managed projects誰有資格建立（靠一個全域權限）、實際的建立步驟、project key 的命名規則、Details 頁面上哪些欄位改得動，以及 board 和 workflow 綁在一起會產生什麼行為
Understand team-managed project access and permissionsaccess level 和指派的 role 是相加而不是覆蓋、三個內建 role 各自能做什麼、建自訂 role 時可以整包勾的三組權限，以及這些權限在 CMP 那邊叫什麼名字
Understand how to add users to team-managed projects加人有兩個入口、只能加已經在站台上有帳號的人、外部人員要用 guest 的身分、一個人可以同時持有多個 role，以及把人移除時常踩的兩個陷阱

TMP 的 board 和 workflow 是綁在一起的

官方「Get started」花很多篇幅講 board，因為這是 TMP 跟 CMP 最大的操作差異：column ＝ status，一體兩面。自己按按看。

TMP：column ＝ status
  • 在 board 上建一個叫「Review」的 column，Jira 會同時幫你生出一個同名的 status「Review」
  • 把 column 改名，對應的 status 也會跟著改名，兩邊永遠一致
  • 刪掉 column，那個 status 也會一起被刪；如果欄裡還有 issue，Jira 會要你先指定把它們搬到哪一欄
CMP：column 與 status 分開
  • status 定義在 workflow 裡，要改得找 Jira admin
  • column 定義在 board settings 裡，board admin 就能改
  • 一個 column 可以對應好幾個 status；反過來說，沒有被任何 column 對應到的 status，issue 走到那裡就會從 board 上消失

必記規則

規則內容
位置決定類別column 的位置直接決定 status 的類別：最左邊那一欄屬於 To do、最右邊那一欄屬於 Done，夾在中間的全部算 In progress。你搬動 column 的順序，類別就跟著換
最右欄 ＝ resolvedissue 一被拖進最右邊那一欄，就會被標上完成的勾勾並視為已解決，報表與 backlog 也是照這個判定
永遠要有 Done不能刪掉最後一個 Done column；刪含 issue 的 Done 欄，接收的欄會繼承 Done 狀態
Sprints 開著時board 在 sprint 開始前是空的；不能在 board 上直接建 issue，只能在 backlog 建再拉進 sprint；sprint 結束時 Done 的 issue 清掉、不回 backlog
Sprints 關著（Kanban 式）Done 的 issue 14 天後自動清掉；可手動清（僅 project admin／Jira admin）；清 parent 時 sub-task 一起清，不管 sub-task 狀態
Column limit沒有開 Sprints 的 Kanban 式 board 可以替每一欄設卡片數量上限（欄位標題的 ••• → Set column limit），超過時該欄會變色提醒，用來控制同時進行的工作量
Status categoriesTo do／In progress／Done 三類，多個 status 可歸同一類（例：Backlog、Waiting for approval 都是 To do）
考題
看到「TMP 開了 Sprints，成員說 board 上看不到任何 issue」，答案是還沒有開始任何一個 sprint——sprint 沒開始，board 本來就是空的，issue 都待在 backlog。看到「TMP Kanban 的 Done issue 兩週後不見了」，這是正常行為，系統每 14 天會自動清一次；資料沒有消失，用 See all Done issues 就找得回來。
Bullet 2

存取與權限：兩個變數決定一個人能做什麼

圖 2　互動版加總計算器在 620.1.1 的存取等級段落。

被加入 project 時自動獲得的三項

不管給什麼 role，一被加入就有：Browse project View project View issues。所以 TMP 沒有「加了人但他看不到 project」這種狀況（CMP 有，因為 Browse Projects 可能沒給那個 role）。

三個反例（考題最愛）
  • Open ＋ 指派 Viewer ≠ 唯讀：Open 已經給全站 Member，Viewer 只是疊上去，他照樣能編輯。要唯讀得先把 project 改成 Limited。
  • 從 Open 改成 Limited，原本的人不會自動保有 Member：只有被明確加入的人保住原 role，其餘（包含正被指派 issue 的人）掉成 Viewer。想保住核心成員，先把他們明確加為 Member 再改 access level。
  • Viewer 不是純唯讀：Viewer 能留言與加附件。「Limited 之下沒被加入的人能不能留言？」答案是能。

來源：Manage how people access your team-managed space、Team-managed space permissions

高頻考點
CMP 有一個獨立的 Assignable User 權限，可以精準控制「誰可以被指派 issue」；這個權限在 TMP 被簡化掉了，所以你沒辦法單獨控制誰能被指派。TMP 的規則是：只要某個 role 勾了「Work on issues」那一組裡的任何一項權限，持有該 role 的人就會出現在 Assignee 的候選清單裡。

需要 app access 的權限

Viewer 可以給任何站台註冊使用者，不需要 Jira 授權席次。但 Member／Administrator 的多數權限需要 Jira app access——沒有席次的人即使給了 Member，功能也用不全。席次只有 site admin 能給。

考題
「加了一個人為 Member，他能看但不能編輯」→ 他沒有 Jira app access（授權席次），找 site admin。

Bullet 3

怎麼加人

圖 3　兩個入口匯合到同一個「加人」對話框，之後流程相同。
規則內容
能加誰只能加已經在這個 Atlassian 站台裡有帳號的人。如果在搜尋框裡打了名字卻找不到人，代表他還沒被邀請進站台，要先請 Jira admin 邀請，之後才加得進 project
外部協作者請 admin 邀請為 guest（限單一 project、不佔正式席次）
可加群組可以，整個 group 拿同一個 role
多重 role一個人或 group 可同時有多個 role
疊加原則Access 頁指派的 role 不覆蓋 access level 給的 role，是加上去
Role 的兩種用途（官方）官方講了兩個：第一，補上 access level 沒有給到的權限；第二，讓核心成員即使日後 project 的 access level 被調整，也還保有穩定的權限不會被降級

第二個用途值得記：把核心團隊明確加為 Member，之後就算 project 從 Open 改成 Limited，他們仍是 Member；沒被明確加的人則降成 Viewer。

移除人的兩個陷阱

  1. 如果你曾把全站 group 加進某個 role，被移除的人可能仍透過 group 有權限——要跟 Jira admin 確認 group 成員。
  2. 從 project 移除 ≠ 從 Jira 移除；後者只有 Jira admin／site admin 在 user management 做。
把三個 bullet 串起來

Acme 新成立「Data Platform」團隊，工程師小林要自己開 project

  1. 小林點 Projects → 看得到 Create project → 有權限（Create TMP 全域權限）
  2. Scrum template → Select a team-managed project → Name「Data Platform」，key 自動「DP」→ Next
  3. Details：category 選 Jira admin 建好的「Engineering」；default assignee 設自己
  4. Access：改成 Limited（全公司可看可留言，不能亂改）
  5. Add people：三個工程師 → Member（明確加，之後 level 變動也不掉權限）；資料分析師阿芳 → 複製 Member 改成「Analyst」，拿掉 Manage sprints；外包 Kevin → 請 admin 邀成 guest，加為自訂 role「Contractor」，只勾 Collaborate 包 ＋ Create issues
  6. Sprints 開著 → 提醒團隊：board 在第一個 sprint 開始前是空的，issue 要在 backlog 建
阿芳說她看得到 issue 但拖不動、改不了
這是典型的授權席次問題，不是 role 設錯。檢查 site admin 有沒有給她 Jira app access——沒有席次的人就算掛著 Member，也只能看不能動。
Kevin 可以被指派 issue，但小林沒給他 Work on 的權限
回頭檢查那個自訂 role 是不是勾到了「Work on issues」群組裡的任何一項（例如看似無害的 Log work）。TMP 沒有獨立的 Assignable User 權限，只要勾中其中一項，這個人就會出現在指派清單裡。
自測

13 題

使用者說「我沒有 Create project 按鈕」，TMP 的情況下該查什麼？
解答
先查全域權限 Create team-managed projects 有沒有被 Jira admin 從他所屬的群組移除。這是一個站台層級的全域權限，不是 project 裡的設定，所以就算他在別的 project 是 admin 也沒用。Jira admin 常會為了控管 project 數量而收回這個權限，收回之後使用者的 Projects 選單裡就不會出現 Create project 這個按鈕——不是壞掉，是被關掉了。
TMP 的 key 規則有哪三條？改 key 後多久生效？
解答
三條規則是：至少 2 個字元、必須以大寫字母開頭、只能包含大寫字母與數字。改完 key 之後，board 上要最多 10 分鐘才會反映新的 key，這段時間看到舊 key 是正常的。另外舊 key 會被收進 Previous keys 清單，雖然可以刪掉，但刪了以後所有引用舊 key 的連結就會失效，建議留著。
Private project 的名稱，Jira admin 看得到嗎？官方建議？
解答
看得到。Private 擋的是一般使用者，不是站台管理員——Jira admin 永遠看得到站台上所有 project 的名稱，也進得了它的 project settings。所以如果專案名稱本身就是機密（例如「Acme 併購案」），把 project 設成 Private 並不能保護它。官方的建議是直接用代號（codename）當 project 名稱，讓名字本身不洩漏資訊。
Sprints 開著時，能在 board 上直接建 issue 嗎？
解答
不能。開了 Sprints 之後，board 只顯示「目前進行中的 sprint」裡的 issue，所以它不提供在 board 上直接建立 issue 的入口。正確流程是先在 backlog 建立 issue，再把它拉進 sprint。這也是為什麼第一個 sprint 還沒開始時，board 看起來完全空白——不是資料掉了，是還沒有任何 sprint 在跑。
Kanban 式 TMP 的 Done issue 多久清一次？誰能手動清？
解答
系統每 14 天自動清一次，把 Done 的 issue 從 board 上移走。想提前清，project admin 與 Jira admin 可以手動執行。要注意這只有在 Sprints 關閉（也就是跑 Kanban 式）時才適用；開了 Sprints 的 board 是靠結束 sprint 來清，沒有手動清除這個選項。被清掉的 issue 只是不顯示在 board 上，資料還在，用 See all Done issues 就找得回來。
被加入 TMP 時自動獲得哪三項權限？
解答
Browse project、View project、View issues 這三項。只要被加進 TMP，不管給的是哪一個 role，這三項都自動具備。所以 TMP 不會出現「人加進來了卻看不到這個 project」的狀況——那是 CMP 才有的問題，因為 CMP 的 Browse Projects 權限可能根本沒給那個 role。
Member 有沒有 Manage sprints？有沒有 Edit reporters？
解答
Member 有 Manage sprints，沒有 Edit reporters（改 reporter 是 Administrator 才能做的）。這題考的是一個容易搞混的地方：Manage sprints、Edit any due date、Access development tools 這三項雖然被官方歸在「Manage issues」這個權限群組底下，但 Member 就已經具備了，不必是 Administrator。剩下那些真正屬於管理層級的（刪別人的東西、改 reporter、管 watchers）才是 Administrator 專屬。
TMP 的 Transition any issue 對應 CMP 哪三個權限？
解答
對應 CMP 的 Transition Issues、Resolve Issues、Close Issues 三個權限。TMP 把它們合併成一項，好處是設定簡單，代價是失去顆粒度——在 CMP 你可以讓某個 role 只能轉狀態卻不能關單，在 TMP 做不到，給了就是三件事一起給。
TMP 怎麼決定誰可以被指派？
解答
TMP 沒有像 CMP 那樣獨立的 Assignable User 權限。它的判定規則是：只要某個 role 勾了「Work on issues」這一組裡的任何一項權限（例如 Create issues、Log work、Edit any issue…），持有該 role 的人就會出現在 Assignee 下拉清單裡。這常讓人踩雷——你只是想讓外包廠商能記錄工時，結果他就變成可被指派的對象了。
內建的 Viewer／Member／Administrator 能編輯嗎？能刪嗎？
解答
三個內建 role 既不能編輯也不能刪除，Jira 要保證每個站台的 Viewer／Member／Administrator 意義一致。想要一個「像 Member 但不能管 sprint」的角色，做法是到 Manage roles 按 Duplicate 複製一份，再在複製出來的自訂 role 上調整勾選。
刪除自訂 role 會影響哪兩件事？會把人移出 project 嗎？
解答
會影響兩件事：notifications（通知設定裡若指定通知這個 role，就會失效）與 issue type restrictions（限制某些 issue type 只有特定 role 能用的設定也會失效）。但不會把人踢出 project——人還在成員名單上，只是少了這個 role 帶來的權限。
加人時找不到某位同事，原因？外部人員怎麼辦？
解答
原因是他還沒有這個 Atlassian 站台的帳號。Add people 的搜尋框只找得到站台上已存在的使用者，不能直接用 email 把外面的人拉進來，所以要先請 Jira admin 在使用者管理那邊邀請他進站台。如果對方是外部的協作者（廠商、客戶），請 admin 邀請成 guest：guest 只能存取被指定的那一個 project，也不佔用正式的授權席次。
Open project 裡明確把某人加為 Viewer，他能編輯 issue 嗎？
解答
能編輯，這是最常考的反直覺題。因為 access level 設成 Open 時，全站使用者已經自動拿到 Member；你另外指派的 Viewer 是疊加上去，不是覆蓋下來，兩者取聯集之後他仍然保有 Member 的全部能力。想真正把某個人限制成唯讀，順序要反過來：先把 project 的 access level 降成 Limited（或 Private），再用 role 一項一項往上加。要限制先改成 Limited。
常見陷阱

考題喜歡設的誤解

誤解事實
「把人指派成 Viewer 就變唯讀」Open 之下他仍是 Member；role 是疊加，不會降權
「Private project 連 Jira admin 都看不到」Jira admin 永遠看得到 project 名稱，也進得了 project settings；敏感專案要用代號命名
「加成 Member 就一定能編輯」還要有 Jira app access（授權席次），否則只能看
「刪掉自訂 role，那些人就離開 project 了」不會；人還在，只是少了該 role 的權限，另會影響 notifications 與 issue type restrictions
「TMP 可以指定誰能被指派」沒有獨立的 Assignable User；有 Work on issues 群組任一項權限就可被指派
「TMP 的自訂欄位別的 project 也能用」只屬於這個 project；同名欄位是兩個物件
「TMP 想加幾種 work type 都可以」上限 30 個，而且只能自訂 standard 層
「把人從 project 移除＝他在 Jira 沒帳號了」兩回事；他可能還透過 group 有權限，移除站台帳號是 Jira／site admin 的事
實作（25 分鐘）

用第二個帳號，把六種組合各看一次

建一個測試 TMP，準備第二個帳號（測試帳號或請同事幫忙）。每一步都用第二個帳號實際開 project，確認「看得到什麼、能做什麼」。

#設定第二個帳號應該看到的結果
AAccess ＝ Open，不加任何人找得到 project、能編輯 issue（全站預設 Member）
BOpen ＋ 明確指派 Viewer仍然能編輯——role 疊加，不會降權
C改成 Limited，不加人看得到、能留言與加附件，但不能編輯
DLimited ＋ 明確加為 Member能編輯；之後 access level 再變也保得住
E改成 Private（保留 D 的指派）D 的人仍進得去；沒被加的人搜不到也進不去
FManage roles → Duplicate Member → 自訂 role（只留 View、Comment）→ 指派驗證自訂 role 生效；同時確認內建三個 role 不能編輯也不能刪

「他為什麼不能做 X」的排查順序

  1. 他在站台上有帳號嗎？（Add people 搜不到人＝還沒被邀請進站台）
  2. 他是不是 Jira admin？（是的話權限來自全域，不受 access level 影響）
  3. project 的 access level 是什麼？（決定他的預設 role）
  4. 他有沒有被明確指派 role？（記得是疊加，不是覆蓋）
  5. 他是不是透過 group 拿到 role？（移除個人不會拿掉 group 給的）
  6. 他有 Jira app access（授權席次）嗎？（看得到但不能編輯，多半是這一項）
  7. 站台方案限制？（Free 不能編輯 permissions／roles）
  8. 該 issue 有沒有 issue type restriction 或留言可見度限制？
