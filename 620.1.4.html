620.1.4 · Describe how to manage general project configurations

管理 project 的一般設定：details、sidebar、categories、trash

這一節是 domain 1 的收尾，考的是 project admin 日常會碰的四件事：改 details（尤其是改 key 的後果）、整理 sidebar、用 category 分群、把 project 丟進 trash。內容不多，但「改了會怎樣」「誰能做」兩類細節是送分題，也是失分題。

術語：考試用 project／issue；現行產品為 space／work item，「project sidebar」現行已改為橫向的 space navigation tabs。本教材沿用考試用語，並標出現行差異。

寫 Project admin 的意思是「只要有 Administer Projects 就改得動」，不是「只有 project admin 才能改」——Jira admin（Administer Jira）自動涵蓋站台上每一個 project 的管理權，所以這些欄位他當然也改得了，site 與 org admin 同理。
整張表唯一真正排他的是 Key：那一列反過來，project admin 就是不行（CMP），必須由 org／site／Jira admin 出手。
欄位用途最低需要的權限改了會怎樣

另外要記得 project name 全站唯一，而且 Jira admin 永遠看得到所有 project 的名稱，連 Private 的也一樣——所以敏感專案官方建議用代號命名

TMP：project admin 自己就能改（實機驗證 2026-09-09）。

兩個常被弄錯的限制
  • Default assignee 不是任意 user picker，只有 Unassigned／Project lead 兩個選項。若改不了，檢查 ⚙ General configuration 的「Allow unassigned issues」。
  • Software ↔ Business project 不能直接轉換；只能建新 project 再把 issue 搬過去。
三個都跟「網址／識別」有關，但出現的地方完全不同

這三個欄位很容易混在一起，記法是各自問「填了之後，我在哪裡會看到它？」

欄位填的是什麼填了之後在哪裡看得到
Key這個 project 自己的識別碼無所不在——每張 issue 的編號前綴（MOB-12）、issue 的網址、JQL、board filter、Confluence 的 Jira macro 全都靠它。這也是為什麼改它要這麼謹慎
URL一個外部網址（Confluence space、roadmap、規格文件…）只在站台的 project（Spaces）目錄那一頁——就是你從左上角 Projects → View all projects 進去的那個清單。進到 project 內部之後就看不到它了，issue 上更不會出現。所以它的用途很單純：讓在專案目錄裡瀏覽的人，能一鍵跳到這個團隊的文件
Description給管理員看的專案摘要官方原句只有一句：Administrators can view the description in the Summary section of your space’s settings.——沒有附任何截圖或路徑。
⚠️ 2026-09-09 實際在站台上找過，找不到這個顯示位置。
兩件事要分清楚：官方說的是 Project settings 裡的 Summary，不是 project 側欄那個儀表板式的 Summary 頁（後者顯示近 7 天完成張數與狀態圖表，跟 description 無關）。但即使找對地方，目前也沒看到它。務實建議：不要把 Description 當成「會被誰看到」的欄位——需要讓團隊看到的說明放 Confluence，或用 URL 欄位指過去。

URL 與 Description 都只有 CMP 有；TMP 的 Details 只有 Avatar、Name、Key、Category、Access（想要 TMP 的 description，官方需求 JSWCLOUD-17584 至今仍是 Gathering Interest）。
另外要分清楚：URL 欄位不會改變這個 project 的網址（那由 key 決定），更不是站台網址（站台網址要在 admin.atlassian.com 用 Update URL 改）。

找不到這兩個欄位的顯示位置？先確認三件事
  1. 你在的是 CMP 嗎——TMP 根本沒有 URL 與 Description 這兩個欄位，Details 頁上不會出現。
  2. 你找的是正確的 Summary 嗎——官方指的是 Project settings 裡的 Summary，不是 project 側欄那個儀表板式的 Summary 頁。
  3. 官方對這兩個欄位的著墨都極少：URL 只寫了「顯示在 Spaces 目錄」，Description 只寫了「管理員可在 settings 的 Summary 看到」，都沒有附畫面。介面改版時這類低調欄位的位置很容易悄悄變動，遇到對不上時以站台實際畫面為準，不要硬套文件。

證據界線：改 key 要什麼權限，兩篇官方寫得不一樣
  • Edit a space’s details（考綱連結那篇）原句：Only organization, site, and Jira admins can edit a space key.——講得非常死，而且沒有區分 company-managed 或 team-managed，等於一律排除 project admin。
  • Create, edit, and delete team-managed spaces 講同一件事時卻寫：If you have space permissions, this is how to change the space’s key——「space permissions」在 TMP 的語境裡就是 project admin（Administrator role／Administer spaces），並沒有把 key 拉出來另外限制。兩篇皆為 2026-09-09 查核。
  • 實機驗證定案（2026-09-09）：用「只有 project admin、沒有 Jira admin」的帳號實測，TMP 改得動 key，CMP 改不動。所以兩篇文件其實都沒寫錯，各自只描述了自己那一半——考綱那篇講的是 CMP 的行為，TMP 那篇講的是 TMP 的行為。

作答一律以考綱連結那篇為準：改 key ＝ 需要 org／site／Jira admin，project admin 做不到。考題最愛的長相就是「project admin 想改 key，卻發現欄位是灰的」，答案永遠是權限不足。

實務上則照實測走：TMP 的 project admin 自己改得動 key，CMP 的 project admin 只能開單請 Jira admin。這其實很符合兩種 project 的一貫分工——TMP 的設定長在 project 裡、project admin 全權；CMP 的設定是站台層物件、動它就要 Jira admin。key 只是又一個例子。

另外兩個順帶要記的：建立 project 時 key 是 Jira 自動產生的（你不必自己想），而建立者預設成為 project owner。

考題長相
「Project admin 想改 key 卻找不到欄位可編輯」→ 改 key 需要 org／site／Jira admin。「改 key 後舊連結壞了嗎？」→ 沒壞，alias 會導向；「什麼情況會壞？」→ 刪除 previous key。
Project sidebar（現行：space navigation）

側欄上有什麼，由「開了哪些 features」決定

考試年代（2023）

左側 sidebar 列出 Board、Backlog、Reports、Releases、Components、Issues、Project pages、Add shortcut…。

  • CMP：項目對應 project 的 features；Releases 對應 versions、Components 對應 components
  • TMP：Project settings → Features 開關（Backlog、Sprints、Releases、Reports…），關掉就從 sidebar 消失
  • Add shortcut：project admin 可加外部連結（例如 Confluence space）
現行（2026）

Project 導覽改成頁面上方的橫向 tabs，概念相同、多了幾個可調項。

  • Project admin 或 board admin 可以：設預設 tab、改名、移除、還原、排序（拖曳或 More actions → Move tab left／right）
  • 加 tab：導覽列的 + → Add to navigation
  • 限制：永遠要有一個 default tab；List 與 Apps tab 不能移除
  • 能出現哪些 tab 取決於：project 類型（software／business）、管理方式（CMP／TMP）、開啟的 features
  • 改動對所有有權進入 project 的人生效

Navigation tabs 能做的五件事（現行）

動作誰規則／限制
Set as defaultProject admin 或 board admin進 project 時預設打開的 tab；永遠要留一個 default，default tab 不能被移除
Rename同上只改顯示名稱，不影響底層 feature 是否開啟
Move left／right同上拖曳或 More actions → Move tab left／right；改動對所有能進 project 的人生效
Remove／還原同上List 與 Apps tab 不能移除；移除過的 tab 之後可用導覽列的 + → Add to navigation 加回來
加 shortcut（外部連結）Project admin（部分站台設定另需 Jira admin）要填完整 URI（含 https://）；只填網域或相對路徑不會生效
兩個年代共同的考點
sidebar／navigation 是「呈現層」：想讓 Releases 出現，先確認 project 有 versions（CMP）或 Releases feature 開著（TMP）；想讓某項目消失，是 project admin 的事，不用 Jira admin。
Project categories

Jira admin 建、project 挑、JQL 用

圖 1　category 是「貼在 project 上的標籤」，用途是跨 project 的搜尋、filter、report、目錄篩選；它不是 parent project。
動作誰路徑
建立 categoryJira admin⚙ Settings → Projects → Project categories → 輸入名稱與描述 → Add
指派給 projectTMP：project admin；CMP：details 頁寫「contact a Jira admin」（categories 頁的步驟則未區分）。考試作答：Jira admin 建、在 Project settings → Details 指派••• → Project settings → Details → Category 下拉 → Save details
刪除 categoryJira admin⚙ Settings → Projects → Project categories → Delete（被指派的 project 變成無 category，project 本身不受影響）
使用任何人JQL category = "X"、saved filter、dashboard gadget、Projects 目錄篩選
考題長相
「想把 5 個 project 分成一組做 dashboard」→ category + category = "X"。「想用 category 做 parent／child project」→ 不行，官方明講 category 不能做階層；要階層用 Plans（Premium）或 epic 跨 project。
Trash

60 天內可還原，之後永久刪除

圖 2　Trash 是「暫停」不是「刪除」；還原後 project 回到目錄、issue 回到搜尋結果。
動作誰能做路徑／備註
Move to trashAdminister Jira 全域權限，或該 project 的 Administer Projects（官方 Move a space to trash 頁原文：「the Administer Jira global permission or … the permission to administer spaces」）；TMP 的 Administrator role 也含此權限⚙ → Projects（或 Manage projects）→ ••• → Move to trash → Move；project admin 也可從 Project settings → Details 進入
RestoreAdminister Jira⚙ → Projects → Trash → ••• → Restore；legacy 的無效 epic-link 關係不會被恢復
Delete permanentlyAdminister Jira⚙ → Projects → Trash → ••• → Delete permanently；必須先在 trash 裡，不能直接刪
Trash 期間—issue、components、attachments、versions 一起進 trash；issue 從基本／進階搜尋消失，直連可讀不可編；project 從目錄消失；admin 可看到誰、何時丟的、何時會被永久刪
不受影響—scheme、workflow、issue type 以及與其他 project 共用的設定都不受影響，它們是站台層級的物件，不會跟著 project 進 trash

Trash 與 Archive 不是同一件事

面向TrashArchive（封存）
方案所有方案都有，Free 也不例外只有 Premium／Enterprise 能封存；之後降到 Standard 仍可存取與還原已封存的 project，但不能再封存新的
誰能做Move to trash：Administer Jira 或該 project 的 Administer Projects；Restore／永久刪除：Administer JiraJira／site admin 可封存與還原 CMP 與 TMP；project admin 只能封存 TMP
期限60 天後自動永久刪除；期限內有 Administer Jira 的人也可以提早手動刪掉沒有期限，不會被自動刪除
一起被處理的資料issue、components、attachments、versions同樣是 issue、components、attachments、versions；不影響 scheme、workflow、issue type 與跟別的 project 共用的設定
還看得到嗎搜尋看不到；拿到直接連結的人可以讀，但不能編輯一樣搜尋看不到、直連可讀不可編；封存前就有權限的人仍可透過 API 讀到 project 細節，要真的擋掉必須封存前先改權限
兩個容易被考的細節
  • 60 天不是保證：期限內任何有 Administer Jira 的人都可以直接 Delete permanently。「還在 trash 就一定救得回來」是錯的。
  • 還原不會修好 legacy 的 epic-link：project 若有無效的 epic-link 關係，trash 還原與 archive 還原都不會把這些連結恢復。

來源：Archive a space

證據界線：project admin 到底能不能把 CMP 丟進 trash
  • Move a space to trash（考綱路徑）寫的是「the Administer Jira global permission or … the permission to administer spaces」，沒有限定 project 類型——本教材以此為準。
  • Archive a space 則寫 project admin 只能封存 team-managed space，並補一句「同樣的規則也適用於把 project 移到 trash 與還原」。

兩篇不一致。作答原則：題目問「誰能把 project 丟進 trash」→ Administer Jira 或 Administer Projects；題目明確在講 archive → project admin 只能封存 TMP。Restore 與永久刪除兩篇一致，都是 Administer Jira。

「不見了」的三種排查

現象最可能的原因怎麼確認
board 上少了幾張，但搜尋找得到board filter／quick filter 篩掉了；TMP Kanban 的 Done 會在 14 天後自動從 board 清掉看 board 的 filter query；用 See all done issues
整批 issue 從搜尋消失，直連還打得開但不能編整個 project 進了 Trash 或被 Archive⚙ → Projects → Trash／Archive 找 project 名稱，順便看是誰、什麼時候做的
issue 還在，只是不出現在 Releases 清單version 被封存（version 層級，不是 project 層級）Project settings → Releases → 顯示已封存的版本
官方的替代建議
之後可能還會用到的 project，官方建議archive（Premium）或 hide，而不是進 trash 等 60 天。Data Center 遷移到 Cloud 時，重新遷移前要先把 trash 裡的同名 project 永久刪除。

Project admin 小美想把 project key 從 MOB 改成 APP，Details 頁的 key 欄位是灰的。為什麼？
解答
因為改 project key 需要 org、site 或 Jira admin 等級的權限，一般的 project admin 沒有這個資格，所以欄位會呈現灰色不可編輯。這個設計是刻意的：key 是每張 issue 編號的前綴，改動會牽動全站的連結、filter 與 JQL，所以 Atlassian 把它收在站台管理員手上。小美要做的是把需求交給 Jira admin，而不是在 project settings 裡找別的入口。
Key 改成 APP 後，同事留言裡的 MOB-12 連結還能點嗎？
解答
能點，而且會正確導向。Jira 在改 key 時會把舊的 MOB 自動存進 Previous keys，並建立一個 alias（別名）；任何人點到 MOB-12 都會被導向 APP-12。要注意的是連結上的文字不會被改寫——留言裡看到的仍然是「MOB-12」這幾個字，只是點下去會到新的地方，所以團隊初期會有一段時間新舊 key 混著出現，這是正常的。
改 key 之後，Jira admin 還應該提醒團隊做什麼？
解答
雖然舊 key 靠 alias 仍然能動，官方還是建議把 board filter、dashboard 的 filter gadget、以及各種全域 JQL 查詢都更新成新的 key，讓設定與現況一致，避免日後有人看到舊 key 一頭霧水。另外在動手改之前應該先備份站台——這是官方對所有重大變更的一貫建議。
公司想把舊 key MOB 拿給一個全新的 project 用，該怎麼做、有什麼風險？
解答
做法是到原 project 的 Details → Previous keys 把 MOB 這筆刪掉（一樣需要 org／site／Jira admin），舊 key 釋放出來之後才能給新 project 使用。風險相當高：一旦刪除，支撐舊連結的 alias 就消失了，所有還在引用 MOB 的連結、board filter、dashboard gadget 與 JQL 全部會失效，而且無法自動修復。所以標準做法是先公告、先確認沒有人還在用舊 key，再刪。
Default assignee 想設成 QA 小傑，但下拉只有 Unassigned 和小美。怎麼辦？
解答
因為 Default assignee 不是一個可以自由挑人的 user picker，它的下拉永遠只有兩個選項：Unassigned，或是這個 project 的 Project lead（owner）。所以看到「只有 Unassigned 和小美」是正常的——小美就是現任 lead。想讓新 issue 預設指派給小傑，唯一的路是先把 Project lead 改成小傑，下拉裡才會出現他。順帶一提，如果連 Unassigned 都選不到，那是站台的 ⚙ → General configuration 把「Allow unassigned issues」關掉了。
想把 6 個 project 的 issue 放在同一個 dashboard 看，且不想一個一個列 project key。
解答
用 project category。先請 Jira admin 到 ⚙ → Projects → Project categories 建一個分類，再到每個 project 的 Project settings → Details 把它指派上去；之後用 JQL category = "X" 建一個 saved filter，拿這個 filter 去餵 dashboard gadget 就好。這樣做的好處是之後增減 project 不必回頭改 filter——新 project 只要指派同一個 category 就自動被納入，比手動列出六個 project key 好維護得多。
PM 想用 category 做「母 project 底下有子 project」的結構。
解答
做不到。官方文件明講 category 不支援階層，它本質上只是貼在 project 上的一個標籤，用來在目錄裡篩選與分群，沒有母子關係的概念。真的需要跨 project 的階層，有兩條路：用 Premium 方案的 Plans（可以在 epic 之上再疊層級），或是利用 CMP 的 epic 可以收別的 project 的 issue 當 child 這個特性，做出跨 project 的工作階層。
Project admin 想把自己的 project 丟進 trash，需要找 Jira admin 嗎？之後想還原呢？
解答
丟進 trash 不用：官方寫 Administer Jira 或 Administer Projects 都可以。但 Restore 與 Delete permanently 只有 Administer Jira，這時才要找 Jira admin。
Project 進 trash 後，有人用 JQL 搜還找得到裡面的 issue 嗎？拿到直連呢？
解答
搜尋找不到——不論基本搜尋還是 JQL 進階搜尋，trash 裡的 issue 都不會出現在結果中，project 也會從目錄消失。但如果有人手上握有直接連結，還是打得開來看，只是不能編輯。這 60 天內 Jira admin 可以隨時把整個 project 還原回來，附帶的 issue、components、attachments、versions 都會一起回來。
Jira admin 想直接永久刪除一個 project，找不到 Delete 按鈕。
解答
因為 Jira 不提供一步到位的永久刪除，一定要走兩段：先 Move to trash，再到 ⚙ → Projects → Trash 找到那個 project，從 ••• 選 Delete permanently。這個設計是為了給誤刪一個緩衝。反過來說也要提醒：東西進了 trash 不代表 60 天內一定安全，任何有 Administer Jira 的人都能在期限內提前永久刪除。
Project admin 想讓 Releases tab 出現在 project 導覽上，但找不到。
解答
要記住 sidebar／導覽是呈現層，它上面有什麼，取決於底層開了哪些 features，而不是導覽本身壞掉。TMP 的做法是到 Project settings → Features 把 Releases 打開；CMP 則要確認這個 project 真的有 versions（導覽上的 Releases 對應的就是 versions 功能）。底層條件滿足之後，導覽的增減、排序、改名、設 default，project admin 或 board admin 自己就能做，不必找 Jira admin。

考題喜歡設的誤解

誤解事實
「改 key 會讓舊連結全部失效」不會。舊 key 會被存成 previous key，靠 alias 把舊連結導向新的 issue；真正會讓連結失效的是之後把 previous key 刪掉
「Project admin 可以改 key」改 key 需要 org、site 或 Jira admin；project admin 看到的是灰色不可編輯的欄位
「Default assignee 可以指定任何成員」只有 Unassigned 或 Project lead／owner（官方原句 the default assignee can only be either Unassigned, or the Space owner，2026-09-08）
「Project admin 可以建 category」category 是站台層級的物件，只有 Jira admin 建得出來；project 這邊只能從既有清單裡挑一個來指派
「Category 可以做 parent project」官方明確說 category 不支援階層，它只是分群用的標籤；要階層得用 Plans 或跨 project 的 epic
「Project admin 丟了 project 也能自己還原」丟 trash：Administer Jira 或 Administer Projects 都可；Restore／Delete permanently 只有 Administer Jira
「Trash 裡的 issue 完全看不到」搜尋（含 JQL）看不到，但拿到直接連結的人仍打得開來讀，只是不能編輯
「Trash 會連 scheme 一起清掉」不會。scheme、workflow、issue type 這些站台層級的設定完全不受影響，被丟進 trash 的只有 project 與它的 issue、components、attachments、versions
「Software project 可以改成 Business project」不能直接轉換，Jira 沒有這個按鈕；只能建一個新的 Business project，再把 issue 用 bulk move 搬過去
「Archive 和 Trash 差不多」Archive 沒有期限、要 Premium／Enterprise；Trash 60 天後永久刪除，所有方案都有
「進了 trash 的 project，60 天內一定救得回來」不一定。60 天只是自動刪除的上限，期限內任何持有 Administer Jira 的人都可以直接執行 Delete permanently，一旦刪掉就救不回來
「Project admin 可以封存任何 project」project admin 只能封存 TMP；CMP 要 Jira／site admin
「封存後別人就完全存取不到了」封存前有權限的人仍可透過 API 讀到細節；要擋掉必須封存前先改權限
「navigation 上的 tab 都能移除」List 與 Apps 不能移除，而且一定要留一個 default tab
「加 shortcut 時填網域就好」不行，必須填完整的 URI（含 https://）；只填網域或相對路徑不會生效
實作（20 分鐘）

在試用站台走一遍

  1. 用 project admin 帳號開 Details：確認 key 欄位不可編輯、Default assignee 只有兩個選項、URL 欄位只在 CMP 出現。
  2. 用 Jira admin 改一個測試 project 的 key（先在 issue 留言貼舊 key 連結）：改完點舊連結，確認導向新 key；看 Details 的 Previous keys。
  3. 刪掉 previous key，再點同一個連結，觀察失效；把 key 改回去。
  4. ⚙ → Projects → Project categories 建「Lab」，指派給兩個 project，用 category = "Lab" 搜尋。
  5. 用 project admin 帳號把測試 project 丟進 trash：搜尋看不到 issue、直連可讀不可編；同一帳號到 ⚙ → Projects → Trash 確認沒有 Restore 權限；換 Jira admin 帳號看誰丟的、何時永久刪，Restore 回來。
  6. 在 project 導覽按 +，加一個 tab、改名、設為 default、再移除；試著移除 List tab 確認不行。
  7. （Premium／Enterprise）把另一個測試 project Archive：
    預期：搜尋找不到它的 issue、直連仍可讀不可編、⚙ → Projects → Archive 看得到誰封存與何時封存；再 Restore 回來。跟 trash 的差別是沒有 60 天倒數。
  8. 用 project admin 帳號分別對一個 CMP 與一個 TMP 按 Archive，記錄哪一個做得到。
    預期：只有 TMP 做得到，對應官方「project admin 只能封存 team-managed space」。
