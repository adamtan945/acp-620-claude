620.1 Project Creation（13%）

1.1 選 project type：CMP vs TMP

選 project type：先問要不要跨 project 共用設定，再問團隊要不要自己管。
面向 Company-managed Team-managed
誰建 Jira admin（Administer Jira） 任何人（Create team-managed projects 全域權限）
設定 scheme（workflow / issue type / field / screen / permission / notification）可共用 每個 project 獨立，project admin 全權
權限 permission scheme，39 項細顆粒 3 個內建 role + 自訂 role；Open / Limited / Private
Board 可多個 board、跨 project board 一個 project 一個 board（要更多需用 saved filter 建）
Components 有 無
Issue security 有 無（用 issue type 限制 + Private 替代）
匿名存取 可（Browse Projects 給 Public） 不可
共用設定 建 project 時可「share settings with existing project」 不可
Kanban 清 Done 手動 Release 或 sub-filter 自動每 14 天清除

Template：Scrum / Kanban（另有 Bug tracking 等 business 類）。Scrum 有 sprint、backlog；Kanban 連續流。

共用設定的優缺點：建 CMP 時選「Share settings with an existing project」→ 用同一組 scheme。優點：一致、Jira admin 改一次全套生效；限制：任何一個 project 想改 workflow 就會影響所有共用者（改前要先 copy scheme）。

1.2 建立與設定 TMP

  • 建立：Projects → Create project → Team-managed → 選 Scrum / Kanban template。
  • 可開關的 features：Backlog、Sprints、Estimation、Releases & versions、Reports、On-call。
  • 注意：開了 Sprints，board 在 sprint 開始前是空的（issue 都在 backlog）。
  • Board 必須永遠有一個 Done 狀態欄。

存取等級（必考）：

Access 全站使用者自動拿到 能做
Open Member 看、建、編
Limited Viewer 看、留言；不能建、編
Private 無 只有 Jira admin 與明確加入者；目錄與搜尋看不到
  • 三個內建 role：Administrator（改設定、加 admin、管 feature、改 issue type、board rules）、Member（建、編、留言、轉狀態）、Viewer（只看、留言）。內建 role 不能改，只能複製成自訂 role。
  • 加人：Project settings → Access → Add people（可加 user 或 group）；也可從 Share 加。人可以同時有多個 role；指派的 role 疊加在 access level 之上。
  • 移除人只是移出 project，不是刪帳號。
  • 外部人員 → 請 admin 邀請為 guest。
  • Free 方案不能改 permission / role。

1.3 CMP 的 issue type 設計

CMP 預設三層：Epic → Story／Task／Bug → Sub-task。
  • 三層是預設；Premium 以上可加更多層級（Initiative 等）。
  • Sub-task 全站開關：⚙ → Issues → Sub-tasks；要停用得先把既有 sub-task 轉成 standard 類型。
  • Sub-task blocking condition：workflow transition 上的 condition，父項要等 sub-task 到指定狀態才能轉。
  • 一個 parent 最多顯示 500 個 child；超過就看不到、且 sub-task 不再納入 time tracking 彙總。
  • Sub-task 的 story points 不計入 burndown / velocity（只算 parent）。
  • Issue type scheme 決定哪些 type 出現在哪個 project（Jira admin）。

1.4 Project details 與 sidebar

欄位 備註
Name 出現在搜尋、目錄、切換器
Key 改 key 是大事（見下）
URL 外部文件連結
Avatar / Description —
Category 由 Jira admin 建（⚙ → Projects → Project categories）；project admin 只能挑；不能做階層；可用於 JQL category = "X"、filters、reports
Project lead 通常是 admin
Default assignee 只能選 Unassigned 或 Project lead；要指派別人就先換 lead

改 project key 前要想到：先備份；舊 key 除非刪 project 否則不能再用；舊連結透過 alias 仍有效；Confluence macro 仍可用（可能快取延遲）；board filter 與 dashboard 的 JQL 要更新；要通知使用者。

Trash：project 進垃圾桶 60 天後永久刪除；issue 從搜尋消失但直連仍可讀（不可編）；scheme / workflow 不受影響。丟進 trash 需 Administer Jira 或該 project 的 Administer Projects（CMP、TMP 都一樣）；Restore／永久刪除只有 Administer Jira。

620.2 Board Configuration（29%，最大 domain）

2.1 三種 board

ScrumKanbanKanban with backlog
節奏sprint ＋ backlog連續流，沒有 sprintKanban 加一個獨立的 backlog 畫面
重點估點、velocityWIP limit（column constraint）把某個 status 放進 Kanban backlog 欄，這些 issue 不佔 board
主要報表Burndown、Sprint reportControl chart、CFD同 Kanban
清掉 Done完成 sprintCMP：Release 或 Hide completed；TMP：14 天自動清同 Kanban
  • Board 是「戰術」視圖（未來一兩週）；Timeline 是長期規劃。
  • Board 最多顯示 5,000 個 issue。
  • 選型題：要 sprint 節奏 → Scrum；持續交付 / 維運 → Kanban；Kanban 但 backlog 太長把 board 塞爆 → Kanban with backlog。

2.2 跨 project / 跨團隊 board

  • 建 board 三種來源：(a) 新 project、(b) 既有 project（自動生成 filter project = X ORDER BY Rank ASC）、(c) saved filter（跨 project 唯一方法；TMP 要第二個 board 也走這條）。
  • 需要 Browse Projects 權限才能選該 project。
  • 別人要看得到 board = 看得到底層 saved filter + 有相關 project 的 Browse Projects。filter 沒分享 → 只有 owner 看得到 board。
  • Board 位置（location）：某個 project 或個人 profile；Board settings → General → Location 可改；掛在停用的 project / user 上會失聯，需重新指定。
  • Board admin ≠ project admin：board settings 裡的 Administrators 欄位；board admin 可改 board 設定，project admin（該 location 的）也可。
  • 跨 project board 的隱含代價：各 project 的 workflow 狀態都要對到 columns、sprint 會跨 project、估算單位要一致。

2.3 Columns ↔ workflow statuses

每個 status 要對應到一欄；沒對應的 status，issue 就不會出現在 board 上。
  • Scrum 與多數 agile 報表以最右欄判定 Done；Cancelled 這種也要放最右欄。Kanban 的 Hide completed work 則看 status category 是 Done，跟對到哪一欄無關。查證修正
  • 未對應（unmapped）的 status → issue 不在 board 上。排查「issue 不見了」第一個看這裡。
  • Simplified workflow：board admin 可直接在 board 加/刪 status（等同改 workflow），限該 project 專用 workflow。
  • Column constraints：Issue count 或 Issue count excluding sub-tasks；min / max；超過 max 欄頭變紅、低於 min 變黃。是提醒，不會阻擋。
  • Kanban backlog：把一個 status 拖進 Kanban backlog panel → 該 status 的 issue 進獨立 backlog 畫面。

2.4 Filter、sub-filter、quick filter

三層由外往內一層一層縮小範圍；quick filter 只影響點的那個人。
  • Board filter 改了 → board 內容立刻變；沒有 ORDER BY Rank → 不能拖曳排序。
  • Quick filter 預設兩個：Only My Issues（assignee = currentUser()）、Recently Updated（updatedDate >= -1d）。多選是 AND。
  • Sub-filter 可改，例如加 AND status != Cancelled。
  • Filter 的分享權限決定誰看得到 board（見 2.2）。
  • Filter 用到 currentUser() 時每個人看到的 board 不同。

2.5 Estimation 與 time tracking

設定 選項 影響
Estimation statistic Story points / Original time estimate / Issue count / 自訂數字欄位 Burndown 縱軸、velocity 單位
Time tracking None（用 statistic 追蹤）/ Remaining estimate and time spent 選後者：burndown 用剩餘時間，且 sub-task 的工時計入
  • Sub-task 的 story points 永遠不計；只有 parent 的算。
  • 改 estimation statistic 不會回溯改變歷史 sprint 的報表資料。
  • TMP 要先在 features 開 Estimation，再選 story points 或 time。

2.6 Swimlanes / card colors / card layout / working days / detail view

Swimlanes（一次只能一種）

依據 行為
Queries JQL 分 lane，由上到下第一個符合者；預設 Expedite（priority = Blocker）與刪不掉的 Everything Else；ORDER BY 無效（一律 rank）
Stories sub-task 掛在 parent 下
Assignees 每人一條；Unassigned 可設在最上或最下
Epics 依 parent epic
Projects 跨 project board 用
None 無泳道

Card colors：Issue type / Priority / Assignee / Queries（第一個符合的 query 決定色，都不符合＝灰）/ None。

Card layout：最多再加 3 個欄位；Scrum 的 backlog 與 active sprint 可分開設。Days in column：灰點 → 紅點（5 天以上出現紅、20 天四紅點）；Scrum 預設關、Kanban 預設開。

Working days：時區、每週工作日、非工作日（假日）。影響 Burndown、Sprint report、Epic report、Version report、Control chart、Sprint Health / Burndown gadget。CFD 不受影響（它按日曆日）。

Issue detail view（board 右側面板）：project admin 設定顯示哪些欄位（Administer Projects）；Summary 永遠在。

620.3 Managing Projects（25%）

3.1 權限（project + global）

這裡只列 620 會考的重點，完整內容見 620.3.1 專案權限：

Project admin 要懂的全域權限

Global permission 對 project 的影響
Browse users and groups 沒有它，@提及與 picker 只看得到同 project 有 Browse 的人
Share dashboards and filters 沒有它，filter / dashboard 只能自己用 → board 無法分享
Make bulk changes 沒有它，搜尋結果沒有 Bulk change 選項

Administer Jira 建 CMP、custom field、time tracking、issue linking 開關

改一般欄位Edit Issues；但 Assignee 要 Assign Issues、Reporter 要 Modify Reporter、Due date 與排序要 Schedule Issues，各自獨立

Administer Projects 的邊界：可以做 role 成員、versions、components、details、layout；不能改 permission scheme、換 scheme、建 role、改 workflow（除非 workflow 未共用且用新編輯器）。

3.2 Project roles

  • Project settings → People → Add people → 選 user 或 group → 選 role。
  • CMP 預設 role：Administrators、atlassian-addons-project-access（給 Marketplace app 用，別動）；常見另建 Developers / Members / Viewers。
  • Role 的意義：scheme 寫角色名，各 project 自己填人 → 授權下放，不必找 Jira admin。
  • Role vs Group：跨 project 同一批人 → group；各 project 不同人 → role；可把 group 放進 role。
  • Role 也用在 notification scheme、issue security level、workflow condition、filter / dashboard 分享。

3.3 Versions、Releases、Roadmap

Version 狀態：Unreleased（過了 release date 會顯示紅色）/ Released / Archived（從下拉與報表隱藏）。

動作 效果 / 注意
Release 若有未解決 issue，會問要「忽略」或「移到另一個 version」；Kanban board 的 sub-filter 會讓這批 issue 從 board 消失
Unrelease 回到 Unreleased
Archive 隱藏；不可再指派
Merge 把 A 併入 B，issue 的 Fix version 改成 B；A 消失
Delete 需選擇 issue 要改到哪個 version 或直接清空
Edit / Reschedule 改名、日期；拖曳排序
  • Fix version（修在哪個版本，決定 Release 內容）vs Affects version（哪個版本受影響，不會把 issue 放進版本）。
  • 需要 Administer Projects + Manage Versions 權限。
  • Release page / release hub：進度條（To do / In progress / Done）、Warnings（open PR、未 review、build 失敗——需要整合 dev tool 且有 View Development Tools）、Related work（連結設計稿、文件、部署等）、Approvals（可選）。
  • Roadmap / Timeline：單一 project 的 Gantt；顯示 epic 與其 child、依賴線、sprint、release；child 用 sprint 日期（Scrum）或 start/due date（Kanban）排；沒有 parent 的 issue 不會出現；跨 project 要 Premium 的 Plans。
  • 範圍變動反映在 Version report（預測 release 日）、Release burndown、Epic burndown 的「scope added」深藍段。

3.5 自動指派

多個 component 時先比 default assignee 的類型優先序，同一級才看 component 名稱字母序。
  • Component 的 default assignee 選項：Project default / Component lead / Project lead / Unassigned。
  • 優先序：Component lead > Project lead > Unassigned > Project default；同一級才依 component 名稱字母序。查證修正
  • 被指派者必須有 Assignable User 權限，否則跳過往下一層。
  • 更複雜規則（輪流、平衡工作量、依欄位）→ 用 Automation 的 Assign issue action。

3.6 Issue field layout

Description、Context、Hidden 三區；Context 裡再用 Hide when empty 分隔線切成兩段。
  • 入口：issue 右上 ••• → Configure → Issue layout（或 Project settings → Issues → Layout）。
  • Project admin 可設定，前提是 screen 沒有被其他 project 共用；哪些欄位「可用」由 screen 決定（Jira admin）；tab 只有 Jira admin 能改。
  • Layout 可複製到使用相同 screen 的其他 project。
  • 使用者自己可 pin 欄位到最上。
  • 欄位與權限的關係：欄位在 layout 上不代表能改——Assignee 要 Assign Issues、Due date 要 Schedule Issues、Reporter 要 Modify Reporter。

620.4 Automation（14%）

4.1 四種自動化手段怎麼選

情境用什麼
一次性改一堆 issueBulk change
每次轉換狀態就做某件事（同步、可靠）Workflow post function（Jira admin）
事件驅動、有條件分支、跨 issue 動作Automation rule
以上都做不到（複雜計算、外部系統）Marketplace app

Bulk change - 需要 Make bulk changes（全域）+ 對應 project 權限（例如 bulk move 要 Move Issues）。 - 上限 1,000 個 issue；四步：選 issue → 選操作 → 設定 → 確認。 - 操作：Edit、Move、Transition、Delete、Watch / Stop watching。 - 可取消勾選「Send mail for this update」避免通知轟炸。 - 不能 bulk edit：Summary、Description、Attachments、Resolution（要走 transition）、time tracking 欄位。 - Move 到 TMP 會丟失 component 與 version 資料；workflow 不同要對應 status。

Workflow post function - 每個 transition 有 5 個必要 post function（設狀態 → 加留言 → 寫歷史 → reindex → fire Generic Event），不可刪、不可排序，只能在中間插入。 - 常用可選：Assign to current user / reporter / lead developer、Update issue field、Update custom field、Copy value from other field、Clear field、Trigger webhook。 - 只有 Jira admin 能改（workflow 共用時）；順序有意義。

4.2 Automation rule 的解剖

Rule details 決定範圍與身分；主體是 Trigger → Condition → Action，需要動到相關 issue 時用 Branch。
  • Project rule：project admin 在 Project settings → Automation 建；scope 限該 project。
  • Global / multi-project rule：需 Jira admin；⚙ → System → Global automation。
  • Trigger 常考：Issue created、Issue transitioned、Field value changed、Issue commented、Scheduled（cron + JQL）、Manual、Sprint started / completed、Version released、Multiple issue events、Incoming webhook、DevOps（PR merged、Build failed…）。
  • Condition 常考：Issue fields condition（首選，不用 smart value）、JQL condition、User condition（是誰 / 在哪個 group）、Related issues condition（parent / sub-task / linked 是否符合）、Advanced compare（smart value + regex）、If / else block（最多兩層巢狀）。
  • Branch：For sub-tasks / parent / epic / linked issues / JQL / most recently created；分支平行執行，順序不保證，不能依賴分支間的變更。
  • Action 常考：Edit issue（Add/remove values 保留既有 labels；多選欄位預設整組取代）、Transition、Assign（balanced workload / round robin / 指定 / smart value）、Create issue / sub-tasks、Clone、Comment、Send email、Lookup issues（≤100）、Create variable、Log action、Send web request。
  • Smart values：{{issue.key}}、{{issue.summary}}、{{issue.assignee.displayName}}、{{issue.status.name}}、{{issue.fixVersions}}、{{issue.parent}}、{{triggerIssue}}（觸發的那張，跟 branch 內的 {{issue}} 不同）、{{createdIssue}}、{{now}}、{{now.plusDays(5)}}、list 的 .first .last .size .join(", ")。

620.5 Reporting（19%）

5.1 JQL

結構：field operator value [AND|OR|NOT ...] [ORDER BY field ASC|DESC]；括號決定優先；IN 常可取代多個 OR。

Basic search 做不到的（要切 JQL）：OR、NOT、EMPTY、!= / IS / > 等比較、以及沒指定 project 的 project 專屬欄位。

Operators

類 運算子 備註
相等 = != IN NOT IN != 不匹配空值；文字欄位不能用 =
比較 > >= < <= 只用於可排序欄位（日期、版本、數字）
文字 ~ !~ Summary、Description、Environment、Comments、text 欄位；支援萬用字元與詞幹
空值 IS EMPTY IS NOT EMPTY（= NULL） 只有 IS / IS NOT 能配 EMPTY
歷史 WAS WAS IN WAS NOT CHANGED 述詞：AFTER BEFORE BY DURING ON FROM TO

常考寫法 - 未指派或非我的：assignee != currentUser() OR assignee is EMPTY - 上週建立：created >= startOfWeek(-1) AND created < startOfWeek() - 曾經 In Progress 但現在不是：status WAS "In Progress" AND status != "In Progress" - 上個月由某人改成 Done：status CHANGED TO Done BY jsmith DURING (startOfMonth(-1), endOfMonth(-1)) - 這個 sprint 的 bug：sprint in openSprints() AND issuetype = Bug - 分類：category = "Platform" - Text：text ~ "login error"、summary ~ "login*" - 排序永遠在最後：ORDER BY priority DESC, created ASC

5.3 Agile reports 與 issue analysis reports

報表 Board 看什麼 讀法
Burndown Scrum 剩餘工作 vs 時間 灰 guideline（開始時無 issue 則沒有）；紅線實際；sub-task 點數不計；scope 增加會往上跳
Burnup Scrum / TMP scope（紅）vs 完成（綠） 紅線上升＝scope creep；紅綠交會＝完成
Sprint report Scrum 完成 / 未完成 / 移除 / 完成於 sprint 外 「*」＝sprint 開始後加入；3 → 3.5 估點改變
Velocity Scrum 每 sprint 承諾 vs 完成 取近幾個 sprint 平均預測產能
Epic report Scrum 某 epic 的完成 / 未完成 / 未估點清單 某時點的組成
Epic burndown Scrum, CMP 依 sprint 看 epic 進度 + 預測還要幾個 sprint 用近 3 sprint velocity；>30% 未估點則預測不可靠；深藍＝scope added
Release / Version burndown Scrum 版本進度與預測 release 日 同上邏輯
Version report Scrum 預測版本完成日 受 working days 影響
Control chart Scrum / Kanban cycle time（開始到完成）；lead time 是建立到完成 藍線 rolling average（以 issue 數為窗，取 20%、最少 5、奇數）；藍帶標準差＝可預測性；離群點要查
CFD Scrum / Kanban 各狀態累積數量隨時間 某色帶垂直變寬＝該欄瓶頸；帶寬是當時在該狀態的數量（官方提醒它不等於傳統的 WIP 數字）；按日曆日 查證修正

5.4 Agile at scale

  • 跨 project 的 board（saved filter）＋ 共用 estimation 單位。
  • Timeline 只看單一 project；跨 project 規劃要 Plans（Premium）。
  • 統一 scheme（CMP 共用設定）＋ project categories 分群 ＋ dashboard 用跨 project filter 彙總。
  • Component / version 都是 project 內的，跨 project 追蹤靠 labels、custom field 或 Plans。

實作 Lab（建議 Jira Standard 30 天試用；Free 缺 permission scheme / role / 多 board）

Lab A — Project creation（45 分） 1. 建一個 CMP Scrum、一個 TMP Kanban；比較 Project settings 側欄差異。 2. TMP：切 Open → Limited → Private，用第二帳號觀察；建自訂 role「Reviewer」只給留言。 3. CMP：改 project key，觀察舊連結、board filter 是否還正常。 4. 建 project category（需 Jira admin），在 JQL 用 category =。 5. 把 TMP 丟進 trash 再還原：確認 project admin 能丟（CMP、TMP 都可以），但 Restore 只有 Jira admin 能做。查證修正

Lab B — Board（90 分，最重要） 1. 在 CMP 建第二個 Scrum board（從 saved filter），filter 不分享 → 用第二帳號看不到；分享後看得到。 2. Columns：新增「Cancelled」status 不對應 column → issue 消失；把它放最右欄 → 回來且算完成。 3. 設 column constraint max 3，塞 4 個看欄頭變紅。 4. 建 Kanban board；Release 一個版本 → issue 消失；把 sub-filter 改掉再看。 5. 拿掉 filter 的 ORDER BY Rank → 拖曳失效。 6. Swimlane 選 Queries，加一條 issuetype = Bug 放在 Expedite 上面，觀察「第一個符合」。 7. Card colors 選 Queries，兩條互相重疊的 query，看誰贏。 8. Estimation 切 Story points ↔ Issue count，看 burndown 縱軸變化；給 sub-task 點數確認不計。 9. Working days 拿掉週末，看 burndown 的 guideline 變形。 10. 建兩個 quick filter 同時勾選，確認 AND。

Lab C — Managing projects（60 分） 1. 建 versions v1.0、v1.1；v1.0 留一個未解決 issue 再 Release → 選移到 v1.1；Merge v1.1 到 v2.0。 2.
