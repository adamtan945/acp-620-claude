620.4.1 · Identify ways to automate Jira (bulk change, workflow, automation, apps)

辨識 Jira 的自動化手段：
bulk change、workflow post function、automation、filter subscription、app

Domain 4 的官方導言說得很直接：project admin 要懂每一種手段怎麼運作、各自適用什麼情境，而且 post function 這種要跟 Jira admin 合作。這一節不教怎麼寫 rule（那是 620.4.2），只教「這個需求該用哪一種」。

術語：考試用 project／issue；現行產品為 space／work item，automation 的「rule」現行文件也稱「flow」。本教材沿用考試用語。
這一節考什麼

四種手段都做不到時才是 Marketplace app 的領域。考題通常把 app 當「排除其他選項後的答案」，不會考特定 app。
核心模型

先問「多常發生、由什麼觸發」，手段自然浮現

四種手段（加上 app）不是功能強弱的排序，而是觸發方式不同：人手一次、workflow 轉換、時間表、事件。照下面的順序問，第一個答「是」的就是答案。

手段 1

Bulk change：一次改最多 1,000 個 issue

需要的兩層權限
  • 全域權限 Make bulk changes（Jira admin 授予群組）
  • 該操作在每個受影響 project 的權限：bulk move 要 Move Issues、bulk transition 要 Transition Issues、bulk delete 要 Delete Issues…

缺任一層，搜尋結果的 ••• 選單就不會出現 Bulk change。

上限與範圍
  • 一次最多 1,000 個 issue
  • 入口：搜尋結果 → ••• → Bulk change all N issues
  • 可跨 project（每個 project 都要有對應權限）

四步驟

1
選 issue
從搜尋結果勾選（全選或部分）
2
選操作
Edit／Move／Transition／Delete／Watch／Stop watching
3
設定
要改的欄位、目的地 project、對應 status、必填欄位
4
確認
可取消「Send mail for this update」

五種操作與注意事項

操作能做什麼注意
Edit一次改 assignee、due date、priority、components、labels、custom field…不能改：Summary、Description、Environment、Attachments、Project、Resolution、time tracking 欄位、Import Id、Read-only text 類 custom field
Move搬到另一個 project 或改 issue typeworkflow 不同要對應 status、補必填欄位；CMP → TMP 會掉 components 與 versions
Transition一批 issue 走同一個 transition要填該 transition 的必填欄位（例如 Resolution）；只有共用 workflow 的 issue 能一起轉
Delete一次刪除不可逆；一般建議用 Done 類狀態或 archive 取代
Watch／Stop watching批次加入或退出關注—
考題最愛的兩個數字與一個清單
1,000（上限）、兩層權限（Make bulk changes ＋ project 權限）、以及「Resolution 不能 bulk edit，要走 bulk transition」。
手段 2

Workflow post function：transition 之後自動做的事

Post function 掛在 workflow 的 transition 上，每次有人走過那個 transition 就同步執行。它和 condition、validator 是同一個 transition 上的三個階段，考題常混在一起問。

圖 2　Condition 藏按鈕、validator 擋提交、post function 事後執行。Subtask Blocking Condition（620.1.3）就是第 ① 階段。
項目內容
誰能改Jira admin（workflow 是全站物件）。Project admin 只有在 workflow 未共用且用新編輯器時才能動——所以 domain 導言說「需要與 Jira admin 合作」
可加的自訂項Assign to Current User／Lead Developer／Reporter、Clear Field Value、Copy Value From Other Field、Update Issue Field、Update Issue Custom Field、Trigger a Webhook、Set issue security level based on project role
典型用途轉到 Done 時設 Resolution；Reopen 時清 Resolution；轉到 In Review 時指派給 reporter
和 automation 的差別Post function 同步、只認 transition、沒有條件分支、改完要 publish workflow；automation 非同步、任何事件都能觸發、有 condition／branch，但受執行上限與 actor 權限影響
手段 3

Filter subscription：不改 issue，只按時寄清單

怎麼建
  1. 搜尋 → Save as 存成 filter（可加星、可分享）
  2. Filter → Details → New subscription
  3. 選收件人（自己或 group）、排程（每日／每週／每月或 cron）、是否空結果也寄
權限與陷阱
  • 訂閱給群組需要全域權限 Manage group filter subscriptions
  • 收件人只會看到自己有權限看的 issue（filter 以收件人身分執行）
  • 要分享 filter 給別人需全域權限 Share dashboards and filters
  • 它是「通知」手段，不會改任何欄位；要改欄位請用 automation 的 Scheduled trigger
考題長相
「每週一早上把逾期未關閉的 issue 寄給各 PM」→ filter subscription（或 automation Scheduled ＋ Send email）。若題目強調「不要改 issue、只要 email 清單」，選 filter subscription；若要同時改欄位或依條件分流，選 automation。
手段 4

Automation for Jira：事件驅動的 rule

官方定義：「removes the need to do manual, repetitive work by letting your team's processes and workflows run themselves.」每條 rule 由 trigger → condition → action 組成，可加 branch 對相關 issue 動作。細節在 620.4.2，這裡只放本節會考的定位：

面向內容
誰能建Project admin 在 Project settings → Automation 建單一 project 的 rule（CMP 需 Administer Projects ＋ Browse Projects；TMP 需 Administrator）。Global／multi-project rule 只有 Administer Jira 能建
建立方式從 template、從零開始、或用 Rovo 描述需求產生
三種入口Issue 事件（created／transitioned／updated／field changed／commented…）、Scheduled（cron ＋ JQL）、Manual、DevOps 事件、Incoming webhook
典型用途建立時自動指派與加 sub-task、欄位改變時同步 parent、Done 時關閉所有 sub-task、每天找逾期 issue 加標籤並通知
代價受 actor 權限與執行上限限制；非同步；rule 多了難追（620.4.3）

情境練習

先自己判斷，再點開解答

PM 想把 sprint 結束時 200 張未完成的 issue 一次改成 priority = Low，並且不想寄出 200 封通知。
解答
Bulk change → Edit，第 4 步取消「Send mail for this update」。需要 Make bulk changes ＋ 該 project 的 Edit Issues。
使用者有 Make bulk changes 全域權限，但在某個 project 的搜尋結果裡看不到 Bulk change 選項。
解答
缺第二層：該 project 的對應權限（例如 Edit Issues）。兩層都要。
想用 bulk edit 把 300 張 issue 的 Resolution 設成 Won't Do。
解答
Resolution 不能 bulk edit；改用 bulk transition 走一個會要求 Resolution 的 transition。
每次 issue 轉到 Done，都要把 Resolution 設成 Done；團隊不想依賴任何人記得做。
解答
Post function（Update Issue Field → Resolution）掛在 Done transition；需要 Jira admin。同步且必然執行，比 automation 更適合。
Jira admin 在 Done transition 想把「Fire Generic Event」移到最前面，讓 app 早一點收到事件。
解答
不可以。五個必要 post function 順序固定、不可刪改；改了會讓 automation 與 Marketplace app 行為異常。
主管要每週一 09:00 收到「逾期且未指派」的 issue 清單 email，不需要改任何欄位。
解答
Filter subscription：存 filter（`duedate < now() AND assignee is EMPTY AND resolution is EMPTY`），New subscription 排每週一。
承上，要寄給整個 `pm-team` 群組，但建立訂閱時找不到群組選項。
解答
缺全域權限 Manage group filter subscriptions，請 Jira admin 授予。
Issue 建立時，若 component 是 Backend 就自動加三個固定 sub-task 並指派給 lead。
解答
Automation rule：Issue created → Issue fields condition（component = Backend）→ Create sub-tasks ×3 → Assign。有條件、要建相關 issue，其他手段做不到。
Project admin 想建一條「跨三個 project」的 rule。
解答
Multi-project／global rule 需要 Administer Jira；project admin 只能建自己 project 的 rule，請 Jira admin 在 Global automation 建。
需求是「issue 進 In Progress 時，把它的 Confluence 需求頁狀態同步改成 In development」——Jira 內建手段做得到嗎？
解答
Automation 可用 Send web request 或 Confluence 動作嘗試；若牽涉 Confluence 頁面屬性等內建動作不支援的操作，才考慮 Marketplace app。考題邏輯：先排除四種內建手段，再選 app。
常見陷阱

考題喜歡設的誤解

誤解事實
「有 Make bulk changes 就能 bulk 任何操作」還要每個 project 對應的權限（Edit／Move／Transition／Delete Issues）
「Bulk edit 可以改 Summary 或 Resolution」Summary、Description、Environment、Attachments、Project、Resolution、time tracking 都不能；Resolution 走 bulk transition，Project 走 bulk move
「Post function 只有 Jira admin 看得到，跟 project admin 無關」Project admin 要懂它的效果（例如 Resolution 為什麼自動被設），才能判斷需求該找 Jira admin 還是自己用 automation
「Filter subscription 可以順便改欄位」只寄 email；要改欄位用 automation Scheduled trigger
「Automation 是萬能的，一律用它」每次 transition 都要做、且要同步保證的事，post function 更可靠；一次性的事用 bulk change 更省
「Project admin 可以建 global rule」只能建自己 project 的 rule；global／multi-project 要 Administer Jira
選型反例：一次性清理不要留成永久 Scheduled rule
「把 300 張舊卡補上 label」是一次性需求，做成每天跑的 Scheduled rule 會長期吃用量、而且未來新卡也會被改到。正確做法是分批 Bulk change，做完就結束。反過來，「每次建立 Bug 都要指派」是持續性需求，用 bulk change 只會補一次、之後的新卡不會處理。 判斷句：先問這是「一次把既有資料改好」還是「以後每次都要做」。
來源：Edit multiple work items、Automation service limits
實作（30 分鐘）

四種手段各做一次

  1. Bulk change：搜出 5 張 issue → ••• → Bulk change → Edit → 改 priority，取消 Send mail；再試 bulk edit Summary，確認欄位不在清單裡。
  2. Post function（需 Jira admin 或專用 workflow）：在 Done transition 加 Update Issue Field → Resolution = Done；在 Reopen transition 加 Resolution = None。轉一張 issue 來回看 Resolution 變化。
  3. Filter subscription：存一個「逾期未指派」filter → New subscription → 每天 → 勾「即使沒有結果也寄」，看隔天信箱。試著改成寄給 group，觀察是否有權限。
  4. Automation：Project settings → Automation → Create rule：Issue created → Issue fields condition → Assign issue。看 audit log 一次成功紀錄。
  5. 做完回到圖 1，對每一步問自己「為什麼不是另一種手段」。
