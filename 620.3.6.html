620.3.6 · Configure issue field layout

設定 issue field layout：欄位放哪、誰能改、改了不等於能編輯

Issue layout 是 project admin 少數能直接動手的 CMP 設定，但有兩個前提常被忽略：哪些欄位「可用」由 Jira admin 的 screen 決定，以及欄位出現在畫面上不代表使用者有權限改它。這一節把區域、權責、權限三件事拆開講。

術語：考試用 project／issue／screen；現行產品為 space／work item／screen。本教材沿用考試用語。

核心模型

Layout 的四個區域

打開任一 issue → 右上 ••• → Configure（或 Project settings → Issues → Layout）。畫面分成三個可見區域加一個「不顯示」區域，欄位在四者之間拖曳。

圖 1　拖曳規則：Description ↔ Context 可互拖；分隔線以下的欄位空值時收進「Show more fields」，一有值就自動跳到 Details。
區域放什麼行為
Description fields多行 rich text：Description、Environment、自訂 Paragraph版面上最顯眼的一區，可以放文字、程式碼區塊、圖片與表格，適合需要大量說明的內容

Hidden fields不想在這個 project 顯示的欄位在這個 project 的 issue 畫面上不顯示，但欄位仍在 screen 上、既有資料完整保留，JQL 與報表照樣讀得到

改 Task 卻連 Sub-task 一起變
如果 Task 與 Sub-task 共用同一個 View screen，layout 設定可能以同一組 issue types 一起生效。改之前先看清楚正在調整的是哪個 screen、涵蓋哪些 types；改完用另一個共用同 screen 的 type 開一張 issue 驗證。
Screen 共用時 project admin 改不了
如果這個 project 的 screen 也被別的 project 使用，layout 設定會鎖住（避免一個 project 改動影響另一個）。解法：請 Jira admin 複製一份 screen／screen scheme 給這個 project 專用。

TMP 對照

TMP 的欄位長在 project 裡：Project settings → Issue types → 選 type → 直接拖曳欄位、建新欄位，不需要 Jira admin，也沒有全站共用的 screen／screen scheme 物件（考試作答用這版）。考題問「哪種 project 的 admin 能自己新增欄位」→ TMP。

TMP：必填、預設內容、排序是三件不同的事
  • Required：在 Project settings → Issue types（或 Work types）為該類型的欄位勾選；Summary 本來就必填。
  • 預設內容／預設值：建立時帶入的起始資料（例如 Bug 的「重現步驟」範本、Story point estimate 的 Default number），使用者仍可改，不是強制保留。
  • 排序：只是呈現位置，調整順序不會讓任何欄位變成必填。
系統欄位「不能改名稱」不代表「不能設 default value」；官方也未逐一承諾每個預設欄位都提供相同控制，實際選項以站台為準。來源：Customize work item fields in team-managed spaces（2026-09-08 核對）
現行差異（2026-09-08 查核）
官方「Map a screen to a workflow transition」現已列出 TMP 入口：Project settings → Work types → Edit workflow → 選 transition → Rules → Add → Request input → Show a screen，可在轉換時要求填欄位。所以「TMP 完全沒有 screen」已不準確：TMP 沒有 screen scheme，但 transition 可掛輸入畫面。實際選項以站台為準（實機驗證）。
欄位 vs 權限

看得到 ≠ 改得了

Layout 決定欄位顯不顯示；permission scheme 決定使用者能不能改。三個欄位有專屬權限，Edit Issues 管不到它們：

欄位需要的權限沒權限時的表現
AssigneeAssign Issues欄位看得到但點不動，呈現唯讀狀態；連把 issue 轉給別人也做不到
ReporterModify Reporter欄位照常顯示，但呈現唯讀狀態，改不了開單人
Due date（以及 board／backlog 的 rank）Schedule IssuesDue date 改不動，而且在 board 與 backlog 上拖曳卡片時會彈回原位
其他一般欄位（Summary、Description、Priority、Labels、自訂欄位…）Edit Issues整張 issue 的一般欄位都變成唯讀，只能看不能改
Time tracking（Original estimate、Log work）Work On Issues（＋ Edit Issues 改估算）issue 上不會出現 Log work 的選項，記不了工時
Security LevelSet Issue SecuritySecurity Level 不會出現在可編輯的欄位清單裡，沒辦法調整這張 issue 的可見範圍

情境練習

先自己判斷，再點開解答

TMP 的 admin 想讓 Bug 的「重現步驟」一定要填，於是把它拖到最上面。使用者仍可以留空送出。為什麼？
解答
因為排序只是決定欄位顯示的位置，跟必不必填毫無關係。TMP 底下有三件常被混為一談的事要分清楚：Required（在 Project settings → Issue types 為該欄位勾選，沒填就送不出去）、預設內容／預設值（建立 issue 時自動帶入的起始資料，例如「重現步驟」的範本，但使用者仍然可以整段刪掉）、排序（純粹是呈現位置）。這位 admin 真正要做的是勾 Required；如果他要的是給同事一個填寫範本，那該設的是預設內容——但那擋不住有人清空它。
Project admin 改了 Task 的 layout，結果 Sub-task 的畫面也跟著變。哪裡出問題？
解答
沒有出問題，這是預期行為。issue layout 是掛在 screen 上的，不是掛在 issue type 上；當 Task 與 Sub-task 共用同一個 View screen 時，改動當然會同時反映在兩者身上。所以動手之前要先弄清楚你正在調整的是哪一個 screen、它涵蓋了哪些 issue type。如果確實需要兩者分開，得請 Jira admin 複製一份 screen 與 screen scheme，讓其中一種 issue type 專用。改完之後，養成用另一個共用同 screen 的 type 開一張 issue 驗證的習慣。
Project admin 想在 issue 上加一個新的「Customer」下拉欄位，Configure 畫面找不到。原因？
解答
因為這個欄位還不存在，或是存在但沒有被加進這個 project 所使用的 screen。這裡有一條界線要記牢：layout 只能替「已經在 screen 上的欄位」安排位置，不能無中生有。建立 custom field、把欄位加進 screen，兩件事都是站台層級的動作，屬於 Jira admin。所以 project admin 的正確動作是開單請 Jira admin 建立欄位並加到對應的 screen，之後才輪到自己在 Configure 畫面決定它放哪一區。
Project admin 打開 Configure，所有欄位都拖不動。最可能原因？
解答
最可能是這個 project 使用的 screen 同時也被別的 project 使用。Jira 為了避免一個 project 的調整波及其他 project，會在這種情況下把 layout 鎖住，project admin 拖不動任何東西。解法是請 Jira admin 複製一份 screen 與 screen scheme 給這個 project 專用，脫離共用之後就解鎖了。這個模式在 CMP 反覆出現——只要物件是共用的，權限就會被拉高到 Jira admin，workflow、field configuration 也都是同樣的邏輯。
Fix versions 放在分隔線下方，某張 issue 卻顯示在 Details。為什麼？
解答
因為分隔線的意思是「空值時才隱藏」（Hide when empty），不是「永遠不顯示」。放在分隔線下方的欄位，沒有值時會被收進「Show x more fields」裡，一旦被填了值就會自動升到 Details 區顯示出來。這個設計相當貼心——不常用的欄位平常不佔版面，真的有資料時又不會被埋起來。所以看到「同一份 layout 底下不同 issue 的欄位排列不太一樣」，通常就是這個機制在運作，不是設定錯亂。
使用者能改 Summary、Description，但 Assignee 灰掉。缺什麼？
解答
缺的是 Assign Issues 權限。Jira 把三個欄位從 Edit Issues 裡獨立出來，各自需要專屬權限：Assignee 要 Assign Issues、Reporter 要 Modify Reporter、Due date（連同 board 的拖曳排序）要 Schedule Issues。所以「其他欄位都能改、就這幾個灰掉」是很典型的症狀。要特別區分兩種狀況：欄位灰掉（顯示但不能編輯）＝權限問題；欄位整個不見＝layout 或 screen 問題，兩者要找的人不一樣。
使用者說「Due date 欄位完全不見了」，另一位說「看得到但改不了」。分別是什麼問題？
解答
這兩個是完全不同層次的問題，也是本節最核心的辨別題。「欄位完全不見」是顯示層的問題——可能是 project admin 把它拖到了 Hidden 區，也可能是這個欄位根本不在該 issue type 的 screen 上（後者要找 Jira admin）。「看得到但改不了」則是權限問題——Due date 需要 Schedule Issues，而不是 Edit Issues。記住這條判斷法則：Layout 決定「顯不顯示」，permission scheme 決定「能不能改」，先看症狀屬於哪一邊，再決定去改設定還是去要權限。
兩個 project 用同一份 screen，PM 想讓 B project 的 layout 跟 A 一樣。最快做法？
解答
在 A 的 layout 設定頁使用「Copy to other projects」（複製到其他 project）功能，直接把整份排版套過去，不必手動重排一次。這個功能有一個硬性前提：只能複製到使用相同 screen 的 project——這也正是題目特別交代「兩個 project 用同一份 screen」的原因。如果兩邊 screen 不同，這個選項就用不了，只能請 Jira admin 先調整 screen 設定。
PM 想讓自己的 issue 畫面把「Sprint」放最上面，但不想影響同事。
解答
用 Pinned fields（釘選欄位）。它是每個使用者自己的偏好設定，把 Sprint 釘在最上面只會影響 PM 自己的畫面，同事完全不受影響，而且任何使用者都能用，不需要任何管理權限。相對地，layout 是整個 project 共用的設定，改了所有人都會看到。這題想建立的判斷是：個人偏好用 pinned，團隊共識才動 layout。
把「Story points」拖到 Hidden 後，JQL 還搜得到嗎？舊資料還在嗎？
解答
兩個都還在。把欄位拖到 Hidden 只影響這個 project 的 issue 詳細畫面要不要顯示它，欄位本身仍然掛在 screen 上，既有的資料一筆都不會消失，JQL 照樣搜尋得到、報表照樣算得到。這一點與 field configuration 的 hidden 效果不同（後者會讓 JQL 認為欄位不存在，還記得 620.2.4 那個 Kanban board 上 Task 全部消失的陷阱嗎），兩者不要混淆。
TMP 的 project admin 想新增欄位，需要找 Jira admin 嗎？
解答
不需要。這正是 TMP 與 CMP 最大的差異之一：TMP 的欄位是長在 project 裡的，project admin 到 Project settings → Issue types 選一個 type，就能直接建立新欄位、拖曳排序、設定必填，全程不必找 Jira admin。代價是這些欄位只存在於這個 project，別的 project 用不到，也沒有 screen 與 screen scheme 這種可共用的物件。（補充一個現行變化：TMP 的 transition 可以用 Request input 規則掛一個輸入畫面，但那是流程控制，不是欄位管理，兩者別混為一談。）
常見陷阱

考題喜歡設的誤解

誤解事實
「Project admin 可以在 layout 建新欄位」不能。layout 只能替 screen 上已經有的欄位安排位置；建立 custom field、把欄位加進 screen 都是 Jira admin 的權責（TMP 則沒有這個限制）
「Layout 可以跨 project 共用」不行。layout 是各 project 各自的設定；唯一的捷徑是「Copy to other projects」，而且只能複製到使用相同 screen 的 project
「Hidden 會刪掉欄位資料」不會。Hidden 只是讓欄位不顯示在這個 project 的 issue 畫面上，欄位仍在 screen、資料完整保留，JQL 與報表照樣讀得到
「Edit Issues 就能改所有欄位」不能。Assignee 要 Assign Issues、Reporter 要 Modify Reporter、Due date 與拖曳排序要 Schedule Issues，這三個欄位被獨立出來，Edit Issues 管不到
「Pinned fields 是 layout 的一部分」不是。Pinned fields 是每個使用者自己的偏好，任何人都能設，只影響自己的畫面，跟 project 的 layout 是兩回事
「TMP 把欄位往上排就會變成必填」不會。Required（必填）、預設內容（帶入的起始值，可被改掉）、排序（呈現位置）是三件互相獨立的事；只有勾 Required 才會強制填寫
「有 Manage work item layouts 就能建欄位」不能。這個細分權限只讓人排列既有欄位，一樣受「screen 未被其他 project 共用」的限制，不等於取得全站的 custom field 管理權
「改 Task 的 layout 不會影響 Sub-task」不一定。layout 是掛在 screen 上的，兩個 issue type 共用同一個 View screen 時，改動會一起生效；要分開得請 Jira admin 給專用 screen
「分隔線下方的欄位永遠不顯示」不是。分隔線的意思是「空值時隱藏」，欄位一旦被填了值就會自動升到 Details 區顯示出來
實作（20 分鐘）

把 layout 與權限拆開看

  1. CMP 任一 issue → ••• → Configure：把 Due date 拖到分隔線下、Labels 拖到 Hidden，存檔後開 issue 看差異；填一個 Due date 觀察它跳到 Details。
  2. 用第二個帳號（只有 Browse＋Edit Issues 的 role）開同一張 issue：Assignee、Reporter 顯示但唯讀；再給它 Assign Issues，重新整理。
  3. 把 project 的 screen scheme 指給另一個 project 共用，回到 Configure 觀察被鎖住的提示；改回專用後再試。
  4. 在 layout 頁用「Copy to other projects」複製到相同 screen 的 project。
  5. 對照 TMP：Project settings → Issue types → Story，直接建一個新欄位並拖曳；再對同一欄位勾一次 Required、設一次預設內容、換一次排序，各建一張 issue 觀察三者互不影響。
  6. 找兩個共用同一 View screen 的 issue type（例如 Task 與 Sub-task），改其中一個的 layout 後開另一個驗證是否一起變動。
