620.1.3 · Recommend an issue type configuration for a company-managed project

為 company-managed project 推薦 issue type 設計

這一節資料量不大，但它是整份考試「推薦題」的第一站，重點在判斷而不是操作：需要哪些 issue type？該用 epic／standard／sub-task 哪一層？要不要新建 type？

術語：考試用 project／issue／sub-task；現行產品為 space／work item／subtask。本教材沿用考試用語。
這一節考什麼

標題的三個關鍵字

關鍵字意思
business requirements題目會先給你一段情境，描述這個團隊怎麼工作、他們想追蹤什麼；你要從敘述裡讀出真正的需求，而不是照字面挑名詞
recommend要你做出建議，而建議通常包含三個判斷：需要哪幾種 issue type、每一種該放在 epic／standard／sub-task 的哪一層、以及到底該不該為它新建一個 type
company-managedCMP 的 issue type 是「標籤 ＋ scheme」，建新 type 要 Jira admin；你是 project admin，要懂什麼時候該去請 Jira admin 建、什麼時候不必

唯一的 bullet：「Understand the features associated with epics, base (standard) and sub-task issue types」——三層各自能做什麼、不能做什麼。

三層階層

先把「能力表」背起來

滑鼠移到圖中的層級，下方對應的能力卡會亮起。

圖 1　Epic 的 child 只能是 standard；sub-task 不能直接掛在 epic 下。
Epic
  • 不能自己進 sprint，因為它是裝東西的容器，真正進 sprint 的是它底下的 standard issue
  • 不會以卡片形式出現在 board 上；它出現在 backlog 的 Epic panel 裡，在 Timeline 上則畫成一條長條
  • 自己的 story points 不計入 burndown，進度是把底下 child 的點數加總出來的
  • 底下 child 記錄的工時可以向上彙總（roll-up）到 epic
  • 有專屬的報表可看：Epic report、Epic burndown 與 Timeline
  • 一個 epic 底下的 child 顯示上限是 500 個
Standard（Story／Task／Bug）
  • 可以獨立放進 sprint，它就是 sprint 規劃的基本單位
  • 在 board 上以一張卡片呈現，是團隊每天在拖動的東西
  • 它的 story points 會計入 burndown 與 velocity，估點估在這一層才有意義
  • 可以自己記錄工時，底下 sub-task 的工時也會彙總上來
  • Sprint report、burndown 這些報表算的都是這一層
  • 底下的 sub-task 一樣有 500 個的顯示上限
Sub-task
  • 不能自己進 sprint，它永遠跟著 parent 一起進、一起出
  • 在 board 上也是一張卡片，通常顯示在 parent 所屬的泳道底下
  • 就算你替它填了 story points，也不會計入 burndown 或 velocity
  • 可以記錄工時，而且會彙總到 parent 身上
  • 沒有自己的報表，所有數字都併進 parent 一起看
  • Issue security 直接繼承 parent，不能單獨設一個等級
500 上限的後果（考點）
超過 500 個 child，parent 上看不到 child 清單（得用搜尋），而且 sub-task 不再納入 parent 的 time tracking 彙總。官方建議拆成多個 parent。

官方定義句

  • Epic：high-level initiatives，把相關工作分組的大型工作項目。
  • Standard：regular business tasks，日常工作實際發生的層級。
  • Sub-task：把 standard 拆成更小的塊，只能當 child。

三層在 Scrum vs Kanban 的角色

層ScrumKanban
Epic用來裝跨越多個 sprint 的大主題，並靠 Epic burndown 預測還要幾個 sprint 才做得完同樣是主題容器，在 Timeline 上排長條；沒有 sprint 就沒有 Epic burndown
Standard團隊在 sprint planning 時承諾的單位，story points 就估在這一層就是在 board 上從左流到右的卡片，重點指標是 cycle time（一張卡走完要多久）
Sub-task用來在 sprint 內把一張卡分給不同人做，但不影響 velocity 的計算一樣是同一張卡片內部的分工，在 Stories 泳道模式下會顯示在 parent 底下
核心模型

CMP 的 issue type 是「標籤 ＋ 四張對照表」

在 CMP，一個 issue type 本身沒有任何行為，行為全靠 scheme 對應出來。點上方的 type，看它各自對到哪一份 workflow、screen、field configuration。

圖 2　「建一個新 issue type」的真正成本不是建 type，而是要不要跟著建新的 workflow、screen、field configuration，並改四份 scheme。

Sub-task 的設定細節

全站開關、多種 type、刪除前置作業

全站開關

⚙ → Issues → Sub-tasks → Enable／Disable

  • 預設啟用。
  • 要停用前，必須先把所有既有 sub-task 轉成 standard type（Move → convert to issue）。
  • 這是全站設定——一關全部 project 都沒 sub-task。
多種 sub-task type 與刪除
  • 可建多個 sub-task type（「Sub-task」「QA sub-task」「Design sub-task」），各自可對不同 workflow／screen；建立時可選加進哪個 issue type scheme。
  • 刪 sub-task type 前要先搜尋並 bulk move 該 type 的所有 issue 到別的 type，否則資料會卡住。

不繼承的東西Fix versions、components、assignee、priority、估點都不繼承，要自己填。「parent 有 fix version，sub-task 就會出現在 release report」是錯的

證據界線：epic 底下能不能直接掛 sub-task

階層模型的標準答案是 epic → standard → sub-task，考試照這個作答。但官方 Create a work item and a subtask 補了一個例外：在 company-managed software space，可以用工作項目上的 Add parent 連結，把 subtask 直接指到 project 用來裝大塊工作的那個 type（預設就是 epic）。

Condition 和 validator 差在哪
這一項是 condition，不是 validator，兩者攔截的時間點不同：condition 在你還沒動作前就把轉換按鈕整個藏起來，你根本看不到那個選項；validator 則是讓按鈕照常出現，等你按下去、送出表單之後才跳錯誤擋下來。考題常拿這兩個互換來設陷阱，看到「按鈕不見了」就是 condition，看到「按了才報錯」才是 validator。

「擋住 parent」與「自動完成 parent」是兩種不同的東西

需求做法特性
sub-task 沒完成就不准 parent 轉到 DoneWorkflow → transition → Subtask Blocking Condition需 Jira admin（或該 project 專用 workflow 的 project admin）；按鈕直接消失；只有 CMP 有

推薦題練習

先想「要新 type？用哪一層？」再看解答

QA 團隊回報的缺陷需要「Steps to reproduce」「Severity」兩個必填欄位，並且要多一個「Verified」狀態才能關閉。
解答
應該新建一個 issue type「Bug」（或直接沿用內建的 Bug），並替它配一份專用的 screen 與專用的 workflow。判斷依據很明確：這類工作既需要不同的必填欄位（Steps to reproduce、Severity），又需要不同的流程（多一個 Verified 狀態），兩個條件都踩到了，就值得獨立成一個 type。實際要動的是三份 scheme，而且都得請 Jira admin 出手：issue type screen scheme（決定這個 type 用哪張畫面）、field configuration scheme（決定哪些欄位必填）、workflow scheme（決定它走哪一套流程）。
PM 想把「行動版」「網頁版」的工作分開看報表，但流程和欄位完全相同。
解答
不要為此新建 issue type。關鍵在題目那句「流程和欄位完全相同」——既然兩者走一樣的 workflow、填一樣的欄位，它們的差別只是分類，而分類該用 Component（建 Mobile 與 Web 兩個）或 label 來做。報表需求也解得掉：用 Pie chart 這類 gadget 依 component 分群即可。為了純分類而增生 issue type，會讓站台的 scheme 愈來愈難維護，是實務上常見的壞味道。
一個 Story 要前端、後端、QA 三個人分別做，PM 想在 sprint 內追蹤各自進度。
解答
用 sub-task。在同一張 Story 底下開三個 sub-task，分別指派給前端、後端、QA，PM 就能在 sprint 內看到各自的進度。要提醒團隊的是：story points 仍然估在 Story 上，不要分散到 sub-task 去填，因為 sub-task 的點數不計入 burndown 與 velocity，填了反而讓人誤以為有算到。
「會員系統改版」預計橫跨四個 sprint，主管想看還要幾個 sprint 才做完。
解答
用一個 epic 來裝。把橫跨四個 sprint 的 story 全部掛在這個 epic 底下，主管要的「還要幾個 sprint」就看 Epic burndown——它會用最近 3 個 sprint 的 velocity 推估剩餘工作還要幾個 sprint 消化得完。前提有兩個：底下的 story 要有 story points 估點，而且必須是 Scrum board（Kanban 沒有 sprint，也就沒有 Epic burndown 可看）。
團隊想停用 sub-task，但按 Disable 失敗。
解答
原因是站台上還存在著 sub-task，Jira 不允許在有資料的情況下把功能關掉，否則那些 issue 會變成孤兒。正確順序是先清資料，再關功能：用 JQL 把所有 sub-task 搜出來（hierarchyLevel = -1，舊版寫法是 issuetype in subtaskIssueTypes()），用 bulk move 或 Move 逐一 convert 成 standard type，全部清空之後才按得動 Disable。也別忘了這是全站設定，關掉會影響站台上每一個 project。
Sub-task 還沒做完，工程師就把 Story 拉到 Done，PM 想阻止。
解答
在 workflow 通往 Done 的那個 transition 上加一個 Subtask Blocking Condition，勾選「所有 sub-task 必須到 Done」。這是 condition，效果是 sub-task 沒做完時，Done 這個按鈕根本不會出現，工程師想拉也拉不了。要注意兩件事：改 workflow 通常要 Jira admin（除非這份 workflow 是該 project 專用的，project admin 才動得了），而且這個 condition 只有 CMP 有，TMP 的 workflow 編輯器沒這一項，得改用 automation 達到近似效果。
主管把 200 個 sub-task 掛在同一張 Task 下，抱怨 time tracking 不準。
解答
問題出在 child 數量。一個 parent 底下的 child 顯示上限是 500 個，一旦超過（或正在逼近），parent 頁面上不但列不出完整的 child 清單，sub-task 的工時也不再被納入 parent 的 time tracking 彙總，所以主管看到的數字才會失準。官方的建議是把工作重新拆成多個 parent，而不是硬塞在同一張 issue 底下。
團隊在 Kanban board 上把 epic 也當卡片拖，問為什麼 epic 不會進 sprint。
解答
因為 epic 是容器，不是 sprint 規劃的單位。真正被放進 sprint、被估點、被燃盡的是它底下的 standard issue（Story、Task、Bug）。epic 在 board 上也不會以卡片形式出現，它出現的位置是 backlog 的 Epic panel 與 Timeline 上的長條；團隊如果一直想拖 epic，通常表示他們把 epic 當成一張大 story 在用，該重新拆一次。
客戶服務團隊要「Refund」和「Complaint」兩種請求，Refund 需要主管核准步驟。
解答
建立兩種 request type／issue type，並且讓 Refund 走一套含 Approval 步驟的 workflow。判斷準則還是那一條：流程不同就該分 type。Refund 多了一個主管核准的關卡，Complaint 沒有，兩者的 workflow 本質上不一樣，硬塞在同一個 type 裡只能靠人工約束，既不可靠也做不出乾淨的報表。
想讓「文件撰寫」這類工作在 velocity 裡不被計算，但仍要追蹤。
解答
最直接的做法是把它做成 sub-task：sub-task 照樣可以被指派、被追蹤、被記錄工時，但它的 story points 不會計入 velocity，剛好符合「要追蹤但不要算進去」的需求。另一條路是另外建一個 issue type，再從 board 的 filter 或 estimation 設定把它排除，但那要多維護一份設定；在官方的階層模型下，sub-task 是最省事也最不容易出錯的答案。
常見陷阱

考題喜歡設的誤解

誤解事實
「Epic 可以直接掛 sub-task」依標準階層不行，epic 的 child 只能是 standard 層的 issue，sub-task 得再掛在 standard 底下（CMP 用 Add parent 的例外見上方說明）
「Sub-task 可以單獨拉進另一個 sprint」不行，sub-task 沒有自己的 sprint 欄位可以獨立設定，它永遠跟著 parent 走
「Sub-task 的 story points 也算 velocity」不算。velocity 與 burndown 只計算 standard 層（也就是 parent）的點數，sub-task 填了也不會被加進去
「Sub-task 開關是 project 層設定」那是全站設定（⚙ → Issues → Sub-tasks），一關就是所有 project 都沒有 sub-task，不能只關某一個 project
「Project admin 可以建新 issue type」在 CMP 不行，issue type 是全站物件，只有 Jira admin 建得了並加進 scheme；TMP 則相反，project admin 自己就能建
「想分類就建新 issue type」如果只是想做分類，用 component、label 或 custom field 就好。新建 issue type 的門檻應該是「它需要不同的 workflow 或不同的欄位」，否則只會讓 scheme 愈養愈亂
「Subtask Blocking Condition 是 validator」它是 condition，會直接把轉換按鈕藏起來；validator 是按下去之後才擋，兩者時機不同
「Initiative 是 Jira 內建的第四層」標準階層只有 epic／standard／sub-task；更高層要 Premium 的 Plans。把 epic 取名叫 Initiative 不會多出一層
「站台上有這個 issue type，我的 project 就用得到」三項都要成立：該 type 在 project 的 issue type scheme 裡、對應 screen 上有你要填的欄位、你有該 project 的 Create Issues 權限
「Sub-task 什麼都繼承 parent」只繼承 project、issue security level 與 sprint；fix versions／components／assignee 都不繼承
「Business 與 JSM project 也是 epic／story／task」預設 type 不同：business 以 Task／Sub-task 為主，JSM 用 request types 對應到底層 issue types
「TMP 也能加 Subtask Blocking Condition」這是 CMP workflow 的 condition，TMP 的 workflow 編輯器沒有這一項；TMP 要做類似效果得靠 automation
實作（20 分鐘）

把「type 是標籤」看成實體

  1. 在 CMP 建一個 epic，掛三張 story，每張 story 掛兩個 sub-task；開 Timeline 看 epic 長條與 child；把其中一張 story 拉進 sprint，觀察 sub-task 一起進去。
  2. 給 sub-task 填 story points，開 sprint 後看 burndown 縱軸——確認沒算進去。
  3. 請 Jira admin（或自己有權限）在 Done transition 加 Subtask Blocking Condition；sub-task 未完成時看 Done 按鈕消失。
  4. 試著停用全站 sub-task，觀察錯誤訊息；把一個 sub-task 用 Move 轉成 Task，再試一次。
  5. 在 ⚙ → Issues → Issue type schemes 看你的 project 用哪份 scheme，再看 workflow scheme 與 issue type screen scheme 裡 Bug 與 Task 各對到什麼。
  6. 建 sub-task 時觀察繼承：先給 parent 一個 issue security level 並放進 sprint，再建 sub-task。
    預期：project、security level、sprint 三項自動帶入；Fix versions 是空的——不繼承。
  7. 做一條 automation：所有 sub-task 轉 Done 時自動把 parent 轉 Done。
    預期：跟第 3 步的 blocking condition 對照——一個是事前擋住按鈕，一個是事後自動推進。
