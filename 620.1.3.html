620.1.3 · Recommend an issue type configuration for a company-managed project

為 company-managed project 推薦 issue type 設計

這一節資料量不大，但它是整份考試「推薦題」的第一站，重點在判斷而不是操作：需要哪些 issue type？該用 epic／standard／sub-task 哪一層？要不要新建 type？

術語：考試用 project／issue／sub-task；現行產品為 space／work item／subtask。本教材沿用考試用語。
這一節考什麼

標題的三個關鍵字

關鍵字意思
business requirements題目給你一段情境（團隊怎麼工作、要追蹤什麼）
recommend你要選：需要哪些 issue type？哪一層？要不要新建？
company-managedCMP 的 issue type 是「標籤 ＋ scheme」，建新 type 要 Jira admin；你是 project admin，要懂什麼時候該去請 Jira admin 建、什麼時候不必

唯一的 bullet：「Understand the features associated with epics, base (standard) and sub-task issue types」——三層各自能做什麼、不能做什麼。

三層階層

先把「能力表」背起來

滑鼠移到圖中的層級，下方對應的能力卡會亮起。

圖 1　Epic 的 child 只能是 standard；sub-task 不能直接掛在 epic 下。
Epic
  • 獨立進 sprint：不會（它是容器）
  • Board 上：不以卡片出現；在 backlog 的 Epic panel、Timeline 是長條
  • Story points 計入 burndown：不算（用 child 加總）
  • Time tracking：child 可 roll-up
  • 專屬報表：Epic report、Epic burndown、Timeline
  • Child 顯示上限 500
Standard（Story／Task／Bug）
  • 獨立進 sprint：可，sprint 的基本單位
  • Board 上：卡片
  • Story points 計入 burndown／velocity：算
  • Time tracking：可；sub-task 工時可 roll-up 到它
  • 專屬報表：Sprint report、burndown 等
  • Child（sub-task）顯示上限 500
Sub-task
  • 獨立進 sprint：不行，跟著 parent
  • Board 上：卡片，通常在 parent 的泳道下
  • Story points 計入 burndown／velocity：不算
  • Time tracking：可，roll-up 到 parent
  • 專屬報表：無（併入 parent）
  • Issue security：繼承 parent
500 上限的後果（考點）
超過 500 個 child，parent 上看不到 child 清單（得用搜尋），而且 sub-task 不再納入 parent 的 time tracking 彙總。官方建議拆成多個 parent。

官方定義句

  • Epic：high-level initiatives，把相關工作分組的大型工作項目。
  • Standard：regular business tasks，日常工作實際發生的層級。
  • Sub-task：把 standard 拆成更小的塊，只能當 child。

三層在 Scrum vs Kanban 的角色

層ScrumKanban
Epic跨 sprint 的主題；看 Epic burndown 預測還要幾個 sprint同樣是主題容器，在 Timeline 上排長條；沒有 sprint 就沒有 Epic burndown
Standardsprint 承諾的單位，估點流過 board 的卡片，看 cycle time
Sub-tasksprint 內分工，不影響 velocity同一卡片的分工；Stories 泳道下顯示
核心模型

CMP 的 issue type 是「標籤 ＋ 四張對照表」

在 CMP，一個 issue type 本身沒有任何行為，行為全靠 scheme 對應出來。點上方的 type，看它各自對到哪一份 workflow、screen、field configuration。

圖 2　「建一個新 issue type」的真正成本不是建 type，而是要不要跟著建新的 workflow、screen、field configuration，並改四份 scheme。

預設有哪些 type

Project 類型ParentStandardChild
SoftwareEpicStory、Task、BugSub-task
Business—TaskSubtask
Service management—Service request、Incident、Problem、Change、IT help…—

考題可能問「Software project 預設沒有哪個 type」→ 沒有 Initiative（Premium 才有更上層）。

Sub-task 的設定細節

全站開關、多種 type、刪除前置作業

全站開關

⚙ → Issues → Sub-tasks → Enable／Disable

  • 預設啟用。
  • 要停用前，必須先把所有既有 sub-task 轉成 standard type（Move → convert to issue）。
  • 這是全站設定——一關全部 project 都沒 sub-task。
多種 sub-task type 與刪除
  • 可建多個 sub-task type（「Sub-task」「QA sub-task」「Design sub-task」），各自可對不同 workflow／screen；建立時可選加進哪個 issue type scheme。
  • 刪 sub-task type 前要先搜尋並 bulk move 該 type 的所有 issue 到別的 type，否則資料會卡住。

Sub-task 與 parent 的互動規則

行為規則
Sprint跟 parent 同進同出，不能單獨拉
Board 清除（TMP Kanban）parent 被清，sub-task 不論狀態一起清
Issue security繼承 parent 的 level，不能單獨設
Story points不計入 burndown／velocity
時間追蹤工時可彙總到 parent（parent 的 time tracking 面板勾 include sub-tasks）
Move 到別的 project要跟 parent 一起，或先轉成 standard
轉換Sub-task ↔ standard 都可透過 Move 功能轉換；轉成 sub-task 時要指定 parent
建立時繼承新 sub-task 自動繼承 parent 的 project、issue security level，以及 sprint（software project）。官方原句：sub-task 會 inherit the space, work security level, and sprint value (software spaces) from their parent
不繼承的東西Fix versions、components、assignee、priority、估點都不繼承，要自己填。「parent 有 fix version，sub-task 就會出現在 release report」是錯的
CMP 的前置條件要能建 sub-task，Jira admin 必須啟用 sub-tasks 而且把 sub-task type 加進該 project 的 issue type scheme——兩個條件缺一不可
證據界線：epic 底下能不能直接掛 sub-task

階層模型的標準答案是 epic → standard → sub-task，考試照這個作答。但官方 Create a work item and a subtask 補了一個例外：在 company-managed software space，可以用工作項目上的 Add parent 連結，把 subtask 直接指到 project 用來裝大塊工作的那個 type（預設就是 epic）。

遇到「epic 的 child 是什麼類型」選階層答案；遇到「Add parent 能不能指到 epic」再想這個例外。

來源：Create a work item and a subtask

Subtask Blocking Condition

Workflow → 編輯 → 選 transition（例如 Resolve）→ Add condition → Subtask Blocking Condition → 勾選 sub-task 必須達到的狀態

效果：parent 的 sub-task 沒全部到指定狀態前，parent 的那個 transition 按鈕直接不出現。把下面三個 sub-task 逐一切到 Done 試試。

Condition vs validator
這是「condition」不是「validator」——condition 隱藏轉換按鈕，validator 在按下後才擋。

「擋住 parent」與「自動完成 parent」是兩種不同的東西

需求做法特性
sub-task 沒完成就不准 parent 轉到 DoneWorkflow → transition → Subtask Blocking Condition需 Jira admin（或該 project 專用 workflow 的 project admin）；按鈕直接消失；只有 CMP 有
sub-task 全部完成就自動把 parent 轉到 DoneAutomation rule：trigger 用 work item transitioned，條件檢查「所有 sub-task 都是 Done」，action 轉換 parentTMP／CMP 都可用；是事後自動做，不是事前擋住
把 sub-task 的日期彙總回 parentAutomation 對 sub-task 分支，取最早 start date 與最晚 due date 寫回 parent兩個方向要用不同取法（min 與 max）；直接把「最後一筆」寫回去是最常見的錯誤
關鍵字 → 答案
看到「prevent／can’t be completed until」→ Subtask Blocking Condition；看到「automatically close the parent when all subtasks…」→ automation rule。前者是 workflow condition，後者跟 workflow 無關。
Epic 的功能

bullet 明列要懂的另一半

功能說明
Parent 欄位現行 Jira 用 Parent 欄位取代舊的 Epic Link；在 standard issue 上填 parent = 某 epic
Backlog 的 Epic panel依 epic 篩選 backlog、拖曳 issue 進 epic
Timeline／Roadmapepic 是長條，child 在下面；可畫依賴線；沒有 parent 的 issue 不會出現在 Timeline
Epic report某時點的完成／未完成／未估點清單
Epic burndown依 sprint 看進度，用近 3 sprint velocity 預測還要幾個 sprint
Epic 顏色卡片上的 epic 標籤色；card colors 也可 by epic
Swimlanes by EpicBoard 依 epic 分泳道
跨 projectCMP 的 epic 可以有別的 project 的 standard issue 當 child

推薦題練習

先想「要新 type？用哪一層？」再看解答

QA 團隊回報的缺陷需要「Steps to reproduce」「Severity」兩個必填欄位，並且要多一個「Verified」狀態才能關閉。
解答
新建 issue type「Bug」（或沿用 Bug）並配專用 screen 與專用 workflow——流程與欄位都不同；請 Jira admin 改 issue type screen scheme、field configuration scheme、workflow scheme。
PM 想把「行動版」「網頁版」的工作分開看報表，但流程和欄位完全相同。
解答
不要新 type；用 Component（Mobile／Web）或 label，報表用 Pie chart by component。
一個 Story 要前端、後端、QA 三個人分別做，PM 想在 sprint 內追蹤各自進度。
解答
Sub-task；同一 Story 下三個 sub-task 各自指派；story points 仍算在 Story 上。
「會員系統改版」預計橫跨四個 sprint，主管想看還要幾個 sprint 才做完。
解答
Epic；把四個 sprint 的 story 都掛在該 epic 下，看 Epic burndown（需 story points 估點、Scrum board）。
團隊想停用 sub-task，但按 Disable 失敗。
解答
站台上還有既存 sub-task；先搜 issuetype in subtaskIssueTypes()，bulk move／convert 成 standard，再停用。
Sub-task 還沒做完，工程師就把 Story 拉到 Done，PM 想阻止。
解答
在 workflow 的 Done transition 加 Subtask Blocking Condition（需 Jira admin，除非 workflow 為該 project 專用）。
主管把 200 個 sub-task 掛在同一張 Task 下，抱怨 time tracking 不準。
解答
超過 500 child 顯示上限（或正在逼近），sub-task 不再納入 parent 時間追蹤；拆成多個 parent。
團隊在 Kanban board 上把 epic 也當卡片拖，問為什麼 epic 不會進 sprint。
解答
Epic 是容器層，不是 sprint 的單位；要進 sprint 的是它底下的 standard issue。
客戶服務團隊要「Refund」和「Complaint」兩種請求，Refund 需要主管核准步驟。
解答
兩種 request type／issue type，Refund 配含 Approval 步驟的 workflow——流程不同就該分 type。
想讓「文件撰寫」這類工作在 velocity 裡不被計算，但仍要追蹤。
解答
Sub-task（story points 不計 velocity），或另建 type 但在 board filter／estimation 上排除；官方模型下最直接是 sub-task。
常見陷阱

考題喜歡設的誤解

誤解事實
「Epic 可以直接掛 sub-task」不行，epic 的 child 只能是 standard
「Sub-task 可以單獨拉進另一個 sprint」不行，跟 parent
「Sub-task 的 story points 也算 velocity」不算，只算 parent
「Sub-task 開關是 project 層設定」全站設定
「Project admin 可以建新 issue type」CMP 不行，Jira admin 才行（TMP 可以）
「想分類就建新 issue type」只是分類用 component／label／custom field
「Subtask Blocking Condition 是 validator」是 condition，會直接隱藏轉換按鈕
「Initiative 是 Jira 內建的第四層」標準階層只有 epic／standard／sub-task；更高層要 Premium 的 Plans。把 epic 取名叫 Initiative 不會多出一層
「站台上有這個 issue type，我的 project 就用得到」三項都要成立：該 type 在 project 的 issue type scheme 裡、對應 screen 上有你要填的欄位、你有該 project 的 Create Issues 權限
「Sub-task 什麼都繼承 parent」只繼承 project、issue security level 與 sprint；fix versions／components／assignee 都不繼承
「Business 與 JSM project 也是 epic／story／task」預設 type 不同：business 以 Task／Sub-task 為主，JSM 用 request types 對應到底層 issue types
「TMP 也能加 Subtask Blocking Condition」這是 CMP workflow 的 condition，TMP 的 workflow 編輯器沒有這一項；TMP 要做類似效果得靠 automation
實作（20 分鐘）

把「type 是標籤」看成實體

  1. 在 CMP 建一個 epic，掛三張 story，每張 story 掛兩個 sub-task；開 Timeline 看 epic 長條與 child；把其中一張 story 拉進 sprint，觀察 sub-task 一起進去。
  2. 給 sub-task 填 story points，開 sprint 後看 burndown 縱軸——確認沒算進去。
  3. 請 Jira admin（或自己有權限）在 Done transition 加 Subtask Blocking Condition；sub-task 未完成時看 Done 按鈕消失。
  4. 試著停用全站 sub-task，觀察錯誤訊息；把一個 sub-task 用 Move 轉成 Task，再試一次。
  5. 在 ⚙ → Issues → Issue type schemes 看你的 project 用哪份 scheme，再看 workflow scheme 與 issue type screen scheme 裡 Bug 與 Task 各對到什麼。
  6. 建 sub-task 時觀察繼承：先給 parent 一個 issue security level 並放進 sprint，再建 sub-task。
    預期：project、security level、sprint 三項自動帶入；Fix versions 是空的——不繼承。
  7. 做一條 automation：所有 sub-task 轉 Done 時自動把 parent 轉 Done。
    預期：跟第 3 步的 blocking condition 對照——一個是事前擋住按鈕，一個是事後自動推進。
